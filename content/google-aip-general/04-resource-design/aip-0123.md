大多数 APIs 暴露 *resources*（其主要名词），用户可以创建、检索与操作它们。APIs 可以在本 AIP 要求范围内相当自由地命名其资源类型，并且只须确保在该 API 内唯一。这意味着不同 APIs 使用相同类型名是可能的（且常常是可取的）。例如，Memcache 与 Redis API 都会想把 `Instance` 用作类型名。

然而，在映射 APIs 与其资源之间的关系时，拥有单个全局唯一的类型名变得重要。此外，Kubernetes 或 GraphQL 等工具会与来自多个提供方的 APIs 交互。

## Terminology

在下列指导中，我们使用这些术语：

- **Service Name：** 在 [service configuration](https://github.com/googleapis/googleapis/blob/master/google/api/service.proto) 中定义的名称。这通常（但不一定）匹配用户用来调用该服务的主机名。示例：`pubsub.googleapis.com`。这等价于 Kubernetes 中的 [API Group](https://kubernetes.io/docs/concepts/overview/kubernetes-api/#api-groups)。
- **Type：** 在 API 内用于该类型的名称，例如 Protobuf `message` 的名称。这等价于 Kubernetes 中的 [Object](https://github.com/kubernetes/community/blob/master/contributors/devel/sig-architecture/api-conventions.md#types-kinds)。

## Guidance

APIs **must** 为 API 中的每个资源定义资源类型，遵循下列模式：`{Service Name}/{Type}`。类型名 **must**：

- 匹配包含它的 API 类型的名称。
- 以大写字母开头。
- 只含字母数字字符。
- 为该名词的单数形式。
- 使用 PascalCase（UpperCamelCase）。

### Examples

资源类型的例子包括：

- `pubsub.googleapis.com/Topic`
- `pubsub.googleapis.com/Subscription`
- `spanner.googleapis.com/Database`
- `spanner.googleapis.com/Instance`
- `networking.istio.io/Instance`

### Annotating resource types

APIs **should** 使用 [`google.api.resource`](https://github.com/googleapis/googleapis/blob/master/google/api/resource.proto) annotation 为 API 中的每个资源标注资源类型：

```proto
// A representation of a Pub/Sub topic.
message Topic {
  option (google.api.resource) = {
    type: "pubsub.googleapis.com/Topic"
    pattern: "projects/{project}/topics/{topic}"
    singular: "topic"
    plural: "topics"
  };

  // Name and other fields...
}
```

- Patterns **must** 对应 [resource name]({{< ref "aip-0122" >}})。
- Pattern 变量（花括号内的段）**must** 使用 `snake_case`，并且 **must not** 使用 `_id` 后缀。
- Pattern 变量 **must** 符合格式 `[a-z][_a-z0-9]*[a-z0-9]`。
- Pattern 变量在任意给定 pattern 内 **must** 唯一。（例如 `projects/{abc}/topics/{abc}` 无效；这通常是 collection identifiers 在 pattern 内唯一的自然推论。）
- 具有 [多个 patterns](https://google.aip.dev/client-libraries/4231#multi-pattern-resources) 的资源 **must** 保持顺序：新 patterns **must** 加在列表末尾，既有 patterns **must not** 被移除或重排，因为这会破坏 client library 向后兼容。
- Singular **must** 为该类型的 lower camel case。
  - Pattern 变量 **must** 为资源类型的单数形式，例如表示 `Topic` resource ID 的 pattern 变量名为 `{topic}`。
- Plural **must** 为 singular 的 lower camel case 复数。
  - Pattern 的 collection identifier 段 **must** 匹配这些资源的 plural，[nested collections]({{< ref "aip-0122" >}}) 的情形除外。

#### Pattern uniqueness

当一个资源内定义多个 patterns 时，这些 patterns **must** 彼此唯一；唯一性定义为：去掉所有 resource ID 路径段、留下所有 `/` 分隔符之后，按字符完全相同。

因此下列两个 patterns **must not** 定义在同一资源内：

- `user/{user}`
- `user/{user_part_1}~{user_part_2}`

## Rationale

### Type 与 message 名对齐

除了简单的 schema-resource 一致与对齐之外，许多消费者也受益于 `{Type}` 与 `message` 名称匹配。消费者有更简单的查找，client libraries 除同样好处外还有对齐的用户体验（面向资源的代码命名与生成的 `message` 代码对齐），生成的参考文档把资源与 `message` 文档对齐，等等。

### Singular 与 Plural

资源定义良好的单复数，使客户端能确定在代码与文档中应使用的恰当名称。

lowerCamelCase 可以翻译成资源名的其它常见形式，例如 UpperCamelCase 与 snake_case。
