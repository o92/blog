有些字段只接受（或只返回）一小撮离散值。这时用 enumerations（通常叫 enums）能把允许值说清楚。问题是：enum 一加新值，客户端和兼容性都会跟着疼。这篇讲什么时候用、怎么命名、什么时候改用 string。

## 怎么写

API 可以为预期不频繁变化的值集合暴露 enum：

```proto
// A representation of a book.
message Book {
  // Other fields...

  // Possible formats in which the book may be published.
  enum Format {
    // Default value. This value is unused.
    FORMAT_UNSPECIFIED = 0;

    // The printed format, in hardback.
    HARDBACK = 1;

    // The printed format, in paperback.
    PAPERBACK = 2;

    // An electronic book format.
    EBOOK = 3;

    // An audio recording.
    AUDIOBOOK = 4;
  }

  // The format of the book.
  Format format = 99;

  // Other fields...
}
```

- 所有 enum 值必须用 `UPPER_SNAKE_CASE`。
- 第一个值应当是 enum 名称本身后接 `_UNSPECIFIED`。
  - 若零值本身就很有用，可以例外。尤其是需要 `UNKNOWN` 时，把它当零值通常比两个都留更清楚。`UNKNOWN` 可以加 enum 名称当前缀，这是避免值名冲突的常见做法。
- 只在单个 message 里用的 enums 应当嵌在该 message 内，并且应当紧挨在使用它之前声明。
  - 这种嵌套 enum 的非零值不应当再以 enum 名称本身为前缀。否则用户代码会写成 `MyState.MYSTATE_ACTIVE`，没必要那么长。
- 会被多个 messages 使用的 enums 应当在 package 级定义，并且应当放在 proto 文件底部（见 [AIP-191]({{< ref "aip-0191" >}})）。
  - 某些语言（包括 C++）会把 enum 值提升到父命名空间。同一 proto package 里若有同名值就会撞车。为避免共享值冲突，package 级 enum 值应当用 enum 名称加前缀。
- Enums 应当写明：这套值是冻结的，还是预期以后还会加。

### 何时用 enums

Enums 往往比 strings 或 booleans 更好读，但一改就有开销。因此 enums 应当不频繁接收新值。「不频繁」随用例而变，一个好的经验法则是每年不超过一次。变得勤的，应当改用 string 并文档化格式。

已经有相互竞争、被广泛采用的标准表示时（例如 [language codes](https://en.wikipedia.org/wiki/IETF_language_tag) 或 [media types](https://en.wikipedia.org/wiki/Media_type)），不应当用 enums。

枚举值需要跨 API 共享时，可以用 enum，但值与对应整数的赋值必须一致。

### 其它选项

允许值集合变得勤时，应当改用 `string` 字段，并且必须文档化允许值。这种带枚举语义的 string 应当用 `kebab-case`。

已有相互竞争、被广泛采用的标准表示时（一般但不一定是 string），应当直接用那个标准。哪怕你只允许其中很小一个子集也一样。这时再包一层 enum，把多个 API 拼在一起用时就会被迫做查找表，很烦。

确实不需要再留灵活性时，可以用 boolean。默认值必须是 `false`。

用 protocol buffers 时，`false` 和「未设置」分不开。若必须分清，enum 可能是更好的设计（`google.protobuf.BoolValue` 也能用）。
