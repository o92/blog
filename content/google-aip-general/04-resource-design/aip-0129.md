服务常常给资源字段填默认值，偶尔还会在返回前把用户输入规范化。声明式客户端最怕的就是：我写下的值和你还回来的值对不上，又说不清该不该再改一次。这篇讲这种行为怎么拆字段、怎么文档化。

## 字段只能有一个所有者

字段必须有单一所有者，不是客户端就是服务器。服务器拥有的字段必须用 `OUTPUT_ONLY` field_behavior 标明。其它字段一律视为客户端拥有。服务器必须尊重所有客户端拥有字段的值（包括缺省），并且不得修改它们。

## 生效值

客户端不指定时，服务有时会分配、生成或算出一个值。例如创建虚拟机时没给静态 IP，等于选择动态分配。

常见几类：

- 生成的（UUID）
- 分配的（动态 IP 地址）
- 指定的（最近的软件包版本）

有生效值的属性必须在 API 里拆成两个字段：

- 一个可变字段，用户可以选填，服务不得改
- 一个 `OUTPUT_ONLY` 字段，记录服务决定的生效值

示例：

```proto
message VirtualMachine {
  …
  string ip_address = 4;
  string effective_ip_address = 5 [
    (google.api.field_behavior) = OUTPUT_ONLY
  ];
}
```

### 怎么命名

生效值必须在可变字段名前加前缀 `effective_`。

## 用户指定的字段

用户指定的字段，响应里的值必须与 create 或 update 请求里给的相同。对 string 字段，这意味着原样返回。只有一个例外：

- 字段带 data type annotation 时，可以返回表示该值的规范化 string。

## 规范化

被服务规范化的字段必须用 `google.api.field_info` 扩展标注。怎么用见 [AIP-202]({{< ref "aip-0202" >}})。允许的规范化集合包括：

- uuid
- ipv4
- ipv6
- email

字段上的规范化必须用 `google.api.field_info` annotation 写出来。

## 为什么

服务端修改与默认值常常让 Declarative Clients（见 [AIP-9]({{< ref "aip-0009" >}})）更难写。这些客户端很难判断期望状态何时已经对上：服务改值的规则复杂、不公开、还不可重复。

### 为什么要单一所有者

字段没有单一所有者时，Declarative Clients 会踩坑：客户端给一个值，服务器又盖掉，客户端再纠正，进入死循环。

### 为什么要统一命名

命名一致，跨 API、跨字段才能认出同一套行为。用户指定值与生效值之间的程序化关联，靠的就是这个前缀约定。

### 为什么要披露规范化

规范化让服务能用标准方式存值和还值，同时告诉客户端哪些变更在语义上相同。服务侧做规范化，就能接受更广的、语义相同的输入，而不必把每个值都当原始 string 原样保管。向客户端披露正在用哪种规范化，客户端才能比较发送值和取回值，判断有没有实质差异。

例如某个字段接受电子邮件。对 `ada@example.com`，客户端可能写成 `ADA@example.com`、`aDa@example.com` 或 `AdA@example.com`。这些在语义上相同，服务应当全部接受。服务随后可能用小写化等方式规范化后再存。重要的是：披露给客户端的不是算法细节，而是用来判断两个值该不该视为相等的比较方法。

### 字段值怎么对

没用允许的规范化时，Declarative Clients 分不清哪些变更在语义上有意义。Declarative Client 发出一个值之后，会核对服务是不是原样还回来，以此确认设置成功。
