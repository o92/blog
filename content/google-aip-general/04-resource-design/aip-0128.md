**英文标题**：Declarative-friendly interfaces  
**原文**：[AIP-128](https://google.aip.dev/128) · approved · 创建 2020-10-06  
**许可**：原文 © Google，[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)

很多服务要跟常见 DevOps 工具对接，尤其是管虚拟机、负载均衡器、数据库实例这类可网络寻址资源的工具。这些工具围着 configuration as code 转：用户给出完整的意图景观，工具负责把现状改到那个样子。

它们是 **declarative** 的：不写具体要采取哪些 *actions*，只写期望的 *outcome*。动作由「现在怎样」和「想要怎样」之间的差推导出来。

流行的 DevOps 工具很多，每年还在增加。几百种资源类型对多种工具，靠人手对接扛不住。接口得统一，集成才能自动化。

## 资源

声明式友好的资源必须只用强一致的标准方法来管生命周期。这样工具才能通用地支持它们，也才能跟上其它声明式友好指导（见下文延伸阅读）。

应当标明自己遵循声明式友好风格：

```proto
message Book {
  option (google.api.resource) = {
    type: "library.googleapis.com/Book"
    pattern: "publishers/{publisher}/books/{book}"
    style: DECLARATIVE_FRIENDLY
  };

  // Name and other fields...
}
```

## 调和

更新要花一段时间（多于几秒）才能落地时，资源应当带一个 `bool reconciling` 字段，用来披露变更还在进行中。该字段必须是 output only。

当前状态与用户意图对不上、系统正在调和时，必须把 `reconciling` 设为 `true`。不管调和是用户动作引起的，还是系统自己引起的。

服务响应 `GET` 时必须返回资源的当前状态，不是意图状态。

## 延伸阅读

声明式友好接口上，自动化是第一目标，所以其它 AIP 里的要求往往更严。完整对照：

- 资源不应当用 custom methods：见 [AIP-136]({{< ref "aip-0136" >}})。
- 资源必须用 `Update` 改 repeated fields：见 [AIP-144]({{< ref "aip-0144" >}})。
- 资源必须带若干标准字段：见 [AIP-148]({{< ref "aip-0148" >}})。
- 资源必须有 `etag` 字段：见 [AIP-154]({{< ref "aip-0154" >}})。
- 资源应当提供变更校验：见 [AIP-163]({{< ref "aip-0163" >}})。
- 资源不应当做 soft-delete。若 id 不能复用，资源必须做 soft-delete 以及 undelete RPC：见 [AIP-164]({{< ref "aip-0164" >}})。

annotations 见 [AIP-148]({{< ref "aip-0148" >}})。
