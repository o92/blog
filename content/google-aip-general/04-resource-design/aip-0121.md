**英文标题**：Resource-oriented design  
**原文**：[AIP-121](https://google.aip.dev/121) · approved · 创建 2019-01-26

面向资源的设计把 API 先看成一张资源图，再往资源上挂少量动词。它从 [REST](https://en.wikipedia.org/wiki/Representational_state_transfer) 借了不少原则，但并不等于 REST：接口用 [RPC](https://en.wikipedia.org/wiki/Remote_procedure_call) 定义，同时还能转成大家更熟的 HTTP/JSON。

核心就三句话：

- 基本构件是单独命名的 resources（名词），以及它们之间的关系和层级。
- 常见操作尽量用少量标准 methods（动词）；标准方法盖不住再用 custom methods。
- 协议无状态：每一次请求彼此独立，客户端和服务器角色清楚。

## 先定资源，再定方法

设计时按这个顺序想，不要反过来先堆 RPC：

1. API 要提供哪些 resources（名词）
2. 它们之间的关系和层级
3. 每个 resource 的 schema
4. 每个 resource 上有哪些 methods（动词），能用标准动词就用标准动词

典型的面向资源 API 是「资源种类多，每个资源上方法少」。

## 资源与集合

应当把 API 建成一棵资源树。树上每个节点要么是单个资源，要么是 collection（同一类型资源的集合）。例如一个 publisher 下面有它出版的 books 集合。

资源可以有字段，也可以再挂子资源（多半还是 collections）。

有面向资源的 API，并不等于这个服务是数据库。API 表面跟表结构一一对应反而是反模式：表面会和存储死锁在一起。设计者不要指望 API 去镜像数据库 schema。

## 标准方法

能用标准方法就用标准方法：Get、List、Create、Update、Delete（见 [AIP-131]({{< ref "aip-0131" >}}) 到 [AIP-135]({{< ref "aip-0135" >}})）。盖不住的功能再用 custom methods（见 [AIP-136]({{< ref "aip-0136" >}})）。

custom method **不是**发明新的 HTTP 动词。它仍然用 `POST` 这类常规动词，只是 URI 里多一段自定义动作。

同一资源不论出现在哪个方法的请求或响应里，schema 必须相同。

| 标准方法 | 请求里 | 响应里 |
|--|--|--|
| Create | 包含该资源 | 就是该资源 |
| Get | 无 | 就是该资源 |
| Update | 包含该资源 | 就是该资源 |
| Delete | 无 | 无 |
| List | 无 | 包含这些资源 |

「无」表示：这个资源既不是请求/响应本身，也不包含在里面。

资源至少必须能 Get，这样 Create、Update、Delete 之后才能核对状态。除了 singleton resources（一个 parent 下永远只有一个，见 [AIP-156]({{< ref "aip-0156" >}})）以外，还必须能 List。

## 强一致性

跑在 management plane 上的方法（见 [AIP-111]({{< ref "aip-0111" >}})），一旦调用完成——成功、失败、同步或 long-running 都算——资源在不在、以及所有用户能设的值，都必须已经稳定。随后再 Get，必须立刻看到这个结果。

例如：

- Create 成功后再 Get，必须拿到这个资源。
- Update 成功后再 Get，必须是这次写入的最终值。
- Delete 成功后再 Get，必须是 `NOT_FOUND`；若做了 soft delete（见 [AIP-164]({{< ref "aip-0164" >}})），则带着 `DELETED` 状态回来。

客户端经常要串操作：先建 A，再建依赖 A 的 B。只有「方法返回了 = 状态已经稳了」，下一步才敢开工。

Output only 字段（见 [AIP-203]({{< ref "aip-0203" >}})）最好也遵守同一条。但它们常常表示实时状态，变更完成之后还可能再变，这是允许的。跟资源 State（见 [AIP-216]({{< ref "aip-0216" >}})）绑在一起的 output only 值，则应当已经稳定。

## 无状态

面向资源 API 必须跑在 [无状态协议](https://en.wikipedia.org/wiki/Stateless_protocol) 上：这一次请求不依赖你之前发过什么。每个资源都能直接用名字找到，不必先走一套「导航请求」才能到达。

服务器负责把数据存住（还可能被多个客户端共享）；应用状态由客户端自己管。

## 不要环

资源之间的引用必须能画成 [有向无环图](https://en.wikipedia.org/wiki/Directed_acyclic_graph)（resource references 见 [AIP-122]({{< ref "aip-0122" >}})）。parent-child 也必须无环，而且每个实例只有一个规范 parent（见 [AIP-124]({{< ref "aip-0124" >}})）。

如果 A 和 B 互相引用，创建就要拆成三步：先建空的 A，再建引用 A 的 B，再回写 A。删除时还要先想清楚拆哪条边。管理成本会明显上去。

用户要填的引用不能成环。output only 字段里的关系可以例外：用户不用填，不会把创建/删除流程搞复杂。
