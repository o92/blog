**英文标题**：Resource-oriented design  
**原文**：[AIP-121](https://google.aip.dev/121) · approved · 创建 2019-01-26

面向资源的设计是一种指定 [RPC](https://en.wikipedia.org/wiki/Remote_procedure_call) APIs 的模式，基于若干高层设计原则（其中多数与近期的公开 HTTP APIs 共通）：

- API 的基本构件是单独命名的 *resources*（名词）以及它们之间存在的关系与层级。
- 少量标准 *methods*（动词）为大多数常见操作提供语义。然而，在标准方法不适用时，可以使用 custom methods。
- 无状态协议：客户端与服务器之间的每次交互彼此独立，且客户端与服务器都有明确角色。

读者可能会注意到这些原则与 [REST](https://en.wikipedia.org/wiki/Representational_state_transfer) 的某些原则相似；面向资源的设计从 REST 借用许多原则，同时也在合适之处定义自己的模式。

## Guidance

设计 API 时，考虑下列事项（大致按逻辑顺序）：

- API 将提供的 resources（名词）
- 这些 resources 之间的关系与层级
- 每个 resource 的 schema
- 每个 resource 提供的 methods（动词），尽可能依赖标准动词。

### Resources

面向资源的 API **should** 一般建模为资源层级，其中每个节点要么是简单资源，要么是资源集合。

一个 *collection* 包含 *同一类型* 的资源。例如，一个 publisher 拥有它出版的 books 集合。资源通常有字段，并且资源可以有任意数量的子资源（通常是 collections）。

**Note:** 尽管存储系统与 APIs 之间有一些概念对齐，具有面向资源 API 的服务并不一定是数据库，并且在如何解释 resources 与 methods 上有巨大灵活性。API 设计者 **should not** 期望其 API 会反映其数据库 schema。事实上，API 与底层数据库 schema 完全相同其实是一种反模式，因为它把表面与底层系统紧紧耦合。

### Methods

面向资源的 APIs 强调 resources（数据模型）胜过对这些 resources 执行的 methods（功能）。典型的面向资源 API 暴露大量资源，每个资源上只有少量方法。这些方法可以是标准方法（Get（[AIP-131]({{< ref "aip-0131" >}})）、List（[AIP-132]({{< ref "aip-0132" >}})）、Create（[AIP-133]({{< ref "aip-0133" >}})）、Update（[AIP-134]({{< ref "aip-0134" >}})）、Delete（[AIP-135]({{< ref "aip-0135" >}})）），或 custom methods（[AIP-136]({{< ref "aip-0136" >}})）。

若标准方法（或同一 *service* 中的 custom method）的请求或响应 **是** 该资源或 **包含** 该资源，则该资源在所有方法中的资源 schema **must** 相同。

| Standard method | Request | Response |
|--|--|--|
| Create | 包含该资源 | 就是该资源 |
| Get | 无 | 就是该资源 |
| Update | 包含该资源 | 就是该资源 |
| Delete | 无 | 无 |
| List | 无 | 包含这些资源 |

*上表描述每个标准方法与资源的关系，其中「无」表示该资源既 **不是** 请求或响应，也 **不包含于** 请求或响应中。*

资源 **must** 至少支持 Get（[AIP-131]({{< ref "aip-0131" >}})）：客户端必须能在执行 Create（[AIP-133]({{< ref "aip-0133" >}})）、Update（[AIP-134]({{< ref "aip-0134" >}})）或 Delete（[AIP-135]({{< ref "aip-0135" >}})）等变更后校验资源状态。

资源 **must** 也支持 List（[AIP-132]({{< ref "aip-0132" >}})），singleton resources（[AIP-156]({{< ref "aip-0156" >}})）除外（那种情况下不可能有多于一个资源）。

**Note:** 面向资源设计中的 custom method **并不** 意味着定义新的或自定义的 HTTP 动词。Custom methods 使用传统 HTTP 动词（通常是 `POST`），并在 URI 中定义自定义动词。

APIs **should** 优先使用标准方法而非 custom methods；custom methods 的目的是定义无法干净映射到任何标准方法的功能。Custom methods 提供与传统 RPC APIs 相同的设计自由度，可用于实现常见编程模式，例如数据库事务、导入与导出，或数据分析。

### Strong Consistency

对于操作于 management plane（[AIP-111]({{< ref "aip-0111" >}})）的方法，这些操作的完成（无论成功还是带错误、长时运行操作或同步）**must** 意味着资源的存在状态以及所有用户可设置的值都已达到稳态。

与资源 state（[AIP-216]({{< ref "aip-0216" >}})）无关的 Output only（[AIP-203]({{< ref "aip-0203" >}})）值，对于与资源 state（[AIP-216]({{< ref "aip-0216" >}})）相关的值，**should** 也已达到稳态。

例子包括：

- 在一次成功的 create 是某资源上最近一次变更之后，对该资源的 get 请求 **must** 返回该资源。
- 在一次成功的 update 是某资源上最近一次变更之后，对该资源的 get 请求 **must** 返回该 update 请求中的最终值。
- 在一次成功的 delete 是某资源上最近一次变更之后，对该资源的 get 请求 **must** 返回 `NOT_FOUND`（若为 soft delete（[AIP-164]({{< ref "aip-0164" >}})），则返回带 `DELETED` state 值的资源）。

面向资源 APIs 的客户端常常需要按顺序编排多个操作（例如创建资源 A，再创建依赖 A 的资源 B），确保操作完成后资源立即反映稳定的用户状态，才能让客户端把方法完成当作开始下一操作的信号。

Output only（[AIP-203]({{< ref "aip-0203" >}})）字段理想情况下应遵循相同指南，但这些字段常常表示资源的实时状态，因此有时必须在成功的变更操作之后再改变这些值，以反映状态变化。

### Stateless protocol

与当今大多数公开 APIs 一样，面向资源的 APIs **must** 运行于 [无状态协议](https://en.wikipedia.org/wiki/Stateless_protocol) 之上：任何单个请求的基本行为独立于调用者发出的其它请求。也就是说，每个请求与该客户端或另一客户端发出的其它请求隔离，并且 API 暴露的资源可被直接寻址，而无需施加一系列特定请求才能「到达」期望资源。

在具有无状态协议的 API 中，服务器负责持久化数据（这些数据可能在多个客户端之间共享），而客户端对维护应用状态负有唯一责任与权威。

### Cyclic References

资源之间的关系，例如 resource references（[AIP-122]({{< ref "aip-0122" >}})），**must** 能表示为 [有向无环图](https://en.wikipedia.org/wiki/Directed_acyclic_graph)。parent-child 关系也 **must** 无环，并且按 [AIP-124]({{< ref "aip-0124" >}})，给定资源实例将只有一个规范 parent 资源。

资源之间的环会增加管理资源的复杂度。考虑互相引用的资源 A 与 B。创建这些资源的过程是：

1. 创建资源 A，不引用 B。取回资源 A 的 id。
2. 创建资源 B，引用 A。取回资源 B 的 id。
3. 用对 B 的引用更新资源 A。

删除操作也可能更复杂，因为要推理为成功删除必须先解除哪一个引用。

此要求不适用于通过 output only（[AIP-203]({{< ref "aip-0203" >}})）字段表达的关系，因为它们不要求用户指定这些值，因而不会增加资源管理复杂度。
