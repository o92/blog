**英文标题**：Resource names  
**原文**：[AIP-122](https://google.aip.dev/122) · approved · 创建 2019-01-26  
**许可**：原文 © Google，[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)

大多数 API 暴露的主要名词是 resources。用户要创建、读取、操作它们，就得有一个能存下来的唯一标识。这个标识叫 resource name：用户应当把它当作规范名来存。

## 怎么命名

API 定义的所有 resource names 必须在该 API 内唯一。跨 API 引用时用完整资源名称（见下文）。

Resource names 按 [URI path schema](https://datatracker.ietf.org/doc/html/rfc3986#appendix-A) 来写，但没有前导斜杠：

    publishers/123/books/les-miserables
    users/vhugo1802

各段怎么切：

- 各段应当在 collection identifiers（例如 `publishers`、`books`、`users`）与 resource IDs（例如 `123`、`les-miserables`、`vhugo1802`）之间交替。
- 段与段必须用 `/` 分开。
  - 非末段不得含 `/`。
  - 末段不应当含 `/`。
- 字符集应当只用 [RFC-1123](https://tools.ietf.org/html/rfc1123) 给 DNS 名定的那一套。
  - resource IDs 还不应当用大写字母。
  - 若必须多几个字符，不应当用需要 URL-escaping 的字符，也不应当用 ASCII 以外的字符。
  - Unicode 实在躲不开时，必须以 Normalization Form C 存储（见 [AIP-210]({{< ref "aip-0210" >}})）。
- Resources 必须暴露一个 `name` 字段，里面就是 resource name。
  - 可以把 resource ID 再单独给一个字段（例如 `book_id`）。该字段必须标 OUTPUT_ONLY（见 [AIP-203]({{< ref "aip-0203" >}})）。
  - 也可以再给一个系统生成的唯一 ID 字段 uid（见 [AIP-148]({{< ref "aip-0148" >}})）。同样必须标 OUTPUT_ONLY。
  - 不得再用元组、self-links 或别的形式当资源标识。
  - 所有 ID 字段都应当是 strings。

这里说的 resource names 只在单个 API 内唯一（或者从上下文已经能看出是哪家 API）。所以有时叫 *relative resource names*，用来跟下文的 *full resource names* 区分。

### Collection identifier

Resource name 里的 collection identifier 必须是该资源所用名词的复数。例如 `Publisher` 的集合写成 `publishers`。

- 必须是简洁的美式英语。
- 必须是 `camelCase`。
- 必须以小写字母开头，且只含 ASCII 字母与数字（`/[a-z][a-zA-Z0-9]*/`）。
- 必须用复数。
  - 没有复数（"info"）、或单复数相同（"moose"）时，用单数即可。不得靠加 "s" 造词（不要写成 "infos"）。
- 同一条 resource name 里，collection identifiers 必须互不重复。（`people/xyz/people/abc` 无效）

#### 嵌套集合

层级深了，parent collection 的名字常常会当 child 名称的前缀。这时 child collection 可以省略这段前缀。例如 `UserEvent` 通常挂在 `users` 下面：

```
users/vhugo1802/userEvents/birthday-dinner-226
```

应当改成更短的：

```
users/vhugo1802/events/birthday-dinner-226
```

*message* 与 *resource type* 仍叫 `UserEvent`。缩短的只是 pattern 里的 collection 与 resource identifiers。*resource type* 没缩短，所以 `singular` 与 `plural` 同样不缩短。

```
message UserEvent {
  option (google.api.resource) = {
    type: "example.googleapis.com/UserEvent"
    // Only the collection & resource identfiers in the `pattern` are shortened.    
    pattern: "projects/{project}/users/{user}/events/{event}"
    singular: "userEvent"
    plural: "userEvents"
  };

  string name = 1;
}
```

要这么做，就必须在该资源所有 `pattern` 条目、以及 API 里引用它的任何地方都统一用这一套。做不到就完全不要做。

### Resource ID

Resource ID 段在它的 parent collection 里标识这个资源。`publishers/123/books/les-miserables` 里，`123` 是 publisher 的 resource ID，`les-miserables` 是 book 的 resource ID。

- 用户可以指定 resource IDs 时，API 必须写清允许的格式。用户指定的 resource IDs 应当符合 [RFC-1034](https://tools.ietf.org/html/rfc1034)：字母、数字与连字符；首字符是字母；末字符是字母或数字；最长 63 个字符。
  - 字母还应当限制为小写（正则：以小写字母开头，中间最多 61 个 `a-z` / `0-9` / `-`，并以小写字母或数字结尾）。
  - 不应当允许 ASCII 以外的字符。若必须用 Unicode，必须遵循 [AIP-210]({{< ref "aip-0210" >}})。
- 用户设不了 ID 时，API 应当文档化基本格式以及任何上限（例如「最多 63 个字符」）。
- 创建时怎么填 ID，见 [AIP-133]({{< ref "aip-0133" >}})。

### 别名

有些查找特别常见，给个别名更省事。例如资源树顶上是 `users` 的 API，可以用 `users/me` 当「已认证用户」的快捷方式。

API 可以为常见查找提供编程别名。但返回给用户的数据必须仍用规范 resource name。

### 完整资源名称

多数时候，resource names 只在单个 API 内用，或者从字段上下文已经能看出是哪家 API（例如 `string pubsub_topic`）。

有时服务要引用任意 API 里的资源。这时应当用 *full resource name*：无 scheme 的 URI，由拥有方 API 的 service name（见 [AIP-9]({{< ref "aip-0009" >}})）后接相对 resource name 组成：

```
//library.googleapis.com/publishers/123/books/les-miserables
//calendar.googleapis.com/users/vhugo1802
```

拥有方 API 已经清楚时，不应当用 full resource name。只有字段可能指向多个 API、会歧义时才用。

### Resource URIs

Full resource name 是无 scheme 的 URI，跟真正用来访问资源的完整 URI 略有不同。后者带协议（HTTPS）、API 版本，以及具体的 service endpoint（见 [AIP-9]({{< ref "aip-0009" >}})）：

```
https://library.googleapis.com/v1/publishers/123/books/les-miserables
https://calendar.googleapis.com/v3/users/vhugo1802
```

版本不进 full resource name。期望这条名字跨版本还能用：major version 之间表面可能变，同一 API 的多个 major versions 仍应对同一份底层数据。

Full resource name 与服务 endpoint 的对应是约定。一个服务可以有多个 endpoints（区域化、MTLS、私有访问都常见），full resource name 在这些之间不变。

### 表示资源名称的字段

定义资源时，第一个字段应当是 resource name：类型必须是 `string`，名字必须叫 `name`。该 message 应当带声明类型的 `google.api.resource` annotation（见 [AIP-123]({{< ref "aip-0123" >}})）。

```proto
// A representation of a book in the library.
message Book {
  option (google.api.resource) = {
    type: "library.googleapis.com/Book"
    pattern: "publishers/{publisher}/books/{book}"
  };

  // The resource name of the book.
  // Format: publishers/{publisher}/books/{book}
  string name = 1 [(google.api.field_behavior) = IDENTIFIER];

  // Other fields...
}
```

定义检索或作用于已有资源的方法（例如 `GetBook` 或 `ArchiveBook`）时，请求 message 的第一个字段应当是 resource name：类型必须是 `string`，名字必须叫 `name`。该字段还应当用 `google.api.resource_reference` 标出资源类型（见 [AIP-123]({{< ref "aip-0123" >}})）。

```proto
// Request message for ArchiveBook
message ArchiveBookRequest {
  // The book to archive.
  // Format: publishers/{publisher}/books/{book}
  string name = 1 [
    (google.api.field_behavior) = REQUIRED,
    (google.api.resource_reference) = {
      type: "library.googleapis.com/Book"
    }];

  // Other fields...
}
```

字段不得为其它目的叫 `name`。别的用途要么换词，要么加形容词（例如 `display_name`）。

### 表示资源 parent 的字段

定义从集合检索资源、或往集合里加新资源的方法（例如 `ListBooks` 或 `CreateBook`）时，请求 message 的第一个字段应当是 `string`，应当叫 `parent`，表示该集合的 resource name。`parent` 还应当用 `google.api.resource_reference` 标出 parent 的资源类型（见 [AIP-123]({{< ref "aip-0123" >}})）。

```proto
// Request message for ListBooks.
message ListBooksRequest {
  // The publisher to list books from.
  // Format: publishers/{publisher_id}
  string parent = 1 [(google.api.resource_reference) = {
    type: "library.googleapis.com/Publisher"
  }];

  // Other fields (e.g. page_size, page_token, filter, etc.)...
}
```

可能有多于一种 parent 类型时，`parent` 应当改在 `google.api.resource_reference` 上用 `child_type`：

```proto
// Request message for ListBooks.
message ListBooksRequest {
  // The parent to list books from.
  // Format:
  //   - publishers/{publisher_id}
  //   - authors/{author_id}
  string parent = 1 [
    (google.api.field_behavior) = REQUIRED,
    (google.api.resource_reference) = {
      child_type: "library.googleapis.com/Book"
    }];

  // Other fields (e.g. page_size, page_token, filter, etc.)...
}
```

字段不应当为其它目的叫 `parent`。别的用途尽量换同义词。

### 表示另一资源的字段

字段表示另一资源时，类型应当是 `string`，接受对方的 resource name。字段名应当等价于对应 message 名称的 snake case。

- 合适时可以加前导形容词（例如 `string dusty_book`）。
- 不应当加 `_name` 后缀，除非不加会歧义（例如 `crypto_key_name`）。
- 应当提供 `google.api.resource_reference`，写上被引用的资源类型。
- 实在没法用 resource name、只能用 ID 分量时，应当用 `_id` 后缀（例如 `shelf_id`）。

该字段不应当用实现该资源的 `message` 当字段类型，除非满足下列之一：

- API 仅内部使用，生命周期绑得很紧，并且权限模型允许对嵌入资源做继承访问。
- 嵌入资源是 AIP-162 revisions 模式的一部分。

按名称引用的样子：

```proto
// A representation of a book in a library.
message Book {
  option (google.api.resource) = {
    type: "library.googleapis.com/Book"
    pattern: "publishers/{publisher}/books/{book}"
  };

  // Name of the book.
  // Format is `publishers/{publisher}/books/{book}`
  string name = 1 [(google.api.field_behavior) = IDENTIFIER];

  // The shelf where the book currently sits.
  // Format is `shelves/{shelf}`.
  string shelf = 2 [(google.api.resource_reference) = {
    type: "library.googleapis.com/Shelf"
  }];

  // Other fields...
}
```

## 为什么

### 用 names 而不是 IDs

大型系统里资源种类很多。若只用简单的 resource IDs，实际得靠资源特定的元组才能唯一对上，例如 `(bucket, object)` 或 `(user, album, photo)`。麻烦在于：

- 开发者得记住这些匿名元组。
- 传元组通常比传字符串更难。
- 日志、访问控制这类集中式基础设施看不懂专门的元组。
- 专门元组会把 API 设计锁死，可复用的 API interfaces 更难做。Long Running Operations（见 [AIP-151]({{< ref "aip-0151" >}})）能跟很多其它接口协作，就是因为它们用灵活的 resource names。

### 字段名标准化为 `name`

Resource names 并不新。Uniform Resource Names (URN) 早就跟 URI、URL 一起被形式化过。"name" 这个词日常用得太滥，随便当字段名会把开发者绕晕。所以在符合 AIP 的 API 里，字段名 `name` 留给 resource names。别的本想叫 "name" 的字段，必须换更具体的名字。

### 禁止嵌入资源

把资源 message 直接塞进另一资源的某个字段，会把几件事搅在一起：

- 生命周期变复杂：被依赖的资源删了，嵌在别人里面的那份怎么办？数据保留和清理都会变难。
- 绕过权限：每个资源可以有自己的权限。对依赖资源有读权限、对被依赖资源没有的人，会突然看不到完整对象。
- schema、权限、其它要求一改，两边一起抖。滚动发布更难。

按名称引用可以避免数据重复，并迫使拥有方服务通过标准方法参与解析。逻辑关切按资源隔开。

## 沿革

### 曾禁止用户指定 ID 里用 UUID

当时为了让 API 更声明式友好，要求创建时允许用户指定 resource ID，并鼓励另给一个含 UUID 的 `string uid`。后来又劝阻用户指定的 resource ID 成为 UUID，甚至不要看起来像 UUID。

表面上是：`uid` 已经是服务生成的 UUID，用户指定的 ID 就该更「有意义」。后来觉得这条没价值，就去掉了。
