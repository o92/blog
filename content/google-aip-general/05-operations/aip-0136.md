**英文标题**：Custom methods  
**原文**：[AIP-136](https://google.aip.dev/136) · approved · 创建 2019-01-25 · 更新 2023-03-02  
**许可**：原文 © Google，[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)

标准方法盖不住的动作，才轮到 custom methods。面向资源的设计（见 [AIP-121]({{< ref "aip-0121" >}})）用它们表达用户真正想做的事，而不是硬把语义扭进 Get / List / Create / Update / Delete。能用标准方法就用标准方法；把事情扭曲到「勉强能用」并不是好主意。

## 共通约定

custom methods 长相差很多，但不少原则始终适用：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

上面是对特定资源操作的例子。Custom methods 可以挂在 resources、collections 或 services 上。下列要点三种都适用。

- 方法名称应当是动词后跟名词。
  - 名称不得含介词（"for"、"with" 等）。
  - 动词不应当包含任何标准方法动词（Get，见 [AIP-131]({{< ref "aip-0131" >}})；List，见 [AIP-132]({{< ref "aip-0132" >}})；Create，见 [AIP-133]({{< ref "aip-0133" >}})；Update，见 [AIP-134]({{< ref "aip-0134" >}})；Delete，见 [AIP-135]({{< ref "aip-0135" >}})）。
  - 名称不得含 `Async`。若要区分立即 RPC 与长时运行 RPC，可以用后缀 `LongRunning`。例如标准 `CreateBook` 已经定了、当时没考虑长时运行，可以再引入自定义 `CreateBookLongRunning`。
- HTTP 方法必须是 `GET` 或 `POST`：
  - 检索数据或资源状态的方法必须用 `GET`。
  - 若请求 payload 可能超出 URL 大小限制因而需要 `body`，数据检索方法可以用 `POST`。
  - 若方法有副作用或变更资源或数据，必须用 `POST`。
- HTTP URI 必须用 `:` 后接自定义动词（上例中的 `:archive`），并且 URI 里的动词必须与 RPC 名称中的动词匹配。
  - 需要词分隔时必须用 `camelCase`。
- `google.api.http` 里的 `body` 应当是 `"*"`。
  - 更多见 HTTP and gRPC Transcoding（[AIP-127]({{< ref "aip-0127" >}})）。
- Custom methods 应当接受与 RPC 名称匹配并带 `Request` 后缀的请求 message。
- Custom methods 应当返回与 RPC 名称匹配并带 `Response` 后缀的响应 message。
  - 对特定资源操作时，可以返回资源本身。

### 挂在资源上

只要 API 能这样建模，custom methods 必须对资源操作：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

- 资源 name 的参数必须叫 `name`，并且是 URI 路径里唯一的变量。

### 挂在集合上

多数 custom methods 对单个资源操作，有些可以改为对集合操作：

```proto
// Sorts the books from this publisher.
rpc SortBooks(SortBooksRequest) returns (SortBooksResponse) {
  option (google.api.http) = {
    post: "/v1/{parent=publishers/*}/books:sort"
    body: "*"
  };
}
```

- 若集合的资源有 parent，该资源必须叫 `parent`，并且是 URI 路径里唯一的变量。
- Collection key（上例中的 `books`）必须是字面量。

### 无状态方法

有些 custom methods 完全不挂在资源上。这些方法一般是*无状态的*：接受请求、返回响应，对 API 内的数据没有永久影响。

```proto
// Translates the provided text from one language to another.
rpc TranslateText(TranslateTextRequest) returns (TranslateTextResponse) {
  option (google.api.http) = {
    post: "/v1/{project=projects/*}:translateText"
    body: "*"
  };
}
```

- 若该方法在特定 scope 中运行（例如上例中的 project），请求里的字段名应当是该 scope 资源的名称。需要词分隔时必须用 `snake_case`。
- URI 应当把动词和名词都放在 `:` 之后（这时不要造一个「伪 collection key」，因为没有集合）。例如 `:translateText` 优于 `text:translate`。
- 若涉及计费，无状态方法必须用 `POST`。

### 声明式友好资源

声明式友好资源通常不应当采用 custom methods（其它 AIP 里讨论过的特定声明式友好 custom methods 除外）。声明式友好工具没法自动判断怎么处理它们。

例外是很少使用、本质上命令式的操作，例如 `Move` 或 `Rename`。对这类操作不会期望声明式支持。

## 为什么

### HTTP path

跟标准方法一样，对资源或集合操作的 custom method 需要 `name` 或 `parent`，用来指出操作对象。客户端才能把 custom methods 映射到合适的资源。

### HTTP methods

同时允许 `GET` 与 `POST`，才能分清哪些方法不改数据、哪些会改。只读方法在某些客户端里是一等概念（Terraform 中的 DataSources），也向用户表明：调用它没有运行时影响风险。

本来该用 `GET` 的请求改用 `POST`，是一种便利：

- 避免过大的 query strings 撞上 URL 大小限制。
- 让客户端可以用同一种请求数据序列化方式，至少不必为实现 repeated 字段等复杂规则。
- 让本来可能很简单的 RPCs 在复杂情形下仍能带上 query parameters 表达不了的数据。

### 为什么禁止介词

带介词的方法名，往往说明你在发明新方法，而本该给现有方法加字段，或该换一个动词。例如已有 `CreateBook`，又想加 `CreateBookFromDictation`，考虑改成 `TranscribeBook`。想按属性查找时，不要用 `GetBookByAuthor`，考虑带 `author` 字段的 `SearchBooks`。这样能防止超聚焦方法爆炸，把 API 和客户端表面撑大，管理和消费都更难。

### RPC 名称里不要写 async

"async" 在编程语言里常用来表示这次方法调用是同步还是异步，包括发出 RPCs。这跟 RPC 本身是否启动 long-running operation 不在同一层。RPC 名称里写 "async" 会造成混淆，甚至会给某些语言里同时生成同步与异步调用方法的客户端库带来问题。
