**英文标题**：Custom methods  
**原文**：[AIP-136](https://google.aip.dev/136) · approved · 创建 2019-01-25 · 更新 2023-03-02

面向资源的设计（[AIP-121]({{< ref "aip-0121" >}})）使用 custom methods 来表达仅用标准方法难以建模的任意动作。Custom methods 很重要，因为它们让 API 的词汇能够贴合用户意图。

## Guidance

Custom methods **should** 仅用于无法轻易用标准方法表达的功能；若可能，优先使用标准方法，因其语义一致。（当然，这仅适用于所讨论功能确实符合常规语义的情形；把事情扭曲到让标准方法「勉强能用」并*不是*好主意。）

尽管 custom methods 的设计差异很大，许多原则始终适用：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

**Note:** 上述模式展示了对特定资源操作的 custom method。Custom methods 可以关联到 resources、collections 或 services。下列要点在这三种情形下都适用。

- 方法名称 **should** 为动词后跟名词。
  - 名称 **must not** 包含介词（"for"、"with" 等）。
  - 名称中的动词 **should not** 包含任何标准方法动词（Get（[AIP-131]({{< ref "aip-0131" >}})）、List（[AIP-132]({{< ref "aip-0132" >}})）、Create（[AIP-133]({{< ref "aip-0133" >}})）、Update（[AIP-134]({{< ref "aip-0134" >}})）、Delete（[AIP-135]({{< ref "aip-0135" >}})））。
  - 名称 **must not** 包含术语 `Async`。若意图是区分立即 RPC 与长时运行 RPC，**may** 使用后缀 `LongRunning`。例如，要创建长时运行的 book 创建 RPC（若标准 `CreateBook` 方法在考虑长时运行方面之前已设计），可以引入自定义 `CreateBookLongRunning` 方法。
- HTTP 方法 **must** 为 `GET` 或 `POST`：
  - 检索数据或资源状态的方法 **must** 使用 `GET`。
  - 若请求 payload 可能超出 URL 大小限制因而需要 `body`，数据检索方法 **may** 使用 `POST`。
  - 若方法有副作用或变更资源或数据，**must** 使用 `POST`。
- HTTP URI **must** 使用 `:` 字符后跟自定义动词（上例中的 `:archive`），并且 URI 中的动词 **must** 与 RPC 名称中的动词匹配。
  - 若需要词分隔，**must** 使用 `camelCase`。
- `google.api.http` annotation 中的 `body` 子句 **should** 为 `"*"`。
  - 更多信息见 HTTP and gRPC Transcoding（[AIP-127]({{< ref "aip-0127" >}})）。
- Custom methods **should** 接受与 RPC 名称匹配并带 `Request` 后缀的请求 message。
- Custom methods **should** 返回与 RPC 名称匹配并带 `Response` 后缀的响应 message。
  - 对特定资源操作时，custom method **may** 返回资源本身。

### Resource-based custom methods

若 API 可以如此建模，Custom methods **must** 对资源操作：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

- 资源 name 的参数 **must** 称为 `name`，并且是 URI 路径中的唯一变量。

### Collection-based custom methods

尽管大多数 custom methods 对单个资源操作，有些 custom methods **may** 改为对集合操作：

```proto
// Sorts the books from this publisher.
rpc SortBooks(SortBooksRequest) returns (SortBooksResponse) {
  option (google.api.http) = {
    post: "/v1/{parent=publishers/*}/books:sort"
    body: "*"
  };
}
```

- 若集合的资源有 parent，该资源 **must** 称为 `parent`，并且是 URI 路径中的唯一变量。
- Collection key（上例中的 `books`）**must** 为字面量。

### Stateless methods

有些 custom methods 完全不挂在资源上。这些方法一般是*无状态的*：它们接受请求并返回响应，对 API 内的数据没有永久影响。

```proto
// Translates the provided text from one language to another.
rpc TranslateText(TranslateTextRequest) returns (TranslateTextResponse) {
  option (google.api.http) = {
    post: "/v1/{project=projects/*}:translateText"
    body: "*"
  };
}
```

- 若该方法在特定 scope 中运行（例如上例中的 project），请求 message 中的字段名 **should** 为该 scope 资源的名称。若需要词分隔，**must** 使用 `snake_case`。
- URI **should** 把动词和名词都放在 `:` 分隔符之后（此时避免 URI 中的「伪 collection key」，因为没有集合）。例如，`:translateText` 优于 `text:translate`。
- 若涉及计费，Stateless methods **must** 使用 `POST`。

### Declarative-friendly resources

声明式友好资源通常 **should not** 采用 custom methods（其它 AIP 中讨论的特定声明式友好 custom methods 除外），因为声明式友好工具无法自动确定如何处理它们。

例外是很少使用、本质上命令式的操作，例如 `Move` 或 `Rename`，对此不会期望声明式支持。

## Rationale

### HTTP path

与标准方法类似，对资源或集合操作的 custom method 需要 `name` 或 `parent` 参数来指示它所操作的资源。此约定让客户端可以把 custom methods 映射到适当的资源。

### HTTP methods

同时允许 `GET` 与 `POST` HTTP 动词，可以清楚区分哪些方法不变更数据、哪些会变更。仅读取数据的方法在某些客户端中有一等概念（Terraform 中的 DataSources），并向用户清楚表明哪些方法可以调用而没有运行时影响风险。

允许本应用 `GET` 发出的请求改用 `POST` 是一种便利：

- 它避免过大的 query strings 导致请求违反 URL 大小限制。
- 它允许客户端实现单一的请求数据序列化方式，或至少避免为实现 repeated 字段等复杂规则。
- 它允许本来可能很简单的 RPCs 在复杂情形下仍包含数据，而这些数据可能无法用 query parameters 表示。

### Disallowing prepositions

一般而言，带介词的方法名表明正在使用新方法，而本应向现有方法添加字段，或该方法应使用不同的动词。例如，若已有 `CreateBook` message，而你在考虑添加 `CreateBookFromDictation`，考虑改为 `TranscribeBook` 方法。类似地，若希望有按属性查找的方法，不要用 `GetBookByAuthor`，考虑带 `author` 字段作为搜索维度的 `SearchBooks`。这有助于防止超聚焦方法爆炸，膨胀 API 与客户端表面，并增加管理与消费该 API 的复杂度。

### RPC name

术语 "async" 在编程语言中常用来表示特定方法调用是同步还是异步，包括发出 RPCs。该 sync/async 方面与 RPC 本身是否旨在启动 long-running operation 处于不同的抽象层级。在 RPC 名称本身中使用 "async" 会造成混淆，甚至会给某些语言中同时生成同步与异步方法来调用该 RPC 的客户端库带来问题。
