**英文标题**：Batch methods: Create  
**原文**：[AIP-233](https://google.aip.dev/233) · approved · 创建 2019-06-18 · 更新 2022-06-02  
**许可**：原文 © Google，[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)

有时用户要在单个事务里创建多个资源。一条一条 Create 既慢也对不齐。Batch Create 就是为这件事准备的。同步返回时必须整批原子；异步走 Operation 时才可以谈部分成功。

## 怎么写

API 可以用下列两种模式支持 Batch Create。

同步返回响应：

```proto
rpc BatchCreateBooks(BatchCreateBooksRequest) returns (BatchCreateBooksResponse) {
  option (google.api.http) = {
    post: "/v1/{parent=publishers/*}/books:batchCreate"
    body: "*"
  };
}
```

返回异步解析为响应的 Operation：

```proto
rpc BatchCreateBooks(BatchCreateBooksRequest) returns (google.longrunning.Operation) {
  option (google.api.http) = {
    post: "/v1/{parent=publishers/*}/books:batchCreate"
    body: "*"
  };
  option (google.longrunning.operation_info) = {
    response_type: "BatchCreateBooksResponse"
    metadata_type: "BatchCreateBooksOperationMetadata"
  };
}
```

- RPC 名称必须以 `BatchCreate` 开头。其余部分应当是正在创建的资源的复数。
- 请求与响应 messages 必须与 RPC 名称匹配，并带 `Request` 与 `Response` 后缀。
- 若 batch 方法返回 `google.longrunning.Operation`，`response_type` 与 `metadata_type` 都必须指定。
- HTTP 动词必须是 `POST`。
- HTTP URI 必须以 `:batchCreate` 结尾。
- URI 路径应当表示该资源的集合，与简单 CRUD 用的集合一致。操作跨越 parents 时，可以接受短横线（`-`）当通配符。
- `google.api.http` 里的 body 应当是 `"*"`。

### 原子还是部分成功

batch create 可以支持原子（所有资源都创建或都不创建）或部分成功。做选择时看两点：

- **确保原子性的复杂度：** 作为简单透传数据库事务的操作应当用原子；管理复杂资源的操作应当用部分成功。
- **最终用户体验：** 站在 API 消费者这边想。对该用例而言，即使意味着大批次可能因单个或少数条目的问题而失败，原子行为是否仍更可取？

同步 batch create 必须是原子的。

异步 batch create 可以支持原子或部分成功。若支持部分成功，见下文 Operation metadata 的要求。

### 请求 message

应当用下列模式：

```proto
message BatchCreateBooksRequest {
  // The parent resource shared by all books being created.
  // Format: publishers/{publisher}
  // If this is set, the parent field in the CreateBookRequest messages
  // must either be empty or match this field.
  string parent = 1 [
    (google.api.resource_reference) = {
      child_type: "library.googleapis.com/Book"
    }];

  // The request message specifying the resources to create.
  // A maximum of 1000 books can be created in a batch.
  repeated CreateBookRequest requests = 2
    [(google.api.field_behavior) = REQUIRED];
}
```

- 应当包含 `parent`，除非正在创建的资源是顶层资源。调用方设了此字段、且任何 child 请求的 `parent` 对不上时，请求必须失败。本请求的 `parent` 已设时，child 请求的 `parent` 可以省略。
  - 每个请求只允许 1 个 parent 时，该字段应当必填。
  - 该字段应当标明它所引用的 resource type（见 [AIP-122]({{< ref "aip-0122" >}})）。
  - 该字段的注释应当写清资源 pattern。
- 请求必须包含一个 repeated 字段，接受标准 Create 请求 messages（见 [AIP-133]({{< ref "aip-0133" >}})）。该字段应当叫 `requests`。
  - 该字段应当必填。
- 其它字段可以从标准 Create 请求「提升」，意思是该字段可以在 batch 级或 child 请求级设置。跟 `parent` 一样，同一字段在两级都设了时，值必须匹配。
  - 必须唯一的字段不能提升（例如客户提供的 id 字段）。
- 请求不得包含任何其它必填字段，也不应当包含其它可选字段，除非本文或另一篇 AIP 有描述。
- `requests` 上方的注释应当写清允许的最大请求数。

### 响应 message

应当用下列模式：

```proto
message BatchCreateBooksResponse {
  // Books created.
  repeated Book books = 1;
}
```

- 响应必须包含一个对应已创建资源的 repeated 字段。

### Operation metadata message

- `metadata_type` message 必须要么与 RPC 名称匹配并带 `OperationMetadata` 后缀，要么若该类型由多个 Batch methods 共享，则用 `Batch` 前缀与 `OperationMetadata` 后缀命名。
- 若 batch create 支持部分成功，metadata 必须包含 `map<int32, google.rpc.Status> failed_requests`，用来传达部分失败。
  - 键是 batch 请求里 `requests` 字段中该请求的索引。
  - 每个条目的值必须镜像单个标准 Create 通常会返回的错误。
  - 若失败请求可能因服务端重试最终成功，这类瞬时错误不得用 `failed_requests` 传达。
  - 当 batch 中所有请求都失败时，`Operation.error` 必须设为 `code = google.rpc.Code.Aborted` 且 `message = "None of the requests succeeded, refer to the BatchCreateBooksOperationMetadata.failed_requests for individual error details"`
- metadata 可以包含其它字段来传达操作进度。

### 现有 API 怎么改成部分成功

现有 Batch API 要采用部分成功，必须做到：

- 必须保留默认行为，以免不兼容的行为变更。
- 若 API 返回 Operation：
  - 请求必须有 `bool return_partial_success`。
  - Operation `metadata_type` 必须包含 `map<int32, google.rpc.Status> failed_requests`。
  - 请求里 `return_partial_success` 为 true 时，API 应允许部分成功；否则应继续以原子为默认。
- 若 API 同步返回直接响应：
  - 现有客户端会把成功响应当作原子操作，现有版本不得改成部分成功。
  - 必须改为创建新版本，返回 Operation，并遵循本文的部分成功模式。

## 为什么

### 同步 batch 为什么必须原子

本文先前迭代建议 batch methods 必须原子。同步响应的状态码没有清晰方式传达部分失败：OK 意味着全部成功。往响应里加「部分失败」字段会是破坏性变更，因为现有客户端会把 OK 理解成所有资源都已创建。

另一方面，如 [AIP-193]({{< ref "aip-0193" >}}) 所述，Operations 更擅长呈现部分状态。Operation 的响应状态码并不传达底层操作的结果，客户端必须检查响应体才能判断成没成功。

### 部分失败怎么传达

本文用 `map<int32, google.rpc.Status> failed_requests`，键是原始 batch 里失败请求的索引。考虑过、但没用的选项：

- `repeated google.rpc.Status`。看不出哪个条目对应哪个请求。
- `map<string, google.rpc.Status>`，键为失败请求的 request id。被拒绝是因为：
  - 客户端还得自己维护 request_id → request 的 map。
  - 为传达错误而填充 request id 可能与 [AIP-155]({{< ref "aip-0155" >}}) 冲突，若服务无法保证单个请求跨多个 batch 请求的幂等性。
- `repeated FailedRequest`，里面带着单个 create 请求和 `google.rpc.Status`。把请求 payload 回显到响应里不被鼓励，还会碰到用户数据敏感性问题。
