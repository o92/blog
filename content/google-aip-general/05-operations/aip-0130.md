API 由一个或多个 methods 组成，每个 method 表示服务可以代表消费者执行的一项具体操作。

## Guidance

### 选择方法类别

设计方法时，API 作者应按下列顺序从已定义类别中选择：

1. Standard methods（在 collections 与 resources 上）
2. Standard batch 或 aggregate methods
3. Custom methods（在 collections、resources 或无状态上）
4. Streaming methods

## Rationale

首先推荐面向资源的标准方法与自定义方法，因为它们能在最广的一类客户端中表达（Declarative clients、CLIs、UIs 等），并提供最统一的体验，让用户可以把对一个 API 的知识应用到另一个。

若标准方法不合适，则（挂在 resource 或 collection 上的）custom methods 提供较低但仍有价值的一致性，帮助用户推理该动作的范围，以及读取其配置来告知该动作的对象。尽管变更性 custom methods 不够统一，无法与仅面向资源的客户端（例如 [Declarative Clients]({{< ref "aip-0009" >}})）做自动化集成，它们仍是 CLIs、UIs 与 SDKs 容易识别的模式。

若完全无法以面向资源的方式表达其 APIs，则该操作落入一类缺乏统一性、除 SDKs 外任何客户端都难以建模的类别。此类排在最后，因为用户无法依赖其对相似 APIs 的知识，并且与许多客户端的集成很可能必须手写。
