API 由一个或多个 methods 组成。每个 method 是服务能替消费者做的一项具体操作。方法种类很多，自动化程度差很远：标准方法几乎处处能接；流式方法多数只能手写。设计时按类别选，别一上来就发明新动词。

## 方法有哪些类

方法常常挂在它所操作的对象上（collection 或 resource）。类别如下。

|--|--|--|--|--|
| *Standard Methods* | | | | |

| **Standard resource methods**：获取或变更单个资源（Get、Update、Delete）。 | [AIP-121]({{< ref "aip-0121" >}})、[AIP-131]({{< ref "aip-0131" >}})、[AIP-134]({{< ref "aip-0134" >}})、[AIP-135]({{< ref "aip-0135" >}}) | 可自动化 | 可自动化 | 可自动化 |

## 按这个顺序选

设计方法时，按下列顺序从已定义类别里挑：

1. Standard methods（在 collections 与 resources 上）
2. Standard batch 或 aggregate methods
3. Custom methods（在 collections、resources 或无状态上）
4. Streaming methods

## 为什么

先推荐面向资源的标准方法和自定义方法，因为它们能在最广的一类客户端里表达（Declarative clients、CLIs、UIs 等），体验也最统一：学会一个 API，就能把知识搬到另一个。

标准方法不合适时，挂在 resource 或 collection 上的 custom methods 仍能给一点一致性：用户能看出动作的范围，也能读配置来判断对象。变更性 custom methods 不够统一，没法跟仅面向资源的客户端（例如 Declarative Clients，见 [AIP-9]({{< ref "aip-0009" >}})）做自动化集成。但对 CLIs、UIs 与 SDKs 来说，这仍是容易认出的模式。

完全无法以面向资源的方式表达时，操作就落到一类缺乏统一性的方法上。除 SDKs 外，任何客户端都难建模。这类排在最后：用户没法复用对其它 API 的知识，跟许多客户端的集成很可能必须手写。
