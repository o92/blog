**英文标题**：Long-running operations  
**原文**：[AIP-151](https://google.aip.dev/151) · approved · 创建 2019-07-25  
**许可**：原文 © Google，[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)

有的方法要跑很久。一直阻塞到做完，用户体验通常很差。更好的做法是先给用户一个承诺，让他稍后回来查。long-running operations 大致像 [Python Future](https://docs.python.org/3/library/concurrent.futures.html#concurrent.futures.Future) 或 [Node.js Promise](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Using_promises)：用户拿到一个 token，用来跟踪进度、取回结果。

「显著时间」随工作内容而变。经验法则是 10 秒。

## 怎么写

可能需要显著时间才能完成的个别 API methods 应当返回 [`google.longrunning.Operation`](https://github.com/googleapis/googleapis/blob/master/google/longrunning/operations.proto)，而不是最终的响应 message。

```proto
// Create a book.
rpc CreateBook(CreateBookRequest) returns (google.longrunning.Operation) {
  option (google.api.http) = {
    post: "/v1/{parent=publishers/*}/books"
    body: "book"
  };
  option (google.longrunning.operation_info) = {
    response_type: "Book"
    metadata_type: "OperationMetadata"
  };
}
```

- 响应类型必须是 `google.longrunning.Operation`。`Operation` proto 定义不得复制进个别 APIs。
  - 响应不得是 streaming response。
- 该方法必须包含 `google.longrunning.operation_info` annotation，并且必须定义 response 与 metadata 类型。
  - response 与 metadata 类型必须定义在 RPC 所在文件，或该文件导入的文件中。
  - 若定义在另一个 package 中，必须用完全限定的 message 名称。
  - 响应类型不应当是 `google.protobuf.Empty`（Delete 方法除外，见 [AIP-135]({{< ref "aip-0135" >}})），除非确定*永远*不需要响应数据。将来可能要加响应数据时，为该 RPC 定义一个空 message 再用它。
  - metadata 类型用来在每次 `GetOperation` 上提供进度、部分失败及类似信息。不应当是 `google.protobuf.Empty`，除非确定*永远*不需要 metadata。将来可能要加时，同样先定义一个空 message。
- 有返回 `Operation` 的 messages 的 APIs 必须实现 [`Operations`](https://github.com/googleapis/googleapis/blob/master/google/longrunning/operations.proto) 服务。个别 APIs 不得自己定义一套 long-running operations 接口，以免不统一。
- 若 RPC 支持 validate-only 模式（见 [AIP-163]({{< ref "aip-0163" >}})），对验证请求的响应必须是下列之一：
  - 成功响应，带一个已经完成的 `Operation`：`done` 为 `true`，`response` 里有有效（但可能为空）的响应 message，包在 `google.protobuf.Any` 中。`name` 可以为空，以免服务为成功验证维护状态。
  - 立即错误响应（通常是 "bad request"）
  - `done` 为 `false` 的 `Operation`，表示长时运行的验证。此时 `name` 必须设置，好让客户端轮询到完成。成功验证最终必须表示为 `done=true` 且 `response` 里有有效（但可能为空）的包装响应。失败验证最终必须表示为 `done=true` 且在 `error` 里提供错误详情。

### 标准方法

合适时，Create（见 [AIP-133]({{< ref "aip-0133" >}})）、Update（见 [AIP-134]({{< ref "aip-0134" >}})）或 Delete（见 [AIP-135]({{< ref "aip-0135" >}})）可以返回 `Operation`。此时 `operation_info` 里的响应类型必须是该标准方法本来期望的响应类型。

用 long-running operation 创建或删除资源时，该资源应当出现在 List（见 [AIP-132]({{< ref "aip-0132" >}})）与 Get（见 [AIP-131]({{< ref "aip-0131" >}})）里；但应当表明它尚不可用，一般用 state enum（见 [AIP-216]({{< ref "aip-0216" >}})）。

### 并行 operations

资源可以接受多个将并行在其上工作的 operations，但没有义务这样做：

- 接受多个并行 operations 的资源可以把它们放入队列，而不是同时处理。
- 不允许并行多个 operations 的资源（进行中的那个完成之前拒绝任何新 operation）若用户试图并行操作，必须返回 `ABORTED`，并带解释该情形的错误消息。
- 带声明式友好 APIs（见 [AIP-128]({{< ref "aip-0128" >}})）的资源可以允许后续 updates 抢占现有 operations。此时最新的 update 开始处理，先前的 operations 标为 `ABORTED`，并带解释该情形的错误消息。

### 过期

APIs 可以允许 operation resources 在操作完成后经过足够时间后过期。

经验法则是 30 天。

### 错误

阻止 long-running operation *启动* 的错误必须返回错误响应（见 [AIP-193]({{< ref "aip-0193" >}})），跟其它方法一样。

在执行阶段失败的 operations 必须把错误响应放在 `Operation.error` 的 [google.rpc.Status](https://github.com/googleapis/googleapis/blob/master/google/rpc/status.proto) 字段中。

操作过程中发生的非终止错误可以放在 metadata message 里，并且该字段必须是符合 [AIP-193]({{< ref "aip-0193" >}}) 的 [google.rpc.Status](https://github.com/googleapis/googleapis/blob/master/google/rpc/status.proto)。

### 向后兼容

更改 long-running operation 的 `response_type` 或 `metadata_type` 都是破坏性变更。

## 为什么 validate-only 要这样还

validate-only 的指导来自客户端与服务器之间的张力：客户端希望拿到「完全成形」的 operations，好用同一套逻辑处理；服务器又不想为琐碎操作维护额外状态。仅仅验证请求就生成更多状态，听起来别扭。但以后还能再取的完整 operation，要么需要那份状态，要么需要「特殊」的 singleton operation IDs。折中是：返回「已完成」的 operation。客户端用现有逻辑就能看出已经成功（因此不必再拉更新），服务器也不必维护额外状态。
