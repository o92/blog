**英文标题**：Long-running operations  
**原文**：[AIP-151](https://google.aip.dev/151) · approved · 创建 2019-07-25  
**许可**：原文 © Google，[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)

偶尔，API 可能需要暴露一个需要显著时间才能完成的方法。此时，简单地阻塞直到任务跑完往往是糟糕的用户体验；更好的做法是向用户返回某种承诺，并允许用户稍后回来检查。

long-running operations 模式大致类似于 [Python Future](https://docs.python.org/3/library/concurrent.futures.html#concurrent.futures.Future) 或 [Node.js Promise](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Using_promises)。本质上，用户得到一个可用于跟踪进度并检索结果的 token。

## Guidance

可能需要显著时间才能完成的个别 API methods **should** 返回 [`google.longrunning.Operation`](https://github.com/googleapis/googleapis/blob/master/google/longrunning/operations.proto) 对象，而不是最终的响应 message。

```proto
// Create a book.
rpc CreateBook(CreateBookRequest) returns (google.longrunning.Operation) {
  option (google.api.http) = {
    post: "/v1/{parent=publishers/*}/books"
    body: "book"
  };
  option (google.longrunning.operation_info) = {
    response_type: "Book"
    metadata_type: "OperationMetadata"
  };
}
```

- 响应类型 **must** 为 `google.longrunning.Operation`。`Operation` proto 定义 **must not** 被复制进个别 APIs。
  - 响应 **must not** 为 streaming response。
- 该方法 **must** 包含 `google.longrunning.operation_info` annotation，它 **must** 定义 response 与 metadata 类型。
  - response 与 metadata 类型 **must** 定义在 RPC 所在文件，或该文件导入的文件中。
  - 若 response 与 metadata 类型定义在另一个 package 中，**must** 使用完全限定的 message 名称。
  - 响应类型 **should not** 为 `google.protobuf.Empty`（Delete（[AIP-135]({{< ref "aip-0135" >}})） methods 除外），除非确定*永远*不需要响应数据。若将来可能添加响应数据，为该 RPC 响应定义空 message 并使用它。
  - metadata 类型用于在每次 `GetOperation` 调用上提供进度、部分失败及类似信息。metadata 类型 **should not** 为 `google.protobuf.Empty`，除非确定*永远*不需要 metadata。若将来可能添加 metadata，为该 RPC metadata 定义空 message 并使用它。
- 有返回 `Operation` 的 messages 的 APIs **must** 实现 [`Operations`](https://github.com/googleapis/googleapis/blob/master/google/longrunning/operations.proto) 服务。个别 APIs **must not** 定义自己的 long-running operations 接口，以避免不统一。
- 若 RPC 支持 validate-only 模式（[AIP-163]({{< ref "aip-0163" >}})），对验证请求的响应 **must** 为下列之一：
  - 成功响应，带一个已经完成的 `Operation`：`done` 字段设为 `true`，`response` 字段中有有效（但可能为空）的响应 message，包在 `google.protobuf.Any` message 中。`name` 字段 **may** 为空，以避免服务为成功验证维护状态。
  - 立即错误响应（通常是 "bad request"）
  - `done` 字段设为 `false` 的 `Operation`，表示长时运行的验证。此时 `name` 字段 **must** 设置，以允许客户端轮询该长时运行验证操作直到完成。成功验证 **must** 最终表示为 `done=true` 且 `response` 字段中有有效（但可能为空）的包装响应 message 的操作。失败验证 **must** 最终表示为 `done=true` 且在 `error` 字段中提供错误详情的操作。

**Note:** 用户对「显著时间」的期望可能因所做工作而异。经验法则是 10 秒。

### Standard methods

若适当，APIs **may** 从 Create（[AIP-133]({{< ref "aip-0133" >}})）、Update（[AIP-134]({{< ref "aip-0134" >}})）或 Delete（[AIP-135]({{< ref "aip-0135" >}})）标准方法返回 `Operation`。此时，`operation_info` annotation 中的响应类型 **must** 为该标准方法的标准且期望的响应类型。

用 long-running operation 创建或删除资源时，该资源 **should** 包含在 List（[AIP-132]({{< ref "aip-0132" >}})）与 Get（[AIP-131]({{< ref "aip-0131" >}})）调用中；然而，该资源 **should** 表明它尚不可用，一般用 state enum（[AIP-216]({{< ref "aip-0216" >}})）。

### Parallel operations

资源 **may** 接受多个将并行在其上工作的 operations，但没有义务这样做：

- 接受多个并行 operations 的资源 **may** 把它们放入队列，而不是同时处理这些 operations。
- 不允许并行多个 operations 的资源（在进行中的那个完成之前拒绝任何新 operation）若用户试图并行操作，**must** 返回 `ABORTED`，并包含解释该情形的错误消息。
- 带声明式友好 APIs（[AIP-128]({{< ref "aip-0128" >}})）的资源 **may** 允许后续 updates 抢占现有 operations。此时，最新的 update 开始处理，先前的 operations 标为 `ABORTED`，并带解释该情形的错误消息。

### Expiration

APIs **may** 允许其 operation resources 在操作完成后经过足够时间后过期。

**Note:** operation 过期的经验法则是 30 天。

### Errors

阻止 long-running operation *启动* 的错误 **must** 返回错误响应（[AIP-193]({{< ref "aip-0193" >}})），与任何其它方法类似。

在执行阶段失败的 operations **must** 返回错误响应（[AIP-193]({{< ref "aip-0193" >}})），放在 `Operation.error` 的 [google.rpc.Status](https://github.com/googleapis/googleapis/blob/master/google/rpc/status.proto) 字段中。

在操作过程中发生的非终止错误 **may** 放在 metadata message 中，并且该字段 **must** 为符合 [AIP-193]({{< ref "aip-0193" >}}) 的 [google.rpc.Status](https://github.com/googleapis/googleapis/blob/master/google/rpc/status.proto)。

### Backwards compatibility

更改 long-running operation 的 `response_type` 或 `metadata_type` 都是破坏性变更。

## Rationale

### Validate-only behavior

validate-only 响应的指导来自客户端与服务器之间的张力：客户端受益于可统一处理的「完全成形」operations，而服务器不希望为琐碎操作维护额外状态。仅仅验证请求就应生成更多状态似乎有违直觉，但以后可以获取的完整 operation 响应要么需要那样做，要么需要「特殊」的 singleton operation IDs。所提供的指导是一种折中：通过返回「已完成」的 operation，客户端可以使用现有逻辑检查该 operation 已成功完成（因此不需要再获取更新状态），而服务器不需要维护任何额外状态。
