用户要在 URI 和 protobuf package 里看出这是哪一版、稳不稳定。这篇讲 Google APIs 的版本控制策略。一般而言，这些策略适用于所有 Google 管理的服务。

## 主版本

所有 Google API interfaces 必须提供 major version number：编在 protobuf package 末尾，并作为 REST APIs URI 路径的第一部分。若 API 需要做不兼容变更，按所讨论表面的稳定性级别查阅 [AIP-180]({{< ref "aip-0180" >}}) 与 [AIP-181]({{< ref "aip-0181" >}}) 了解必要步骤。

这里的 "major version number" 取自 [semantic versioning](https://semver.org/)。但与传统 semantic versioning 不同，Google APIs 不得暴露次版本或补丁版本号。例如用 `v1`，不用 `v1.0`、`v1.1` 或 `v1.4.2`。从用户视角看，主版本就地用次/补丁等价变更更新，用户无需迁移即可收到新功能。

API 的新主版本不得依赖同一 API 的先前主版本。API 表面不得依赖其它 APIs，除 [AIP-213]({{< ref "aip-0213" >}}) 与 [AIP-215]({{< ref "aip-0215" >}}) 中概述的情形外。

同一 API 的不同版本必须能够在单个客户端应用内同时工作一段合理过渡期。这段时间让客户端平滑迁到更新版本。较旧版本必须在关闭前经过合理、充分沟通的弃用期。

对具有 alpha 或 beta 稳定性（见 [AIP-181]({{< ref "aip-0181" >}})）的发布，APIs 必须使用下列策略之一，在 protobuf package 与 URI 路径中把稳定性级别附在主版本号之后：

- Channel-based versioning（推荐）
- Release-based versioning
- Visibility-based versioning

### Channel-based versioning

stability channel 是给定稳定性级别上、接收就地更新的长寿命发布。每个主版本的每个稳定性级别不超过一个 channel。在此策略下，最多三个可用 channels：alpha、beta 与 stable。

alpha 与 beta channel 必须把稳定性级别附到版本上；stable channel 不得附稳定性级别。例如，`v1` 是 stable channel 可接受的版本，`v1beta` 或 `v1alpha` 不是。类似地，`v1beta` 或 `v1alpha` 分别是 beta 与 alpha channel 可接受的版本，`v1` 对二者都不可接受。这些 channels 各自「就地」接收新功能与更新。

beta channel 的功能必须是 stable channel 功能的超集；alpha channel 的功能必须是 beta channel 功能的超集。

#### 弃用 API 功能

API 元素（fields、messages、RPCs）可以在任何 channel 中标为 deprecated，表明它们不应再被使用：

```proto
// Represents a scroll. Books are preferred over scrolls.
message Scroll {
  option deprecated = true;

  // ...
}
```

已弃用的 API 功能不得从 alpha 毕业到 beta，也不得从 beta 毕业到 stable。换句话说，功能不得以「预先弃用」的方式到达任何 channel。

beta channel 的功能在被弃用足够长时间后可以移除；我们建议 180 天。对仅存在于 alpha channel 的功能，弃用是可选的，并且功能可以在无通知的情况下被移除。若功能在 API 的 alpha channel 中于移除前被弃用，API 应当应用相同 annotation，并且可以使用任何它希望的时间范围。

### Release-based versioning

此模式对新服务不常用。有现有服务在用，但 Channel-based versioning 是首选。

individual release 是预期在其功能被纳入 stable channel 之前、只可用有限时间段的 alpha 或 beta 发布，之后该个别发布将被关闭。使用基于发布的版本控制策略时，API 可以在每个稳定性级别有任意数量的个别发布。

channel-based 与 release-based 策略都就地更新 stable 版本。即使使用 release-based 策略，也只有单个 stable channel，而不是个别 stable 发布。

Alpha 与 beta 发布必须把稳定性级别附到版本上，后跟递增的发布号。例如 `v1beta1` 或 `v1alpha5`。APIs 应当在文档（例如注释）里写清这些版本的时间顺序。

每个 alpha 或 beta 发布可以用向后兼容变更就地更新。对 beta 发布，向后不兼容更新应当通过递增发布号、发布带该变更的新发布来做。例如当前是 `v1beta1`，接下来发 `v1beta2`。

Alpha 与 beta 发布在其功能到达 stable channel 后应当被关闭。alpha 发布可以在任何时间关闭；beta 发布应当给用户合理过渡期，我们建议 180 天。

### Visibility-based versioning

[API visibility](https://github.com/googleapis/googleapis/blob/master/google/api/visibility.proto) 是 Google API 基础设施提供的高级功能。它允许 API producers 从一个内部 API 表面露出多个外部 API 视图，每个视图关联一个 API visibility label，例如：

```proto
import "google/api/visibility.proto";

message Resource {
  string name = 1;

  // Preview. Do not use this feature for production.
  string display_name = 2
    [(google.api.field_visibility).restriction = "PREVIEW"];
}
```

visibility label 是可用于标记任何 API 元素的大小写敏感字符串。按约定，visibility labels 应始终使用 UPPER case。除非像上例那样应用显式 visibility label，隐式 `PUBLIC` label 应用于所有 API 元素。

每个 visibility label 是 allow-list。API producers 需要把 visibility labels 授予 API consumers，他们才能使用与这些 labels 关联的 API 功能。换句话说，API visibility label 像带 ACL 的 API 版本。

多个 visibility labels 可以通过逗号分隔字符串（例如 `"PREVIEW,TRUSTED_TESTER"`）用在一个元素上。使用多个 visibility labels 时，客户端只需一个 visibility label（逻辑 `OR`）。

默认情况下，授予 API consumer 的 visibility labels 用于验证传入请求。然而，客户端可以如下发送带显式 visibility label 的请求：

```
GET /v1/projects/my-project/topics HTTP/1.1
Host: pubsub.googleapis.com
Authorization: Bearer y29....
X-Goog-Visibilities: PREVIEW
```

单个 API 请求最多可以指定一个 visibility label。

API producers 可以使用 API visibility 做 API 版本控制，例如 `INTERNAL` 与 `PREVIEW`。新 API 功能从 `INTERNAL` label 开始，然后移到 `PREVIEW` label。当功能稳定并普遍可用时，从 API 定义中移除所有 API visibility labels。

一般而言，对增量变更，API visibility 比 API 版本控制更容易实现，但它依赖复杂的 API 基础设施支持。Google Cloud APIs 常常对 Preview 功能使用 API visibility。
