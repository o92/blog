**英文标题**：Stability levels

不同组织（Google 内外）产品生命周期不一样。AIP 用下面几个词来指 API 组件的 stability，好让「能不能破坏性变更、要不要弃用期」有同一套说法。

这些稳定性级别大致对应 Google Cloud 里的产品发布阶段（alpha、beta、GA），但并不相同。GCP 在这套之上还加了自己的额外期望与承诺。

## Alpha

alpha 组件与一组已知用户做快速迭代。这些用户必须能容忍变更。用户数量应当是经过挑选、可管理的集合，以便跟他们所有人个别沟通是可行的。

破坏性变更在 alpha 组件中必须既被允许也被期望。用户必须对稳定性没有期望。

## Beta

beta 组件必须被视为完整，并准备好被宣布为 stable，受公开测试约束。Beta 组件应当暴露给未知、且潜在大量的用户。换句话说，beta 组件不应当躲在 allowlist 后面；相反，应当对公众可用。

beta 组件的用户往往对变更容忍度较低，因此 beta 应当尽可能稳定。然而，beta 组件必须被允许随时间变更。这些变更应当尽量小，但可以包含对 beta 组件的向后不兼容变更。向后不兼容变更必须仅在合理的弃用期之后做出，好让用户有机会迁代码。此弃用期必须在标为 beta 时定义。

Beta 组件应当有时间盒：若在指定时间范围内未发现问题则提升为 stable。该时间范围应当在标为 beta 时指定。合理时间段可以有所不同，经验法则是 90 天。

## Stable

stable 组件必须在主 API 版本的生命周期内得到完全支持。用户对标为 stable 的组件期望这类稳定性，因此对这些组件不得有破坏性变更，受下列注意事项约束。

### 主版本

当破坏性变更变得必要时，API producer 应当创建 API 的下一个主版本，并对现有版本启动弃用时钟。

含 stable 组件的任何版本的下线，必须在标为 stable 时定义正式过程。此过程必须为用户指定弃用期，给出合理的提前警告。

### 隔离的小改

极少数场合，做小的、隔离的破坏性变更可能更可取——若这只会给一小部分用户造成不便。创建新主版本对所有用户都是不便。此时，API producer 可以弃用该组件，但必须在 stable 组件的正常下线期内继续支持该组件。

在 stable API 中做就地破坏性变更被视为极端行动，应当以等于或大于创建新主版本的严肃性对待。例如在 Google，这需要 API Governance 团队批准。

### 紧急变更

在某些例外情形下，例如安全顾虑或监管要求，任何 API 组件都可以以破坏性方式变更，不论其稳定性级别。这些情形下不承诺弃用。
