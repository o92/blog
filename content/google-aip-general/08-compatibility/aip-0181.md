尽管不同组织（Google 内外）有不同的产品生命周期，AIPs 使用下列术语来指 API 组件的 *stability*。

**Note:** 这些稳定性级别大致对应 Google Cloud 中的产品发布阶段（alpha、beta、GA），但并不相同。GCP 在此处概述之上施加自己的额外期望与承诺。

## Alpha

*alpha* 组件与一组已知用户进行快速迭代，这些用户 **must** 能容忍变更。用户数量 **should** 是经过挑选、可管理的集合，以便与他们所有人个别沟通是可行的。

破坏性变更在 alpha 组件中 **must** 既被允许也被期望，并且用户 **must** 对稳定性没有期望。

## Beta

*beta* 组件 **must** 被视为完整并准备好被宣布为 stable，受公开测试约束。Beta 组件 **should** 暴露给未知且潜在大量的用户。换句话说，beta 组件 **should not** 在 allowlist 之后；相反，它们 **should** 对公众可用。

因为 beta 组件的用户往往对变更容忍度较低，beta 组件 **should** 尽可能稳定；然而，beta 组件 **must** 被允许随时间变更。这些变更 **should** 最小，但 **may** 包括对 beta 组件的向后不兼容变更。向后不兼容变更 **must** 仅在合理的弃用期之后做出，以为用户提供迁移代码的机会。此弃用期 **must** 在标为 beta 时定义。

Beta 组件 **should** 有时间盒，若在指定时间范围内未发现问题则提升为 stable，该时间范围 **should** 在标为 beta 时指定。合理时间段 **may** 有所不同，但经验法则是 90 天。

## Stable

*stable* 组件 **must** 在主 API 版本的生命周期内得到完全支持。因为用户对标为 stable 的组件期望此类稳定性，对这些组件 **must** 没有破坏性变更，受下列注意事项约束。

### Major versions

当破坏性变更变得必要时，API producer **should** 创建 API 的下一个主版本，并对现有版本启动弃用时钟。

含 stable 组件的任何版本的下线 **must** 在标为 stable 时定义正式过程。此过程 **must** 为用户指定弃用期，为他们提供合理的提前警告。

### Isolated changes

在极少数场合，做小的、隔离的破坏性变更可能更可取，若这只会给一小部分用户造成不便。（创建新主版本对所有用户都是不便。）此时，API producer **may** 弃用该组件，但 **must** 在 stable 组件的正常下线期内继续支持该组件。

**Important:** 在 stable API 中做就地破坏性变更被视为极端行动，应被以等于或大于创建新主版本的严肃性对待。例如，在 Google，这需要 API Governance 团队的批准。

### Emergency changes

在某些例外情形下，例如安全顾虑或监管要求，任何 API 组件 **may** 以破坏性方式变更，无论其稳定性级别如何，并且这些情形下不承诺弃用。
