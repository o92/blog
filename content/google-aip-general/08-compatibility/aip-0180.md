**英文标题**：Backwards compatibility  
**原文**：[AIP-180](https://google.aip.dev/180) · approved · 创建 2019-07-23

APIs 从根本上是与用户的契约，用户常常针对 APIs 编写代码，然后把它启动进生产服务，并期望它继续工作（除非 API 有表明否则的稳定性级别（[AIP-181]({{< ref "aip-0181" >}})））。因此，理解什么构成向后兼容变更、什么构成向后不兼容变更很重要。

## Guidance

服务更新到新的次版本或补丁版本时，现有客户端代码 **must not** 被破坏。旧客户端 **must** 能够对更新的服务器工作（带相同的主版本号）。

**Important:** 变更是否兼容并不总是清楚。此处指导 **should** 视为指示性的，而不是每个可能变更的穷尽列表。

要考虑三种不同的兼容性：

1. Source compatibility：针对先前版本编写的代码 **must** 能对更新版本编译，并成功与更新版本的客户端库运行。
2. Wire compatibility：针对先前版本编写的代码 **must** 能够与更新的服务器正确通信。换句话说，不仅输入与输出兼容，序列化与反序列化期望也继续匹配。
3. Semantic compatibility：针对先前版本编写的代码 **must** 继续收到大多数合理开发者会期望的东西。（实践中这可能棘手，有时确定用户会期望什么可能涉及判断。）

**Note:** 一般而言，此处具体指导假定使用 protocol buffers 与 JSON 作为传输格式。其它传输格式可能有略微不同的规则。

**Note:** 此指导假定 APIs 意在被一系列消费者调用，用多种语言编写，且无法控制消费者如何以及何时更新。任何范围更有限的 API（例如，仅由与 API producer 同一团队编写的客户端代码调用，或以可强制更新的方式部署的 API）应仔细考虑自己的兼容性要求。

### Adding components

一般而言，新组件（interfaces、methods、messages、fields、enums 或 enum values）**may** 在同一主版本内添加到现有 APIs。

然而，这样做时记住下列指导：

- 针对先前表面编写（因此不知道新组件）的代码 **must** 继续被与以前相同的方式对待。
  - 新的 required 字段 **must not** 添加到现有请求 messages 或资源。
  - 任何由客户端填充的字段 **must** 有匹配该字段引入之前行为的默认行为。
    - 这在某些情形下可能棘手。例如，在先前返回所有条目之后再添加分页（即 `page_size` 无限，这不被建议）。若新 `page_size` 字段的默认值*少于*先前返回的数量，较旧客户端会错误地假定所有结果都已返回。
  - 任何先前由服务器填充的字段 **must** 继续被填充，即使它引入冗余。
- 对 enum values 特别地，要意识到用户代码可能无法优雅地处理新值。
  - Enum values **may** 自由添加到仅用于请求 messages 的 enums。
  - 用于响应 messages 或资源、且预期会收到新值的 enums **should** 文档化这一点。此时仍 **may** 添加 enum values；然而，**should** 使用适当谨慎。

**Note:** 添加与现有组件密切相关的组件时（例如当 `string foo` 已存在时添加 `string foo_value`），可能进入生成代码会冲突的情形。服务所有者 **should** 意识到他们或其用户很可能使用的工具中的细微之处（工具作者 **should** 尽可能努力避免此类细微之处）。

### Removing or renaming components

现有组件（interfaces、methods、messages、fields、enums 或 enum values）**must not** 从同一主版本的现有 APIs 中移除。移除组件是向后不兼容变更。

**Important:** 重命名组件在语义上等价于「移除并添加」。在此类变更可取的情形下，服务 **may** 添加新组件，但 **must not** 移除现有组件。在这可能允许用户为同一语义想法指定冲突值的情形下，行为 **must** 被清楚指定。

### Moving components between files

现有组件 **must not** 在文件之间移动。

把组件从同一 package 内的一个 proto 文件移到另一个是线上兼容的，然而，对 C++ 或 Python 等语言生成的代码会导致破坏性变更，因为 `import` 与 `#include` 将不再指向正确的代码位置。

### Moving into oneofs

现有字段 **must not** 移入或移出 oneof。这是 Go protobuf stubs 中的向后不兼容变更。

### Changing the type of fields

现有字段与 messages **must not** 更改其类型，即使新类型是线上兼容的，因为类型变更以破坏性方式改变生成代码。

### Changing string length

APIs **should** 避免增加 `string` 字段大小或限制（若作为输入接受）的上界。APIs **should** 把期望的大小上界增加视为不兼容变更（作为示例见 [Changing resource names](#changing-resource-names)）。APIs **may** 在有必要保留一致大小时用填充字符把值填满，但若这样做 **must** 被文档化。

### Changing resource names

资源 **must not** 更改其 name（[AIP-122]({{< ref "aip-0122" >}})）。

与大多数破坏性变更不同，这也影响主版本：为了让客户端期望用 v2.0 访问在 v1.0 中创建的资源或反之，两个版本中 **must** 使用相同的 resource name。

更微妙的是，有效 resource names 的集合也 **should not** 改变，原因如下：

- 若 resource name 格式变得更受限，先前会成功的请求现在会失败。
- 若 resource name 格式变得比先前文档化的更宽松，则基于先前文档做假设的代码可能破坏。用户很可能把 resource names 存储在别处，其方式可能对允许的字符集与名称长度敏感。或者，用户可能执行自己的 resource name 校验以遵循文档。
  - 例如，Amazon 开始允许更长的 EC2 resource IDs 时给了客户 [大量警告](https://aws.amazon.com/blogs/aws/theyre-here-longer-ec2-resource-ids-now-available/) 并有迁移期。

### Semantic changes

代码常常依赖 API 行为与语义，*即使此类行为未被显式支持或文档化*。因此，APIs **must not** 以很可能破坏合理用户代码的方式更改可见行为或语义，因为此类变更会被那些用户视为破坏性。

**Note:** 这确实涉及一定程度的判断；提议的变更是否可能破坏用户并不总是清楚，对此指导的扩张性解读表面上可能阻止*任何*变更（这不是意图）。

#### Changing value format or construction

APIs **must not** 在 API 版本内更改用于构造现有字段值的期望格式或算法——即使该字段是 `OUTPUT_ONLY` 且由 API 服务填充。这样做需要新的 API 版本。

例如，把符合 IPv4 格式的字段 `ip_address` 改为包含 IPv6 值是破坏性变更。

#### Default values must not change

默认值是客户端未指定时服务器为资源设置的值。本节仅适用于资源字段上的静态默认值，不适用于动态默认值，例如资源的默认 IP 地址。

更改默认值视为破坏性，并且 **must not** 被做。资源的默认行为由其默认值确定，并且这 **must not** 跨次版本改变。

例如：

```proto
message Book {
    // google.api.resource and other annotations and fields

    // The genre of the book
    // If this is not set when the book is created, the field will be given a value of FICTION.
    enum Genre {
      UNSPECIFIED = 0;
      FICTION = 1;
      NONFICTION = 2;
    }
}
```

改为：

```proto
message Book {
    // google.api.resource and other annotations and fields

    // The genre of the book
    // If this is not set when the book is created, the field will be given a value of NONFICTION.
    enum Genre {
      UNSPECIFIED = 0;
      FICTION = 1;
      NONFICTION = 2;
    }
}
```

会构成破坏性变更。

#### Serializing defaults

APIs **must not** 更改带默认值的字段的序列化方式。例如若值等于默认值时字段不出现在响应中，序列化 **must not** 改为包含带默认值的字段。客户端可能依赖资源中字段的存在或不存在作为语义上有意义的，因此对缺席值的序列化方式 **must not** 在次版本中发生变更。

考虑下列 proto，其中 `wheels` 的默认值为 `2`：

```proto
// A representation of an automobile
message Automobile {
    // google.api.resource and other annotations and fields

    // The number of wheels on the automobile.
    // The default value is 2, when no value is sent by the client.
    int wheels = 2;
}
```

首先当 `wheels` 的值为 `2` 时 proto 序列化为 JSON 如下：

```json
{
    "name": "my-car"
}
```

然后，API 服务把序列化改为即使值等于默认值 `2` 也包含 `wheel`，如下：

```json
{
    "name": "my-car",
    "wheels": 2
}
```

这构成主版本内不向后兼容的变更。

## Rationale

### Risk of string length changes

最终用户可能把资源属性（如 `name`）存储在长度受限的专用数据库列中。若服务开始返回长度为原先文档化/观察到长度两倍的 `name` 值，这可能意外破坏客户的数据库。此外，出现在 URLs 中的字符串属性（包括 query parameters）尤其可能有客户端限制，使它们对长度变更更敏感。

### Risk of changing value format or construction

客户常常依赖字段的格式或算法构造来做客户端解析、哈希或数据库表构造。在现有字段中更改它可能破坏那种客户端消费。
