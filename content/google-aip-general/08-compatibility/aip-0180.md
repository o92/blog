**英文标题**：Backwards compatibility  
**原文**：[AIP-180](https://google.aip.dev/180) · approved · 创建 2019-07-23

API 本质上是跟用户的契约。用户常常对着 API 写代码，丢进生产，并期望它继续工作——除非稳定性级别另有说明（见 [AIP-181]({{< ref "aip-0181" >}})）。所以要分清：什么改动还算向后兼容，什么已经把旧客户端弄坏。

## 底线

服务更新到新的次版本或补丁版本时，现有客户端代码不得被破坏。旧客户端必须还能对着更新的服务器工作（主版本号相同）。

变更是否兼容并不总是一目了然。这里的指导应当视为指示性的，不是每一种可能变更的穷尽清单。

要分开看三种兼容性：

1. Source compatibility：对着先前版本写的代码，必须还能对着更新版本编译，并成功与更新版本的客户端库一起跑。
2. Wire compatibility：对着先前版本写的代码，必须还能与更新的服务器正确通信。不只是输入输出兼容，序列化与反序列化的期望也必须对得上。
3. Semantic compatibility：对着先前版本写的代码，必须继续收到大多数合理开发者会期望的东西。实践中这可能棘手，有时确定用户会期望什么要靠判断。

下面的具体指导，一般假定传输格式是 protocol buffers 与 JSON。其它传输格式可能规则略有不同。

这套指导假定：API 会被一系列消费者调用，用多种语言写，且无法控制他们何时、如何更新。范围更窄的 API（例如只被与 API producer 同一团队写的客户端调用，或以可强制更新的方式部署）应当仔细考虑自己的兼容性要求。

### 加组件

一般而言，新组件（interfaces、methods、messages、fields、enums 或 enum values）可以在同一主版本内加到现有 APIs。

但加的时候记住：

- 对着先前表面写的代码（因此不知道新组件）必须继续被以与以前相同的方式对待。
  - 不得给现有请求 messages 或资源加新的 required 字段。
  - 任何由客户端填充的字段，必须有匹配该字段引入之前行为的默认行为。
    - 有些情形会很棘手。例如先前返回全部条目，后来才加分页（即 `page_size` 无限——这不被建议）。若新 `page_size` 的默认值少于先前返回的数量，较旧客户端会错误地以为结果已经拿全。
  - 任何先前由服务器填充的字段必须继续被填充，即使已经显得冗余。
- 对 enum values 要特别小心：用户代码可能无法优雅地处理新值。
  - 只用于请求 messages 的 enums，可以自由加 enum values。
  - 用于响应 messages 或资源、且预期会收到新值的 enums，应当把这一点写进文档。此时仍可以加 enum values；但应当适当谨慎。

添加与现有组件密切相关的组件时（例如已有 `string foo` 再加 `string foo_value`），可能碰到生成代码冲突。服务所有者应当意识到他们或其用户很可能用到的工具里的细微之处（工具作者应当尽量避开这类细微之处）。

### 删或改名

现有组件（interfaces、methods、messages、fields、enums 或 enum values）不得从同一主版本的现有 APIs 里移除。移除是向后不兼容变更。

重命名在语义上等于「删掉再加」。若这种变更可取，服务可以加新组件，但不得移除现有组件。若这可能让用户为同一语义想法指定冲突值，行为必须写清楚。

### 在文件之间搬

现有组件不得在文件之间移动。

把组件从同一 package 内的一个 proto 文件搬到另一个，线上是兼容的。但对 C++、Python 等语言，生成代码会破坏：`import` 与 `#include` 不再指向正确位置。

### 搬进 oneof

现有字段不得移入或移出 oneof。这在 Go protobuf stubs 里是向后不兼容变更。

### 改字段类型

现有字段与 messages 不得改类型。即使新类型线上兼容，类型变更也会以破坏性方式改变生成代码。

### 改字符串长度

APIs 应当避免增加 `string` 字段大小或限制（若作为输入接受）的上界。APIs 应当把期望的大小上界增加视为不兼容变更（作为示例见 [改资源名](#改资源名)）。有必要保住一致大小时，APIs 可以用填充字符把值填满，但若这样做必须写进文档。

### 改资源名

资源不得更改其 name（见 [AIP-122]({{< ref "aip-0122" >}})）。

跟大多数破坏性变更不同，这也影响主版本：为了让客户端期望用 v2.0 访问在 v1.0 中创建的资源（或反过来），两个版本中必须使用相同的 resource name。

更微妙的是，有效 resource names 的集合也不应当改，原因如下：

- 若 resource name 格式变得更受限，先前会成功的请求现在会失败。
- 若 resource name 格式变得比先前文档化的更宽松，基于先前文档做假设的代码可能坏掉。用户很可能把 resource names 存到别处，其方式可能对允许的字符集与名称长度敏感。或者，用户可能按文档自己做 resource name 校验。
  - 例如，Amazon 开始允许更长的 EC2 resource IDs 时，给了客户 [大量警告](https://aws.amazon.com/blogs/aws/theyre-here-longer-ec2-resource-ids-now-available/)，并设了迁移期。

### 语义变更

代码常常依赖 API 行为与语义，即使这类行为未被显式支持或写进文档。因此，APIs 不得以很可能破坏合理用户代码的方式更改可见行为或语义。这类变更会被那些用户视为破坏性。

这确实涉及一定程度的判断。提议的变更是否可能破坏用户，并不总是清楚。把这条读得太宽，表面上可能挡住任何变更——那不是意图。

#### 改值的格式或构造方式

APIs 不得在 API 版本内更改用于构造现有字段值的期望格式或算法——即使该字段是 `OUTPUT_ONLY`、由 API 服务填充。这样做需要新的 API 版本。

例如，把符合 IPv4 格式的字段 `ip_address` 改成包含 IPv6 值，是破坏性变更。

#### 默认值不得改

默认值是客户端未指定时，服务器为资源设置的值。本节只适用于资源字段上的静态默认值，不适用于动态默认值，例如资源的默认 IP 地址。

更改默认值视为破坏性，不得做。资源的默认行为由其默认值确定，这不得跨次版本改变。

例如：

```proto
message Book {
    // google.api.resource and other annotations and fields

    // The genre of the book
    // If this is not set when the book is created, the field will be given a value of FICTION.
    enum Genre {
      UNSPECIFIED = 0;
      FICTION = 1;
      NONFICTION = 2;
    }
}
```

改为：

```proto
message Book {
    // google.api.resource and other annotations and fields

    // The genre of the book
    // If this is not set when the book is created, the field will be given a value of NONFICTION.
    enum Genre {
      UNSPECIFIED = 0;
      FICTION = 1;
      NONFICTION = 2;
    }
}
```

会构成破坏性变更。

#### 默认值怎么序列化

APIs 不得更改带默认值的字段的序列化方式。例如：值等于默认值时字段不出现在响应中，就不得改成「即使等于默认值也带上该字段」。客户端可能把字段在资源里出现或不出现当成有语义的。因此，对缺席值的序列化方式不得在次版本中变更。

考虑下列 proto，其中 `wheels` 的默认值为 `2`：

```proto
// A representation of an automobile
message Automobile {
    // google.api.resource and other annotations and fields

    // The number of wheels on the automobile.
    // The default value is 2, when no value is sent by the client.
    int wheels = 2;
}
```

首先当 `wheels` 的值为 `2` 时 proto 序列化为 JSON 如下：

```json
{
    "name": "my-car"
}
```

然后，API 服务把序列化改为即使值等于默认值 `2` 也包含 `wheel`，如下：

```json
{
    "name": "my-car",
    "wheels": 2
}
```

这构成主版本内不向后兼容的变更。

## 为什么

### 字符串长度变更的风险

最终用户可能把资源属性（如 `name`）存在长度受限的专用数据库列里。若服务开始返回长度为原先文档化/观察到长度两倍的 `name` 值，可能意外弄坏客户的数据库。出现在 URLs 里的字符串属性（包括 query parameters）尤其可能有客户端限制，对长度变更更敏感。

### 改值的格式或构造方式的风险

客户常常依赖字段的格式或算法构造，做客户端解析、哈希或数据库表构造。在现有字段里改它，可能破坏那种客户端消费。
