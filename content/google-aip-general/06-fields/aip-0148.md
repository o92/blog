有些概念在任何 API 语料里都很常见：资源名、显示名、创建时间、注解。这时用一套一致的字段名和行为来传达这些概念，用户才能把从一个 API 学到的习惯带到另一个。

## 名副其实

标准字段应当用来描述它对应的那个概念，不应当拿去干别的。

### 资源名与 ID

#### name

每个资源必须有 `string name` 字段，用来放 resource name（见 [AIP-122]({{< ref "aip-0122" >}})）。它应当是资源里的第一个字段。

除非本文另有涵盖，`_name` 后缀不应当用来描述其它类型的名称。

#### parent

`string parent` 字段指集合 parent 的 resource name，应当用在大多数 List 请求（见 [AIP-132]({{< ref "aip-0132" >}})）和 Create 请求（见 [AIP-133]({{< ref "aip-0133" >}})）里。

### 其它名字

#### display_name

`string display_name` 必须是可变、用户可设的字段，用来提供人类可读名称，给用户界面用。声明式友好资源应当包含此字段（见 [AIP-128]({{< ref "aip-0128" >}})）。

Display names 不应当有唯一性要求，并且应当限制为 <= 63 个字符。

#### title

`string title` 应当是实体的官方名称，例如公司名。它是 `string display_name` 更正式的变体。

#### given_name

`string given_name` 必须指人或动物的 given name。资源不得对这个概念用 `first_name`：在许多文化里，given name 并不放在前面。

#### family_name

`string family_name` 必须指人或动物的 family name。资源不得对这个概念用 `last_name`：在许多文化里，family name 并不放在后面。

### 时间戳

#### create_time

output only 的 `google.protobuf.Timestamp create_time` 必须表示资源被创建的时间戳。可以是发起创建的时间，也可以是创建完成的时间。声明式友好资源应当包含此字段（见 [AIP-128]({{< ref "aip-0128" >}})）。

#### update_time

output only 的 `google.protobuf.Timestamp update_time` 必须表示资源最近被更新的时间戳。用户对资源做的任何变更都必须刷新这个值；服务内部对资源做的变更可以刷新。声明式友好资源应当包含此字段（见 [AIP-128]({{< ref "aip-0128" >}})）。

#### delete_time

output only 的 `google.protobuf.Timestamp delete_time` 必须表示资源被软删除的时间戳。可以对应「用户请求删除」的时间，也可以对应「服务成功软删除」的时间。资源未被软删除时，`delete_time` 必须为空。

支持软删除的资源应当提供此字段（见 [AIP-164]({{< ref "aip-0164" >}})）。

#### expire_time

`google.protobuf.Timestamp expire_time` 应当表示给定资源或资源属性不再有用或有效的时间（例如轮换的安全密钥）。也可以用于 [AIP-214]({{< ref "aip-0214" >}}) 里描述的类似过期形式。

服务可以给出不精确的 `expire_time`，但资源不得在该时间之前过期。

#### purge_time

`google.protobuf.Timestamp purge_time` 应当表示软删除资源将从系统中清除的时间（见 [AIP-164]({{< ref "aip-0164" >}})）。也可以用于 [AIP-214]({{< ref "aip-0214" >}}) 里描述的类似过期形式。支持软删除的资源应当包含此字段。

服务可以给出不精确的 `purge_time`，但资源不得在该时间之前从系统中清除。

### annotations

为了存少量任意数据，可以加 `map<string, string> annotations` 字段。

`annotations` 必须遵守 [Kubernetes limits](https://kubernetes.io/docs/concepts/overview/working-with-objects/annotations/#syntax-and-character-set)，以保持线上兼容。应当要求点命名空间的 annotation keys，避免工具互相踩。

可能值得放进 annotations 的信息，例如：

- 对 CI/CD，用来传播的 pipeline run 标识符或版本控制标识符。

Annotations 跟各种 labels 不同。Labels 可以被服务端策略使用，例如 IAM conditions。Annotations 的存在，是为了让客户端工具存自己的状态，不必另搞数据库。

### 众所周知的字符串字段

#### IP address

表示 IP 地址的字段必须符合下列要求：

- 类型用 `string`
- 名称用 `ip_address`，或以后缀 `_ip_address` 结尾，例如 `resolved_ip_address`
- 用受支持格式指定 IP 版本：`IPV4`、`IPV6` 之一；两者皆可时用 `IPV4_OR_IPV6`（见 [AIP-202]({{< ref "aip-0202" >}})）

#### uid

output only 的 `string uid` 指资源的系统分配唯一标识符。提供时，此字段必须是 [UUID4](https://en.wikipedia.org/wiki/Universally_unique_identifier#Version_4_(random))，并且必须通过 `UUID4` 格式扩展标明（见 [AIP-202]({{< ref "aip-0202" >}})）。声明式友好资源应当包含此字段（见 [AIP-128]({{< ref "aip-0128" >}})）。

## 为何要标准化这些字符串字段

有些字段表示定义非常清楚、有时语义也有严格治理的概念或产物。对此类字段，API 表面同样标准化很重要。这能改进 API 消费者的工具和文档，也能让跨平台体验更统一。

## 沿革

2023-07 之前，软删除资源的 `purge_time` 也叫 `expire_time`。引入 `purge_time` 是为了少让用户混淆。
