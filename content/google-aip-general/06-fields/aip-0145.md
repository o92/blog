服务常常需要表示离散或连续值的范围。它们含义差异很大，类型也很多：整数、浮点与时间戳，仅举几例；并且范围的期望含义可能因所讨论范围的类型而有细微变化。

## Guidance

表示范围的资源或 message 通常 **should** 使用两个同类型的独立字段，前缀为 `start_` 与 `end_`：

```proto
// A representation of a chapter in a book.
message Chapter {
  string title = 1;

  // The page where this chapter begins.
  int32 start_page = 2;

  // The page where the next chapter or section begins.
  int32 end_page = 3;
}
```

### Inclusive or exclusive ranges

表示范围的字段在大多数情形下 **should** 使用包含起始值与排除结束值（半闭区间）；用区间记法：`[start_xxx, end_xxx)`。

排除结束值更可取，原因如下：

- 它符合用户期望，尤其对时间戳等连续值，并避免需要表达不精确的「极限值」（例如 `2012-04-20T23:59:59`）。
- 它与大多数常见编程语言一致，包括 C++、Java、Python 与 Go。
- 对相邻范围更容易推理：`[0, x), [x, y), [y, z)`，值可以从一个范围衔接到下一个。

### Timestamp intervals

下一节描述 [google.type.Interval](https://github.com/googleapis/googleapis/blob/master/google/type/interval.proto) 类型的使用，它位于 [AIP-213]({{< ref "aip-0213" >}}) 所描述的 common protos 之中。此类型表示两个时间戳之间的范围，带包含起始值与排除结束值。

符合 `Interval` message 期望的两个时间戳之间的范围 **should** 使用它，而不是使用独立的 start 与 end 字段。这允许针对 `Interval` message 编写客户端代码（例如检查给定时间戳是否落在区间内），并在同一 API 的多个区间甚至多个 APIs 之间复用。

APIs **may** 改为使用 start 与 end 时间戳字段。特别地，若 API 内的 message 本质上在描述一个区间并带有关于该区间的额外信息，使用 `Interval` message 引入的额外嵌套层级可能不可取。

### Exceptions

有些情形下，包含起始与结束值（闭区间）有显著的口语先例，以至于使用排除结束值即使对习惯它们的人也会造成困惑。

例如，讨论日期时（不要与时间戳混淆），大多数人使用包含结束：日期为 "April 21-23" 的会议预期开三天：April 21、April 22 与 April 23。对星期几也是如此：营业时间为 "Monday through Friday" 的商家在 Fridays 是开着的，不是关着的。

此时 **should** 改用前缀 `first` 与 `last`：

```proto
// A representation of a chapter in a book.
message Chapter {
  string title = 1;

  // The first page of the chapter.
  int32 first_page = 2;

  // The last page of the chapter.
  int32 last_page = 3;
}
```

对包含起始与结束值有显著口语先例的范围，字段 **should** 仅对这些范围使用带 `first_` 与 `last_` 前缀的包含结束值。服务对其它不适用此情形的范围 **should** 仍使用排除结束值，并且 **must** 把每个范围清楚文档化为包含或排除。
