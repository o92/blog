服务经常要表示一段范围：整数、浮点、时间戳都常见。范围的含义差很多，结束值算不算进去，也常因类型不同而有细微差别。不约定的话，调用方只能靠猜。

## 用 start_ 和 end_

表示范围的资源或 message，通常应当用两个同类型的独立字段，前缀分别是 `start_` 和 `end_`：

```proto
// A representation of a chapter in a book.
message Chapter {
  string title = 1;

  // The page where this chapter begins.
  int32 start_page = 2;

  // The page where the next chapter or section begins.
  int32 end_page = 3;
}
```

### 包含起点，排除终点

表示范围的字段，大多数情形应当包含起始值、排除结束值（半闭区间）。区间记法：`[start_xxx, end_xxx)`。

排除结束值更合适，原因如下：

- 符合用户预期，尤其对时间戳这类连续值，也不必再写不精确的「极限值」（例如 `2012-04-20T23:59:59`）。
- 跟大多数常见编程语言一致，包括 C++、Java、Python 与 Go。
- 相邻范围更好推理：`[0, x), [x, y), [y, z)`，值可以从一段衔接到下一段。

### 时间戳区间

[`google.type.Interval`](https://github.com/googleapis/googleapis/blob/master/google/type/interval.proto) 在 common protos 里（见 [AIP-213]({{< ref "aip-0213" >}})）。它表示两个时间戳之间的范围，包含起点、排除终点。

两个时间戳之间的范围若符合 `Interval` 的期望，应当用它，不要拆成独立的 start / end 字段。客户端可以针对 `Interval` 写通用代码（例如判断某个时间戳是否落在区间内），同一 API 里多个区间、甚至多个 API 之间也能复用。

API 也可以改用 start 与 end 时间戳字段。尤其是：这个 message 本质上就是在描述一个区间，并且还带着关于该区间的额外信息。这时再套一层 `Interval`，嵌套可能得不偿失。

### 口语里习惯闭区间的例外

有些情形，包含起点和终点（闭区间）有显著的口语先例。这时再用排除结束值，即使习惯半闭区间的人也会懵。

例如谈日期时（不要跟时间戳混在一起），多数人用包含结束：会议写 "April 21-23"，预期开三天：April 21、April 22、April 23。星期几也一样：营业时间 "Monday through Friday"，Friday 是开着的，不是关着的。

这时应当改用前缀 `first` 与 `last`：

```proto
// A representation of a chapter in a book.
message Chapter {
  string title = 1;

  // The first page of the chapter.
  int32 first_page = 2;

  // The last page of the chapter.
  int32 last_page = 3;
}
```

对包含起点和终点有显著口语先例的范围，字段应当只对这些范围用 `first_` / `last_` 前缀，并取包含结束值。其它不适用此情形的范围，服务应当仍用排除结束值。每个范围必须写清楚是包含还是排除。
