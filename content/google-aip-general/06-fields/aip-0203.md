**英文标题**：Field behavior documentation  
**原文**：[AIP-203](https://google.aip.dev/203) · approved · 创建 2018-07-17  
**许可**：原文 © Google，[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)

在 protocol buffers 里定义字段时，习惯向用户说明字段行为的某些方面：它是 required 还是 optional。其它工具理解这些行为也可能有用，例如优化客户端库签名。`google.api.field_behavior` 就是用来写这些约定的；它本身不做校验，但客户端会当真。

## 每个字段都要标

API 用 `google.api.field_behavior` annotation 描述广为理解的字段行为，例如字段为 required 或 immutable。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- API 必须在请求中使用的 message 或 sub-message 上的每个字段应用 `google.api.field_behavior` annotation。
  - 一个例外：资源 message 上 AIP-154 的 `etag` 字段，不应当赋予任何 `google.api.field_behavior`。
  - 此外，`oneof` 字段可以省略 `google.api.field_behavior`，但这时应当在注释里写明任何特定行为。
- annotation 必须包含任何准确描述该字段行为的 [google.api.FieldBehavior](https://github.com/googleapis/googleapis/blob/master/google/api/field_behavior.proto#L49) 值。
  - 不得使用 `FIELD_BEHAVIOR_UNSPECIFIED`。
- API 必须至少使用 `REQUIRED`、`OPTIONAL` 或 `OUTPUT_ONLY` 之一。

`field_behavior` 不影响 proto 级行为，但许多客户端（CLI、SDK）靠它们生成代码。加新字段时，要把相关值彻底过一遍。

没有 annotation 的字段，为向后兼容被解释为 `OPTIONAL`。尽管如此，这个 annotation 不得省略。

本文给出的词汇只用于**描述**，本身不加任何校验。目的是让客户端一致地文档化这些行为。

### 嵌套 message 上的字段行为

嵌套 message 上的 `google.api.field_behavior` 与父级的 annotations 相互独立。

例如，嵌套 message 可以有 `REQUIRED` 的字段行为，而父字段可以是 `OPTIONAL`：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上面这个例子里：若指定了 `title`，则 `text` 字段是 required。

## 词汇

### IDENTIFIER

用 `IDENTIFIER` 表示资源 message 里用来标识该资源的字段。它必须附着在 `name` 字段上，不得附着在任何其它字段上（表示 resource names 的字段见 [AIP-122]({{< ref "aip-0122" >}})）。

`IDENTIFIER` 传达的是：在 create 的语境里该字段不作为输入接受（即 `OUTPUT_ONLY`）；同时被视为 `IMMUTABLE`；在以资源为主要输入的变更方法里（例如标准 Update，见 [AIP-134]({{< ref "aip-0134" >}})）又作为输入接受。

此 annotation 不得用在 message 内对其它资源的引用上。

### IMMUTABLE

用 `IMMUTABLE` 表示资源上的字段在创建之后不能更改。它可以加在作为输入或输出、required 或 optional 的字段上。

服务在 update 请求（或类似请求）里收到 immutable 字段时，即使它在 update mask 里：值匹配则应当忽略；请求变更则应当以 `INVALID_ARGUMENT` 报错。

可能的用例（非穷尽）包括：

- 在应用生命周期内不可修改的资源属性（例如磁盘类型）。

「有条件 immutable」的字段不得赋予 immutable annotation。

### INPUT_ONLY

用 `INPUT_ONLY` 表示该字段在请求中提供，对应字段不会出现在输出里。

此外，字段应当仅在它是资源 message 中的字段、或资源 message 内所含 message 的字段时，才描述为 input only。值得注意的是，请求 message（只作为 RPC 参数的 message，名称通常以 `Request` 结尾）里的字段不应当描述为 input only：这已经隐含了。

可能的用例（非穷尽）包括：

- [AIP-214]({{< ref "aip-0214" >}}) 里描述的 `ttl` 字段。

Input only 字段很少见，用之前应仔细考虑。

### OPTIONAL

用 `OPTIONAL` 表示字段不是 required。

若字段是请求 message（作为 RPC 参数的 message，通常以 `Request` 结尾）上的字段，或 submessage 上的字段，它可以描述为 optional。

字段存在性标签 `optional` 与字段行为 `OPTIONAL` 并不互斥。更多细节见 [AIP-149]({{< ref "aip-0149" >}})。

### OUTPUT_ONLY

用 `OUTPUT_ONLY` 表示该字段在响应中提供，但在请求 message 里带上它没有任何效果。服务器必须清除此字段上的任何值，并且不得因为输入上此字段有值而抛错。类似地，服务必须忽略 update field mask 里 output only 字段的存在（见 [AIP-161]({{< ref "aip-0161" >}})）。

此外，字段应当仅在它是资源 message 中的字段、或更下层 message 的字段时，才描述为 output only。值得注意的是，响应 message（只作为 RPC 返回值的 message，通常以 `Response` 结尾）里的字段不应当描述为 output only：这已经隐含了。

若对 API 适当，output only 字段可以设为空值。

可能的用例（非穷尽）包括：

- Create 或 update 时间戳。
- 基于原始用户输入的派生或结构化信息。
- 由服务分配、无法更改的资源属性。

### REQUIRED

用 `REQUIRED` 表示该字段必须在请求或资源上存在（并设为非空值）。

字段应当仅在**下列之一**时描述为 required：

- 它是用户在某处作为输入提供的资源上的字段。此时，仅当存储了「truthy」值时资源才有效。
  - 创建资源时（见 [AIP-133]({{< ref "aip-0133" >}})），create 请求上必须为该字段提供值。
  - 更新资源时（见 [AIP-134]({{< ref "aip-0134" >}})），用户可以省略该字段，前提是该字段也从 field mask 里缺席，表示对该字段无变更（否则必须提供）。
- 它是请求 message（作为 RPC 参数的 message，名称通常以 `Request` 结尾）上的字段。此时必须作为请求的一部分提供值；不这样做必须导致错误（通常是 `INVALID_ARGUMENT`）。

上面的「truthy」定义如下：

- 对 primitives：除 `0`、`0.0`、空 string/bytes 与 `false` 以外的值
- 对 repeated 字段与 maps：至少有一条
- 对 messages：至少一个「truthy」字段的任何 message

字段不应当为了表示下列情形而描述为 required：

- 响应中将始终存在的字段。
- 在某些情形下有条件 required 的字段。
- 任何 message（包括作为资源的 messages）上从未作为用户输入使用的字段。

大多数情形下，空值（布尔的 `false`、整数的 `0`、enums 的未指定值）和未设置值无法区分，因此把 required 字段设成 falsy 值会产生错误。推论：required 布尔必须设为 `true`。

### UNORDERED_LIST

在资源的 repeated 字段上用 `UNORDERED_LIST`，表示服务不保证列表中条目的顺序。

若服务不保证列表中元素的顺序会匹配用户发送的顺序——包括服务会代表用户排序列表的情形——字段应当描述为 unordered list。

带 unordered list 的资源可以以稳定顺序返回列表，也可以以随机、不稳定顺序返回。

## 向后兼容

添加或更改 `google.api.field_behavior` 值，可以表示现有客户端视为不兼容的 API 语义变更。下面是向后不兼容的例子：

- 向先前视为 `OPTIONAL`（隐含或其它）的现有字段添加 `REQUIRED`
- 向现有请求 message 添加标注为 `REQUIRED` 的新字段
- 向先前作为输入接受的现有字段添加 `OUTPUT_ONLY`
- 向先前作为输出发出的现有字段添加 `INPUT_ONLY`
- 向先前视为可变的现有字段添加 `IMMUTABLE`
- 从先前作为输入忽略的现有字段移除 `OUTPUT_ONLY`
- 从现有字段移除 `IDENTIFIER`

有些变更**是**向后兼容的：

- 向现有字段添加 `OPTIONAL`
- 向现有 `name` 字段添加 `IDENTIFIER`
- 把现有字段从 `REQUIRED` 改为 `OPTIONAL`
- 把现有字段从 `OUTPUT_ONLY` 和/或 `IMMUTABLE` 改为 `IDENTIFIER`
- 从现有字段移除 `REQUIRED`
- 从先前在响应中排除的现有字段移除 `INPUT_ONLY`
- 从先前视为 immutable 的现有字段移除 `IMMUTABLE`

## 理由

### 为何需要 IDENTIFIER

Resource names 是任何合规资源的主键，在 create 上从不由用户完全构造。这类字段通常会被标成 `OUTPUT_ONLY`。但在资源本身是主要请求 payload 的场景里，它们又常常作为主键被消费。这时**不能**视为 `OUTPUT_ONLY`。此外，在变更请求（如标准 Update）里，资源名称作为主键不能就地改。这类字段通常会被标成 `IMMUTABLE`。这些互相冲突、又依赖语境的行为，意味着需要一个新值，单独标出并传达 resource name 字段的行为。

### 为何至少要有 REQUIRED、OPTIONAL 或 OUTPUT_ONLY

请求 message 中使用的字段必须是输入或输出。

对输出，`OUTPUT_ONLY` 就够了。

对输入，字段要么 required 要么 optional，因此应至少分别有 `REQUIRED` 或 `OPTIONAL`。只提供 `INPUT_ONLY` 并不传达该字段的必要性，所以仍有必要指定 `REQUIRED` 或 `OPTIONAL`。

### 为何强制要求 field_behavior

每个字段都带 field behavior annotation，资源所展现的整体行为才定义得更清楚。定义清楚的字段行为，能改进程序化客户端和用户理解。

要求 annotation 也迫使 API 作者在最初写 API 时显式考虑该行为。

写完之后再改字段行为，可能导致客户端里的向后不兼容变更。例如把 optional 字段改成 required，会导致 RPC 方法签名、或 Declarative client（见 [AIP-9]({{< ref "aip-0009" >}})）里资源的向后不兼容变更。更详细的兼容性指导见[向后兼容](#向后兼容)。

## 沿革

2023-05 起 field_behavior 成为强制。在此之前，annotation 常常被省略。其值被依赖以产出高质量客户端。此外，在主版本内事后添加或更改某些 field_behavior 值可能向后不兼容。更详细的兼容性指导见[向后兼容](#向后兼容)。

在编写 API 时要求 field_behavior 的收益，超过不对客户端和 API 用户这样做的成本。
