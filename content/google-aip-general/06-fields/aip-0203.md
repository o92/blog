**英文标题**：Field behavior documentation  
**原文**：[AIP-203](https://google.aip.dev/203) · approved · 创建 2018-07-17

在 protocol buffers 中定义字段时，习惯向用户解释字段行为的某些方面（例如它是 required 还是 optional）。此外，其它工具理解此行为也可能有用（例如，优化客户端库签名）。

## Guidance

APIs 使用 `google.api.field_behavior` annotation 描述广为理解的字段行为，例如字段为 required 或 immutable。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- APIs **must** 在请求中使用的 message 或 sub-message 上的每个字段应用 `google.api.field_behavior` annotation。
  - 一个例外是资源 message 上 AIP-154 的 `etag` 字段，它 **should not** 被赋予任何 `google.api.field_behavior`。
  - 此外，`oneof` 字段 **may** 省略 `google.api.field_behavior`，但此时 **should** 在注释中文档化任何特定行为。
- annotation **must** 包含任何准确描述该字段行为的 [google.api.FieldBehavior](https://github.com/googleapis/googleapis/blob/master/google/api/field_behavior.proto#L49) 值。
  - **must not** 使用 `FIELD_BEHAVIOR_UNSPECIFIED`。
- APIs **must** 至少使用 `REQUIRED`、`OPTIONAL` 或 `OUTPUT_ONLY` 之一。

**Warning:** 尽管 `field_behavior` 不影响 proto 级行为，许多客户端（例如 CLIs 与 SDKs）依赖它们来生成代码。添加新字段时，彻底审查并考虑哪些值相关。

没有 annotation 的字段为向后兼容被解释为 `OPTIONAL`。尽管如此，此 annotation **must not** 被省略。

**Note:** 本文给出的词汇仅用于*描述*目的，本身不添加任何验证。目的是为客户端一致地文档化此行为。

### field behavior of nested messages

嵌套 message 上的 `google.api.field_behavior` annotations 与父级的 annotations 相互独立。

例如，嵌套 message 可以有 `REQUIRED` 的字段行为，而父字段可以是 `OPTIONAL`：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

在上述情形中，若指定了 `title`，则 `text` 字段是 required。

## Vocabulary

### Identifier

使用 `IDENTIFIER` 表示资源 message 内的字段用于标识该资源。它 **must** 附着在 `name` 字段上，并且 **must not** 附着在任何其它字段上（见 [表示 resource names 的字段]({{< ref "aip-0122" >}})）。

`IDENTIFIER` 值传达：在 create 方法的语境中该字段不作为输入接受（即 `OUTPUT_ONLY`），同时被视为 `IMMUTABLE`，并在以资源为主要输入的变更方法（例如 [Standard Update]({{< ref "aip-0134" >}})）中作为输入接受。

此 annotation **must not** 应用于 message 内对其它资源的引用。

### Immutable

使用 `IMMUTABLE` 表示资源上的字段在创建之后不能更改。这可以应用于作为输入或输出、required 或 optional 的字段。

当服务在 update 请求（或类似请求）中收到 immutable 字段时，即使包含在 update mask 中，若值匹配，服务 **should** 忽略该字段，但若请求变更则 **should** 以 `INVALID_ARGUMENT` 报错。

immutable 字段的潜在用例（非穷尽列表）包括：

- 在应用生命周期内不可修改的资源属性（例如磁盘类型）。

**Note:** 「有条件 immutable」的字段 **must not** 被赋予 immutable annotation。

### Input only

使用 `INPUT_ONLY` 表示该字段在请求中提供，并且对应字段不会包含在输出中。

此外，字段 **should** 仅在它是资源 message 中的字段、或资源 message 内所含 message 的字段时，才描述为 input only。值得注意的是，请求 messages（只作为 RPC 参数的 message，名称通常以 `Request` 结尾）中的字段 **should not** 描述为 input only，因为这已经隐含。

input only 字段的潜在用例（非穷尽列表）包括：

- AIP-214 中描述的 `ttl` 字段。

**Warning:** Input only 字段很少见，使用前应仔细考虑。

### Optional

使用 `OPTIONAL` 表示字段不是 required。

若字段是请求 message（作为 RPC 参数的 message，通常以 `Request` 结尾）上的字段，或 submessage 上的字段，它 **may** 描述为 optional。

**Note:** 字段存在性标签 `optional` 与字段行为 `OPTIONAL` 并不互斥。更多细节见 [AIP-149]({{< ref "aip-0149" >}})。

### Output only

使用 `OUTPUT_ONLY` 表示该字段在响应中提供，但在请求 message 中包含该字段没有任何效果（服务器 **must** 清除此字段上的任何值，并且 **must not** 因输入上此字段存在值而抛出错误）。类似地，服务 **must** 忽略 update field masks 中 output only 字段的存在（见：[AIP-161]({{< ref "aip-0161" >}})）。

此外，字段 **should** 仅在它是资源 message 中的字段、或更下层 message 的字段时，才描述为 output only。值得注意的是，响应 messages（只作为 RPC 返回值的 message，通常以 `Response` 结尾）中的字段 **should not** 描述为 output only，因为这已经隐含。

若对 API 适当，Output only 字段 **may** 设为空值。

output only 字段的潜在用例（非穷尽列表）包括：

- Create 或 update 时间戳。
- 基于原始用户输入的派生或结构化信息。
- 由服务分配、无法更改的资源属性。

### Required

使用 `REQUIRED` 表示该字段 **must** 在请求或资源上存在（并设为非空值）。

字段 **should** 仅在*下列之一*时描述为 required：

- 它是用户在某处作为输入提供的资源上的字段。此时，仅当存储了「truthy」值时资源才有效。
  - [创建]({{< ref "aip-0133" >}}) 资源时，create 请求上 **must** 为该字段提供值。
  - [更新]({{< ref "aip-0134" >}}) 资源时，用户 **may** 省略该字段，前提是该字段也从 field mask 中缺席，表示对该字段无变更（否则 **must** 提供）。
- 它是请求 message（作为 RPC 参数的 message，名称通常以 `Request` 结尾）上的字段。此时，**must** 作为请求的一部分提供值，若不这样做 **must** 导致错误（通常是 `INVALID_ARGUMENT`）。

我们把上面的「truthy」定义如下：

- 对 primitives，除 `0`、`0.0`、空 string/bytes 与 `false` 以外的值
- 对 repeated 字段与 maps，至少有一个条目的值
- 对 messages，至少一个「truthy」字段的任何 message。

字段 **should not** 为了表示下列情形而描述为 required：

- 响应中将始终存在的字段。
- 在某些情形下有条件 required 的字段。
- 任何 message（包括作为资源的 messages）上从未作为用户输入使用的字段。

**Note:** 在大多数情形下，空值（例如布尔的 `false`、整数的 `0`、或 enums 的未指定值）与未设置值无法区分，因此把 required 字段设为 falsy 值会产生错误。推论是：required 布尔必须设为 `true`。

### Unordered List

在资源的 repeated 字段上使用 `UNORDERED_LIST` 表示服务不保证列表中条目的顺序。

若服务不保证列表中元素的顺序会匹配用户发送的顺序，包括服务会代表用户排序列表的情形，字段 **should** 描述为 unordered list。

带 unordered list 的资源 **may** 以稳定顺序返回列表，或 **may** 以随机、不稳定顺序返回列表。

## Backwards compatibility

添加或更改 `google.api.field_behavior` 值可以表示现有客户端视为不兼容的 API 语义变更。下列是 `google.api.field_behavior` 的向后不兼容变更示例：

* 向先前视为 `OPTIONAL`（隐含或其它）的现有字段添加 `REQUIRED`
* 向现有请求 message 添加标注为 `REQUIRED` 的新字段
* 向先前作为输入接受的现有字段添加 `OUTPUT_ONLY`
* 向先前作为输出发出的现有字段添加 `INPUT_ONLY`
* 向先前视为可变的现有字段添加 `IMMUTABLE`
* 从先前作为输入忽略的现有字段移除 `OUTPUT_ONLY`
* 从现有字段移除 `IDENTIFIER`。

有些变更*是*向后兼容的，如下：

* 向现有字段添加 `OPTIONAL`
* 向现有 `name` 字段添加 `IDENTIFIER`
* 把现有字段从 `REQUIRED` 改为 `OPTIONAL`
* 把现有字段从 `OUTPUT_ONLY` 和/或 `IMMUTABLE` 改为 `IDENTIFIER`
* 从现有字段移除 `REQUIRED`
* 从先前在响应中排除的现有字段移除 `INPUT_ONLY`
* 从先前视为 immutable 的现有字段移除 `IMMUTABLE`

## Rationale

### Identifier field behavior

Resource names 作为任何合规资源的主键，在 create 上从不由用户完全构造。此类字段通常被赋予 `OUTPUT_ONLY` 字段行为。然而，在资源本身是主要请求 payload 的场景中，它们也常常作为主键被消费。此类字段*不能*视为 `OUTPUT_ONLY`。此外，在变更请求中，如 Standard Update，资源名称作为主键不能就地更改。此类字段通常被赋予 `IMMUTABLE` 字段行为。这些冲突且依赖语境的字段行为意味着需要一个新值来单独标出并传达 resource name 字段的行为。

### Required set of annotations

请求 message 中使用的字段必须是输入或输出。

对输出，`OUTPUT_ONLY` annotation 就足够了。

对输入，字段要么 required 要么 optional，因此应至少分别有 `REQUIRED` 或 `OPTIONAL` annotation。仅提供 `INPUT_ONLY` 并不传达该字段的必要性，因此仍有必要指定 `REQUIRED` 或 `OPTIONAL`。

### Requiring field behavior

通过为每个字段包含 field behavior annotation，资源所展现的整体行为定义得更清楚。定义清楚的字段行为改进程序化客户端与用户理解。

要求 annotation 也迫使 API 作者在最初编写 API 时显式考虑该行为。

在最初编写之后修改字段行为可能导致客户端中的向后不兼容变更。例如，把 optional 字段改为 required 会导致 RPC 方法签名或 [Declarative client]({{< ref "aip-0009" >}}) 中资源的向后不兼容变更。更详细的兼容性指导见 [Backwards compatibility](#backwards-compatibility) 一节。

## History

2023-05 起 field_behavior 成为强制。在此变更之前，annotation 常常被省略。其值被依赖以产出高质量客户端。此外，在主版本内事后添加或更改某些 field_behavior 值可能向后不兼容。更详细的兼容性指导见 [Backwards compatibility](#backwards-compatibility) 一节。

在编写 API 时要求 field_behavior 的收益超过不对客户端与 API 用户这样做的成本。
