**英文标题**：States  
**原文**：[AIP-216](https://google.aip.dev/216) · approved · 创建 2018-10-01 · 更新 2022-06-02  
**许可**：原文 © Google，[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)

许多 API 资源带有「state」概念：通常是资源在其生命周期中的位置。例如，虚拟机可能正在供给、可供使用、正在关闭，或潜在处于若干其它情形之一。作业或查询可能正在准备运行、正在主动运行、已经完成，等等。

## Guidance

需要传达其 state 的资源 **should** 使用 enum，它 **should** 称为 `State`（或若需要更多特异性，以单词 `State` 结尾）。当仅作为该 message 内的字段使用时，此 enum **should** 嵌套在它所描述的 message 内。

**Important:** 我们使用术语 `State`，而*不是* `Status`（后者保留给 HTTP 与 gRPC statuses）。

### Enum values

理想情况下，Google APIs 在表达相同语义概念时全程使用相同术语。表达给定 state 通常有许多可用的词，但我们的客户常常把多个 APIs 一起用，当我们的术语一致时对他们更容易。

在高层次上：

- 可供使用的资源是 `ACTIVE`（优先于 "ready" 或 "available" 等术语）。
- 已完成（通常是终止性的）所请求动作的资源使用过去分词（通常以 `-ED` 结尾），例如 `SUCCEEDED`（不是 "successful"）、`FAILED`（不是 "failure"）、`DELETED`、`SUSPENDED` 等。
- 当前正在经历 state 变更的资源使用现在分词（通常以 `-ING` 结尾），例如 `RUNNING`、`CREATING`、`DELETING` 等。此时，期望该 state 是暂时的，并将自行解析为另一 state，无需进一步的用户动作。

**Note:** 记住只添加对客户有用的 states。仅仅因为内部系统中存在就暴露大量 states 是不必要的，并会给客户增加困惑。每个 state 必须带有为何必要的用例。

### Output only

资源中引用 `State` enum 的字段 **should** 按照 [AIP-203]({{< ref "aip-0203" >}}) 表现为并文档化为 "Output only"。

APIs **should not** 允许通过 "update" 方法直接更新 `State` enum（或通过 "create" 方法直接设置），并且 **should** 改为使用自定义 state transition methods。

这是因为 update methods 一般不期望有副作用，也因为直接更新 state 意味着可以把 state 设为任何可用值，而 states 一般反映资源在生命周期中的进展。

### State transition methods

State transition methods 是一类特殊的 custom method，负责把 state 字段从一个 enum 值转换到另一个。作为转换的一部分，其它字段也可能改变，例如 `update_time` 字段。方法定义应如下：

```proto
// Publishes a book.
// The `state` of the book after publishing is `PUBLISHED`.
// `PublishBook` can be called on Books in the state `DRAFT`; Books in a
// different state (including `PUBLISHED`) returns an error.
rpc PublishBook(PublishBookRequest) returns (Book) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:publish"
    body: "*"
  };
}
```

- 方法名称 **should** 为动词后跟资源 message 名称的单数形式。
- 请求 message **must** 与 RPC 名称匹配，并带 `Request` 后缀。
- 响应 message **should** 为资源本身。
  - 若 RPC 是 [长时运行的]({{< ref "aip-0151" >}})，响应 message **should** 为解析为资源本身的 `google.longrunning.Operation`。
- HTTP 动词 **must** 为 `POST`。
- HTTP URI **must** 使用 `:` 字符后跟自定义动词（上例中的 `:publish`），并且 URI 中的动词 **must** 与 RPC 名称中的动词匹配。
  - 若需要词分隔，**must** 使用 `camelCase`。
- `google.api.http` annotation 中的 `body` 子句 **must** 为 `"*"`。
- 接收 resource name 的请求 message 字段 **should** 映射到 URI 路径。
  - 该字段 **should** 称为 `name`。
  - `name` 字段 **should** 是 URI 路径中的唯一变量。其余参数 **should** 映射到 URI query parameters。
- 若不允许 state 转换，服务 **must** 以 `FAILED_PRECONDITION`（HTTP 400）报错。

请求 message 应如下：

```proto
message PublishBookRequest {
  // The name of the book to publish.
  // Format: publishers/{publisher}/books/{book}
  string name = 1 [
    (google.api.field_behavior) = REQUIRED,
    (google.api.resource_reference) = {
      type: "library.googleapis.com/Book"
    }];
}
```

- **must** 包含 resource name 字段。它 **should** 称为 `name`。
- 该字段的注释 **should** 文档化资源 pattern。
- **may** 包含其它字段。

## Additional Guidance

### Default value

每个 state enum 的零值 **should** 遵循下列约定：

```proto
enum State {
  // The default value. This value is used if the state is omitted.
  STATE_UNSPECIFIED = 0;

  // Other values...
}
```

资源 **should not** 向用户提供未指定的 state，并且此值实际上 **should not** 被使用。

### Value uniqueness

同一 package 内的多个顶层 enums **must** 不共享相同的值。这是因为 C++ protoc 代码生成器会把顶层 enum 值展平到单个命名空间。

State enums **should** 住在资源定义内部。

### Prefixes

在每个 enum 值上使用 `STATE_` 前缀是不必要的。除默认值 `STATE_UNSPECIFIED` 外，State enum 值 **should not** 以前缀带上 enum 名称。

### Breaking changes

**TL;DR:** 向用户清楚传达 state enums 将来可能收到新值，并对向现有 enum 添加 states 保持审慎。

尽管向现有 states enum 添加 states *可能* 破坏现有用户代码，添加 states 不视为破坏性变更。考虑只有两个值的 state：`ACTIVE` 与 `DELETED`。用户可能添加检查 `if state == ACTIVE` 的代码，并在 else 情形中简单假定资源已删除。若 API 后来为另一目的添加新 state，该代码将会破坏。

我们最终无法控制此行为，但 API 文档 **should** 积极鼓励用户编写针对 state enums 的代码时预期它们将来可能收到新值。

适当时候 APIs **may** 向现有 State enum 添加新 states，并且添加新 state *不*视为破坏性变更。

### When to avoid states

有时 `State` enum 可能不是对你的 API 最好的选择，尤其在 state 潜在值数量非常少，或 states 并非互斥的情形。

考虑上面讨论的只有 `ACTIVE` 与 `DELETED` 的 state 示例。此时，API 可能更好地暴露 `google.protobuf.Timestamp delete_time`，并指示用户依赖它是否设置来确定删除。

### Common states

下列是常用 states 的列表。确定 state 名称时 APIs **should** 考虑先例，并且在先例冲突时 **should** 把局部一致性置于全局一致性之上。

#### Resting states

「Resting states」是生命周期 states：在没有用户动作时，预期无限期保持。然而，用户可以发起动作，把处于 resting state 的资源移入某些其它 states（resting 或 active）。

- `ACCEPTED`
- `ACTIVE`
- `CANCELLED`
- `DELETED`
- `FAILED`
- `SUCCEEDED`
- `SUSPENDED`
- `VERIFIED`

#### Active states

「Active states」是通常自行解析为单个预期 resting state 的生命周期 states。

**Note:** 记住只暴露对客户有用的 states。仅当资源将在该 state 中停留足够长时间时，Active states 才有价值。若 state 变更是立即的，则不需要 active states。

- `CREATING`（通常变为 `ACTIVE`）
- `DELETING`（通常变为 `DELETED`）
- `PENDING`（通常变为 `RUNNING`）
- `REPAIRING`（通常变为 `ACTIVE`）
- `RUNNING`（通常变为 `SUCCEEDED`）
- `SUSPENDING`（通常变为 `SUSPENDED`）
