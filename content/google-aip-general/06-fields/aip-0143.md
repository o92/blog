口语、国家、货币这类概念，书面上常常有好几种写法："United States" 和 "USA"，"Español" 和 "Spanish"。数据交换时这就变成对不上的字符串。常见做法是用一套标准化代码（多半由 [International Organization for Standardization](https://www.iso.org/) 正式化）。这篇约定：有通行标准就用标准，字段名也跟着标准走。

## 有标准就用标准

对存在标准化代码、而且普遍在用的概念，表示这些概念的字段应当在输入和输出上都用标准化代码。

```proto
// A message representing a book.
message Book {
  // Other fields...

  // The IETF BCP-47 language code representing the language in which
  // the book was originally written.
  // https://en.wikipedia.org/wiki/IETF_language_tag
  string language_code = 99;
}
```

- 表示标准化概念的字段必须用该标准代码的适当数据类型（通常是 `string`）。
  - 不应当用 enum，哪怕实际只允许一小部分值。多个 API 一起用时，enum 常常变成令人沮丧的对照表。
  - 必须写明遵循哪份标准，最好带链接（标准原文、Wikipedia，或类似出处）。
- 除非这个概念有明显更清楚的后缀，字段名应当以 `_code` 或 `_type` 结尾。
- 接受用户提供的值时，校验应当大小写不敏感，除非不敏感会引入歧义（例如同时接受 `en-gb` 与 `en-GB`）。向用户给出值时，API 应当用规范大小写（上例是 `en-GB`）。

### 内容类型

表示内容或媒体类型的字段必须用 [IANA media types](https://www.iana.org/assignments/media-types/media-types.xhtml)。出于遗留原因，字段应当叫 `mime_type`。

### 国家与地区

表示个别国家或民族的字段必须用 [Unicode CLDR region codes](http://cldr.unicode.org/)（[列表](https://www.unicode.org/cldr/charts/46/supplemental/territory_information.html)），例如 `US`、`CH`，并且字段必须叫 `region_code`。

为何不用 `country_code`，见[下文](#为何叫-region_code)。

### 货币

表示货币的字段必须用 [ISO-4217 currency codes](https://en.wikipedia.org/wiki/ISO_4217)，例如 `USD`、`CHF`，并且字段必须叫 `currency_code`。

要表示某种货币里的金额，而不是货币代码本身，用 [`google.type.Money`](https://github.com/googleapis/googleapis/blob/master/google/type/money.proto)。

### 语言

表示口语的字段必须用 [IETF BCP-47 language codes](https://en.wikipedia.org/wiki/IETF_language_tag)（[列表](https://www.unicode.org/cldr/charts/46/supplemental/territory_information.html)），例如 `en-US`、`de-CH`，并且字段必须叫 `language_code`。

### 时区

表示时区的字段应当用 [IANA TZ](http://www.iana.org/time-zones) 代码，并且字段必须叫 `time_zone`。

字段也可以表示 UTC 偏移而不是时区（二者有细微差别）。这时必须用 [ISO-8601 格式](https://en.wikipedia.org/wiki/ISO_8601#Time_offsets_from_UTC)，并且字段必须叫 `utc_offset`。

## 为何叫 region_code

用 `region_code` 而不是 `country_code`，是为了能表达并非国家的地区，也避免跟主权、归属绑在一起的政治争议。Google 和许多公司是 Unicode CLDR 的支持者，产品国际化已经对齐到 CLDR，API 不必另搞一套。CLDR 支持的许多值本身也不是国家，用更通用的名字反而更贴这份规范。
