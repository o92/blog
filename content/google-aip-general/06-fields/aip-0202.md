字段除了名字和类型，有时还需要标明「这个 `string` 其实是 UUID」或「这个 `string` 是 IPv6」。[`google.api.FieldInfo`](https://github.com/googleapis/googleapis/blob/master/google/api/field_info.proto) 通过扩展 `google.api.field_info`，把这类格式信息挂到字段 schema 上。没被要求时不要随手加。

## 只在被要求时标注

仅当本文或另一篇利用 `google.api.FieldInfo` 的 AIP 明确要求时，才需要用 `google.api.field_info` 装饰字段。因此下面的指导也适用于那些场景。

### Format

原始类型的字段仍可以有特定格式。要传达这个格式，通过 `(google.api.field_info).format` 使用 `FieldInfo.Format` 枚举。下面说明每个 `FieldInfo.Format` 值的含义和使用要求。

#### UUID4

`UUID4` 表示受 [RFC 4122](https://datatracker.ietf.org/doc/html/rfc4122) 管辖的 UUID 第 4 版。它必须只用于类型为 `string` 的字段。

服务可以把这类值规范化为全小写。例如 `F47AC10B-58CC-0372-8567-0E02B2C3D479` 会变成 `f47ac10b-58cc-0372-8567-0e02b2c3d479`。

因此，等价比较不得靠原始文本比较。必须用符合 [RFC 4122](https://datatracker.ietf.org/doc/html/rfc4122) 的实现。

#### IPv4

`IPV4` 表示受 [RFC 791](https://datatracker.ietf.org/doc/html/rfc791) 管辖的 IPv4 地址。它必须只用于类型为 `string` 的字段。

服务可以压缩这类值，剥掉每个八位组里的前导零。例如 `001.022.233.040` 会变成 `1.22.233.40`。

因此，等价比较不得靠原始文本比较。必须用符合 [RFC 791](https://datatracker.ietf.org/doc/html/rfc791) 的实现。

#### IPv6

`IPV6` 表示受 [RFC 4291](https://datatracker.ietf.org/doc/html/rfc4291#section-2.2) 管辖的 IPv6 地址。它必须只用于类型为 `string` 的字段。

服务可以把这类值规范化为全小写并压缩零，遵循 [RFC 5952](https://datatracker.ietf.org/doc/html/rfc5952)。例如 `2001:0DB8:0::0` 会变成 `2001:db8::`。

因此，等价比较不得靠原始文本比较。必须用符合 [RFC 4291](https://datatracker.ietf.org/doc/html/rfc4291#section-2.2) 的实现。

#### IPv4 or IPv6

`IPV4_OR_IPV6` 表示该字段可以是 IPv4 或 IPv6 地址，规则见上面 [IPv4](#ipv4) 与 [IPv6](#ipv6) 两节。

#### 格式兼容性

向现有、尚未标明格式的字段添加格式说明符，**不是**向后兼容的——除非该字段一直就符合正在标明的那种格式。

把现有格式说明符改成另一个，在任何情形下都**不是**向后兼容的。

#### 扩展 Format

任何新的 `FieldInfo.Format` 值必须受 [IETF 批准的 RFC](https://www.ietf.org/standards/rfcs) 或 Google 批准的 AIP（见 [AIP-1]({{< ref "aip-0001" >}})）管辖。

## 理由

### 为何要加 format

原始类型字段的格式对可用性可能至关重要。某些编程语言会把特定格式当成独立类型，例如 Java 的 [UUID](https://docs.oracle.com/javase/8/docs/api/java/util/UUID.html)。大多数格式都有服务要校验的结构要求。提前告诉用户是什么格式，体验会好很多。

### 为何不鼓励原始相等比较

受支持格式的文本表示有许多细微差别，转成规范表示并不 trivial。因此，指望每个消费者和每个服务都对齐实现，并不现实。

### 为何要写清规范化

尽管任何受支持格式都不推荐原始比较，值怎么规范化仍要统一：设定消费者预期，也让表面更好用。

### 为何新格式必须有 RFC 或 AIP

那些足够标准化、值得一篇 RFC 或 AIP 的格式，才稳定、才广为人知，适合作为受支持值出现在 Google APIs 里。要求这类额外指导，意味着格式规范本身不由 `FieldInfo.Format` 枚举来管辖。
