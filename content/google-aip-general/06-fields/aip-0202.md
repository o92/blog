[`google.api.FieldInfo`](https://github.com/googleapis/googleapis/blob/master/google/api/field_info.proto) 类型通过伴随的扩展 `google.api.field_info`，在基本的名称与类型信息之外丰富字段的 schema。

## Guidance

仅当本文或另一篇利用 `google.api.FieldInfo` 信息的 AIP 明确要求时，才需要用 `google.api.field_info` 装饰字段。因此，此处指导也适用于那些场景。

### Format

原始类型的字段仍可以有特定格式。为传达该类型格式，通过 `(google.api.field_info).format` 扩展字段使用 `FieldInfo.Format` 枚举。下列指导传达每个 `FieldInfo.Format` 值的含义与使用要求。

#### UUID4

`UUID4` 格式表示受 [RFC 4122](https://datatracker.ietf.org/doc/html/rfc4122) 管辖的 UUID 第 4 版值。它 **must** 仅用于类型为 `string` 的字段。

此类值 **may** 由服务规范化为全小写字母。例如，值 `F47AC10B-58CC-0372-8567-0E02B2C3D479` 会规范化为 `f47ac10b-58cc-0372-8567-0e02b2c3d479`。

因此，等价比较 **must not** 通过原始文本比较完成。相反，**must** 使用符合 [RFC 4122](https://datatracker.ietf.org/doc/html/rfc4122) 的实现。

#### IPv4

`IPV4` 格式表示受 [RFC 791](https://datatracker.ietf.org/doc/html/rfc791) 管辖的 IP v4 地址。它 **must** 仅用于类型为 `string` 的字段。

此类值 **may** 由服务压缩，剥掉每个八位组中的前导零。例如，`001.022.233.040` 会压缩为 `1.22.233.40`。

因此，等价比较 **must not** 通过原始文本比较完成。相反，**must** 使用符合 [RFC 791](https://datatracker.ietf.org/doc/html/rfc791) 的实现。

#### IPv6

`IPV6` 格式表示受 [RFC 4291](https://datatracker.ietf.org/doc/html/rfc4291#section-2.2) 管辖的 IP v6 地址。它 **must** 仅用于类型为 `string` 的字段。

此类值 **may** 由服务规范化为全小写字母并压缩零，遵循 [RFC 5952](https://datatracker.ietf.org/doc/html/rfc5952)。例如，值 `2001:0DB8:0::0` 会规范化为 `2001:db8::`。

因此，等价比较 **must not** 通过原始文本比较完成。相反，**must** 使用符合 [RFC 4291](https://datatracker.ietf.org/doc/html/rfc4291#section-2.2) 的实现。

#### IPv4 or IPv6

`IPV4_OR_IPV6` 值表示该字段可以是 IP v4 或 v6 地址，如 [IPv4](#ipv4) 与 [IPv6](#ipv6) 两节所述。

#### Format Compatibility

向现有、未指定的字段添加格式说明符 **不是** 向后兼容的，*除非* 所讨论字段一直符合正在指定的格式。

在所有情形下把现有格式说明符改为另一个 **不是** 向后兼容的。

#### Extending Format

任何新的 `FieldInfo.Format` 值 **must** 受 [IETF 批准的 RFC](https://www.ietf.org/standards/rfcs) 或 Google 批准的 AIP（[AIP-1]({{< ref "aip-0001" >}})）管辖。

## Rationale

#### Why add a format specifier?

原始类型字段的格式对其可用性可能至关重要。某些编程语言可能把特定类型格式作为独立类型传达，例如 Java 对 [UUID](https://docs.oracle.com/javase/8/docs/api/java/util/UUID.html) 所做的。大多数都有由服务验证的特定结构要求，因此提前向用户传达格式对其体验至关重要。

#### Why discourage primitive equality comparisons?

受支持格式的文本表示有许多细微差别，把值转换为规范表示并非 trivial。因此，在每个消费者与每个服务之间无问题地对齐实现是不可行的。

#### Why document value normalizations?

尽管对任何受支持格式都不推荐原始比较，值的统一规范化对于设定消费者期望、创建用户友好的表面很重要。

#### Why require an RFC or AIP for new formats?

那些足够标准化、值得一篇 RFC 或 AIP 的格式，足够稳定且广为人知，可以作为受支持值纳入并在 Google APIs 中看到使用。要求此类额外指导意味着管辖格式规范不是 `FieldInfo.Format` 枚举本身的责任。
