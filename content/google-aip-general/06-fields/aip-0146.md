API 里大多数字段都有确定的类型或 schema，无论在请求、资源还是自定义响应里。这份 schema 就是开发者写代码时依赖的契约。

偶尔才适合放一个通用或多态字段：能符合多种 schema，甚至完全自由形式。能用更具体的办法时，不要一上来就 Any。

## 尽量选「最不通用」的办法

通用字段一般很少见。必要时服务可以引入。字段要多通用，办法就不一样。总原则：服务应当选能覆盖用例、同时「最不通用」的那一种。

### oneof

`oneof` 可以引入类型联合：用户或服务只能填其中某一个字段。也可以把同一类型（通常是字符串）放进 `oneof`，用来区分选项之间的语义差别。

`oneof` 里每个字段键不同，开发者可以程序化地判断填了哪一个（如果有的话）。

`oneof` 给每个选项留下最多的类型安全和语义。可行时，服务应当优先用它，而不是更泛的多态办法。但潜在选项很多（或无限），或者大型资源结构需要一长串「级联 oneofs」时，这个构造不合适。

向现有 `oneof` 加新的可选字段是非破坏性变更。把现有字段移进或移出 `oneof` 是破坏性的：Go protobuf stubs 会向后不兼容。

### Maps

需要**同一类型**的许多值，但键事先不知道、或由用户决定时，可以用 map。

Map 通常不适合当通用字段，因为值都共享一个类型。偶尔仍有用。尤其是：需要许多同一类型的对象，并且按键名有不同行为（例如键当环境名）时，map 有时合适。

### Struct

[`google.protobuf.Struct`](https://github.com/protocolbuffers/protobuf/tree/master/src/google/protobuf/struct.proto) 可以表示任意嵌套 JSON。键是字符串；值可以是浮点、字符串、布尔、数组，或再嵌一层 struct。于是任意能写成 JSON 的结构都可以表达（走 REST/JSON 时会自动变成 JSON）。

服务事先不知道 schema，或需要存取任意但结构化的用户数据时，`Struct` 最有用。对用户也方便：很容易拿到能在所选环境里原生操作的 JSON 对象。

服务若还要推理这个 `Struct` 的 *schema*，应当用 [JSONSchema](https://json-schema.org/)。JSONSchema 本身就是 JSON，一份有效的 JSONSchema 文档也可以存在 `Struct` 里。

### Any

[`google.protobuf.Any`](https://github.com/protocolbuffers/protobuf/tree/master/src/google/protobuf/any.proto) 可以发送任意序列化的 protocol buffer，并带上类型定义。

但这会引入复杂度。消费者若拿不到那份 proto，`Any` 除了盲目转发数据以外几乎没用。即使消费者**有**那份 proto，也必须先注册类型再手动反序列化，这个过程常常不熟。

因此，除非其它选项都行不通，不应当用 `Any`。
