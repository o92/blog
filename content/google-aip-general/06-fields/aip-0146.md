任何 API 中的大多数字段，无论在请求、资源还是自定义响应中，都有特定类型或 schema。此 schema 是开发者据以编写代码的契约的一部分。

然而，偶尔适合有某种通用或多态字段，可以符合多种 schemata，甚至完全是自由形式。

## Guidance

尽管通用字段一般很少见，必要时服务 **may** 引入通用字段。根据字段需要多通用，有几种方法；一般而言，服务 **should** 尝试引入能够满足用例的「最不通用」的方法。

### Oneof

`oneof` **may** 用于引入类型联合：用户或服务能够指定 `oneof` 内的字段之一。此外，`oneof` **may** 与同一类型（通常是字符串）一起使用，以表示选项之间的语义差异。

因为 `oneof` 中的个别字段有不同的键，开发者可以程序化地确定哪些（若有）字段已填充。

`oneof` 为每个选项保留最大程度的类型安全与语义含义，可行时服务 **should** 一般优先于其它通用或多态选项使用它们。然而，当潜在选项数量很大（或无限），或当有需要一长串「级联 oneofs」的大型资源结构时，`oneof` 构造不合适。

**Note:** 向现有 `oneof` 添加额外可能字段是非破坏性变更，但把现有字段移入或移出 `oneof` 是破坏性的（它会在 Go protobuf stubs 中造成向后不兼容变更）。

### Maps

当需要*同一类型*的许多值，但键未知或由用户决定时，**may** 使用 Maps。

Maps 通常不适合通用字段，因为 map 值都共享一个类型，但偶尔它们有用。特别地，当需要许多同一类型的对象、且基于其键名有不同行为时（例如用键作为环境名），map 有时适合。

### Struct

[`google.protobuf.Struct`](https://github.com/protocolbuffers/protobuf/tree/master/src/google/protobuf/struct.proto) 对象 **may** 用于表示任意嵌套 JSON。键可以是字符串，值可以是浮点、字符串、布尔、数组或额外的嵌套 structs，从而允许任意嵌套、可表示为 JSON 的结构（使用 REST/JSON 时会自动表示为 JSON）。

当服务事先不知道 schema，或当服务需要存储并检索任意但结构化的用户数据时，`Struct` 最有用。此时使用 `Struct` 对用户方便，因为他们可以轻松得到能在所选环境中原生操作的 JSON 对象。

若服务需要推理 `Struct` 的 *schema*，它 **should** 为此使用 [JSONSchema](https://json-schema.org/)。因为 JSONSchema 本身就是 JSON，有效的 JSONSchema 文档本身可以存储在 `Struct` 中。

### Any

[`google.protobuf.Any`](https://github.com/protocolbuffers/protobuf/tree/master/src/google/protobuf/any.proto) 对象可用于发送任意序列化的 protocol buffer 与类型定义。

然而，这会引入复杂度，因为若消费者无法访问该 proto，`Any` 对除盲目数据传播以外的任何任务都变得无用。此外，即使消费者*确实*有该 proto，消费者也必须确保类型已注册然后手动反序列化，这常常是不熟悉的过程。

因此，除非其它选项不可行，`Any` **should not** 被使用。
