**英文标题**：Field names

字段名要让读者一眼看懂，这件事往往比看起来难。作者觉得直观的名字，读者可能一头雾水。用户也很少只用一个 API：多个 API 一起用时，同一件事换了名字、或同一个名字指了两件不同的事，学过的知识就带不过去。

字段名简单、直观、彼此一致，API 才好懂。

## 怎么起名

字段名应当用正确的美式英语。

名字应当把概念说清楚，避免笼统含糊。同时也不要堆多余的词。尤其别加那种「永远成立、几乎不加信息」的形容词。例如没有「未共享」的变体时，`proxy_settings` 就够了，不必写成 `shared_proxy_settings`。

字段名会出现在生成的客户端表面上。描述要够，长度也要合适。

### 大小写

protobuf 里的字段定义必须用 `lower_snake_case`。它们会映射到 JSON 和生成代码里各自的命名约定。

每个词不得以数字开头：snake case 和 camel case 互转时会歧义。同样，不得有前导、尾随或相邻的下划线。

### 跨 API 统一

同一概念应当用同一个名字，不同概念应当用不同名字。跨多个 API 也一样，尤其是很可能一起用的那些。

### Repeated 字段

Repeated 字段必须用正确的复数，例如 `books`、`authors`。非 repeated 字段应当用单数，例如 `book`、`author`。资源名字段也应当用单数，因为字段名跟着资源名走（例如 `repeated Book books`，**不是** `Books books = 1`）。

### 介词

字段名不应当含介词（with、for、at、by 等）。例如：

- `error_reason`（**不是** `reason_for_error`）
- `author`（**不是** `written_by`）

这样名字更容易对得上。介词有时也在暗示设计问题：字段太窄，或类型选得不好。尤其是 with：`book_with_publisher` 多半说明 book 的结构不对，值得重想。

单词 per 是例外。它作为单位的一部分时（例如 miles per hour），见 [AIP-141]({{< ref "aip-0141" >}})。

### 缩写

软件开发者都认识的缩写，例如 config、spec，API 定义里应当用缩写，不要写全称。源码更好读。例如：

- `config`（**不是** `configuration`）
- `id`（**不是** `identifier`）
- `info`（**不是** `information`）
- `spec`（**不是** `specification`）
- `stats`（**不是** `statistics`）

众所周知的单位缩写也应当用。表示数量的字段见 [AIP-141]({{< ref "aip-0141" >}})。例如：

- `distance_km`（**不是** `distance_kilometers`）
- `width_px`（**不是** `width_pixels`）

### 形容词

名词和形容词一起出现时，应当把形容词放在名词之前。例如：

- `collected_items`（**不是** `items_collected`）
- `imported_objects`（**不是** `objects_imported`）

### 动词

字段名不得反映意图或动作，不得是动词。Create 与 Update 里字段表示期望值，Get 与 List 里表示当前值，所以名字必须是名词：说它是什么，不说做什么。

- `collected_items`（**不是** `collect_items`）
- `disabled`（**不是** `disable`）

方法名则相反：标准方法或 custom method 都会改变资源，所以用动词。

### 布尔

布尔字段应当省略前缀 is。例如：

- `disabled`（**不是** `is_disabled`）
- `required`（**不是** `is_required`）

否则会撞上[保留字](#保留字)的名字是例外。例如用 `is_new`，**不是** `new`。

### string 与 bytes

`bytes` 在 JSON 线上会做 base64 编码。要在线上发二进制时，服务应当用 `bytes`，不应当要求用户先手动 base64 再塞进 `string`。例外：API 处理的数据本身就打算以 base64 存在静态存储里，再用 `bytes` 会造成双重编码，这时服务可以用 `string`。

### URI

表示任意 URI 的字段名应当用 `uri`。URL 都是 URI，但并非所有 URI 都是 URL。

`uri` 前面可以加适当前缀。

只能表示 URL 的字段名应当用 `url`。

```proto
message Book {
  string name = 1 [(google.api.field_behavior) = IDENTIFIER];

  // A URL pointing to an image of the book.
  string image_url = 2;

  // A URI identifying the book.
  // This could be an ISBN or a URL.
  string uri = 3;
}
```

先前已经对 URL 字段用了 `uri` 的 API 可以继续用，避免没必要的破坏，也保持局部一致。

### 保留字

字段名应当避开很可能跟常见编程语言关键字冲突的名字，例如 `new`、`class`、`function`、`import`。保留字会让用该语言的开发者难受。

### 与 message 重名

Message 不应当包含与包围它的 message 同名的字段（忽略大小写）。某些语言生成代码时会冲突。

### display_name

许多资源有给人看的名字，常出现在 UI 里。这个字段应当叫 `display_name`，并且不应当要求唯一。

实体若有官方正式名称（公司名、书名），API 可以改用 `title`。`title` 也不应当要求唯一。

## 为何偏 URI 而不是 URL

指导本身已经说了：URL 都是 URI，但并非所有 URI 都是 URL。对齐到 URI，是为了字段能覆盖更多用例，也推动跨 API 统一。这条是「应当」，真正值得更具体时，仍可以用更窄的词。
