**英文标题**：Field names  
**原文**：[AIP-140](https://google.aip.dev/140) · approved · 创建 2019-07-22  
**许可**：原文 © Google，[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)

以对用户直观的方式命名字段，往往是设计 API 最具挑战的方面之一。原因很多；作者觉得完全直观的字段名，读者却可能一头雾水。

此外，用户很少只用一个 API；他们会把多个 APIs 一起用。因此，同一家公司用同一名称表示不同事物（或用不同名称表示同一事物）常常造成不必要的困惑，因为用户无法再把从一个 API 学到的知识应用到另一个。

简而言之，当字段名简单、直观、彼此一致时，APIs 最容易理解。

## Guidance

字段名 **should** 使用正确的美式英语。

字段名 **should** 清楚、精确地传达所呈现的概念，并避免过于笼统、含糊的名称。话虽如此，字段名 **should** 避免包含不必要的词。尤其要避免总是适用、几乎不增加认知价值的形容词。例如，若不存在未共享的变体，`proxy_settings` 可能与 `shared_proxy_settings` 同样有用。

**Important:** 字段名常出现在生成的客户端表面上。确保它们描述充分、长度合适。

### Case

protobuf 文件中的字段定义 **must** 使用 `lower_snake_case` 名称。这些名称会映射到 JSON 与生成代码中的适当命名约定。

此外，字段中的每个词 **must not** 以数字开头，因为在 snake case 与 camel case 之间转换时会造成歧义。类似地，字段 **must not** 包含前导、尾随或相邻的下划线。

### Uniformity

APIs **should** 尽可能对同一概念使用同一名称、对不同概念使用不同名称。这包括跨多个 APIs 的名称，尤其当这些 APIs 很可能一起使用时。

### Repeated fields

Repeated 字段 **must** 使用正确的复数形式，例如 `books` 或 `authors`。另一方面，非 repeated 字段 **should** 使用单数形式，例如 `book` 或 `author`。这意味着 resource names **should** 也使用单数形式，因为字段名应跟随资源名（例如使用 `repeated Book books`，**不是** `Books books = 1`）。

### Prepositions

字段名 **should not** 包含介词（如 "with"、"for"、"at"、"by" 等）。例如：

- `error_reason`（**不是** `reason_for_error`）
- `author`（**不是** `written_by`）

遵循此约定时，字段名更容易经常匹配。此外，字段名中的介词也可能表明设计问题，例如过于受限的字段或次优的数据类型。这对 "with" 尤其如此：名为 `book_with_publisher` 的字段很可能表明 book 资源结构不当，值得重新设计。

**Note:** 单词 "per" 是此规则的例外。当 "per" 作为单位的一部分使用时（例如 "miles per hour"），见 [AIP-141]({{< ref "aip-0141" >}}) 的指导。

### Abbreviations

对软件开发者中众所周知的名称缩写，例如 "config" 与 "spec"，API 定义中 **should** 使用缩写而不是完整拼写。这会让源代码易于读写。例如：

- `config`（**不是** `configuration`）
- `id`（**不是** `identifier`）
- `info`（**不是** `information`）
- `spec`（**不是** `specification`）
- `stats`（**不是** `statistics`）

此外，字段名中 **should** 使用众所周知的单位缩写。表示数量的字段见 [AIP-141]({{< ref "aip-0141" >}})。例如：

- `distance_km`（**不是** `distance_kilometers`）
- `width_px`（**不是** `width_pixels`）

### Adjectives

为求统一，同时包含名词与形容词的字段名 **should** 把形容词放在名词*之前*。例如：

- `collected_items`（**不是** `items_collected`）
- `imported_objects`（**不是** `objects_imported`）

### Verbs

字段名 **must not** 命名为反映意图或动作。它们 **must not** 是动词。相反，因为字段在变更（例如 Create 与 Update）中定义*期望值*，在读取（例如 Get 与 List）中定义*当前值*，名称 **must** 是名词。它定义是什么，而不是做什么。

- `collected_items`（**不是** `collect_items`）
- `disabled`（**不是** `disable`）

相比之下，方法名无论标准还是自定义，都会改变资源的面向，并命名为动词。

### Booleans

布尔字段 **should** 省略前缀 "is"。例如：

- `disabled`（**不是** `is_disabled`）
- `required`（**不是** `is_required`）

**Note:** 否则会是 [保留字](#reserved-words) 的字段名是此规则的例外。例如，`is_new`（**不是** `new`）。

### String vs. bytes

使用 `bytes` 时，字段内容在 JSON 线上会做 base64 编码。当需要在线上发送二进制内容时，服务 **should** 使用 `bytes`，并且 **should not** 要求用户把字段手动 base64 编码进 `string` 字段。一个例外是：API 设计为处理本意在静态存储时做 base64 编码的数据，且使用 `bytes` 导致的双重 base64 编码不可取——此时服务 **may** 使用 `string`。

### URIs

表示任意 URIs 的字段名 **should** 使用 `uri`。特别地，注意 URLs 都是 URIs，但并非所有 URIs 都是 URLs。

字段名 **may** 在 `uri` 前使用适当前缀。

只能表示 URL 的字段名 **should** 使用 `url`。

```proto
message Book {
  string name = 1 [(google.api.field_behavior) = IDENTIFIER];

  // A URL pointing to an image of the book.
  string image_url = 2;

  // A URI identifying the book.
  // This could be an ISBN or a URL.
  string uri = 3;
}
```

**Note:** 先前已对 URL 字段使用 `uri` 的 APIs 可以继续这样做，以避免不必要的 API 变更并保持局部一致性。

### Reserved words

字段名 **should** 避免使用很可能与常见编程语言关键字冲突的名称，例如 `new`、`class`、`function`、`import` 等。保留关键字会给用该语言使用 API 的开发者带来困难。

### Conflicts

Messages **should not** 包含与包围 message 同名的字段（忽略大小写转换）。这会在某些语言生成代码时造成冲突。

### Display names

许多资源有人类可读的名称，常用于 UI 展示。此字段 **should** 称为 `display_name`，并且 **should not** 有唯一性要求。

若实体有官方、正式名称（例如公司名或书名），API **may** 改用 `title` 作为字段名。`title` 字段 **should not** 有唯一性要求。

## Rationale

### URI vs URL

指导本身提到所有 URLs 都是 URIs，但并非所有 URIs 都是 URLs。对齐到 URI 的目标是启用更可泛化的字段，能处理多种用例，并推动跨 APIs 的标准化，形成更连贯的表面。同时，要求是 **should**，在真正值得时允许使用更具体的术语。
