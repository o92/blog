用户进不了实现里去「再理解一下」。他们手里常常只有 API 表面定义和对应文档。所以注释要尽量清楚、完整、无歧义。这篇规定 proto 注释怎么写、能用什么格式、弃用时第一行写什么。

## 每处都要有公开注释

在用 protocol buffers 定义的 APIs 中，必须用 protocol buffers 注释格式，在每个组件（service、method、message、field、enum 与 enum value）之上包含公开注释。即使注释短、看起来没意思，这也很重要：大量工具会读这些注释并拿来用。

服务尤其应当有描述性注释，解释该服务是什么、用户能用它做什么。

许多读者不会是英语母语者。注释应当避免行话、俚语、复杂隐喻、流行文化引用，或任何其它不容易翻译的内容。此外，许多读者会有不同背景与观点；若写涉及人物的示例，注释应当使用无争议且已不在世的人物。

### 文体

注释应当使用语法正确的美式英语。然而，每条注释的第一句应当省略主语，并用第三人称现在时：

```proto
// Creates a book under the given publisher.
rpc CreateBook(CreateBookRequest) returns (Book) {
  option (google.api.http) = {
    post: "/v1/{parent=publishers/*}/books"
    body: "book"
  };
}
```

### 描述写什么

messages 与 fields 的描述应当短但完整。有时注释必然敷衍，因为没什么可说。但在跳到该结论之前，考虑下列问题是否相关：

- 它是什么？
- 你如何使用它？
- 成功时它做什么？失败时它做什么？
- 它是否幂等？
- 单位是什么？（示例：meters、degrees、pixels）
- 副作用是什么？
- 可能破坏它的常见错误是什么？
  - 期望的输入格式是什么？
  - 它接受什么值范围？（示例：`[0.0, 1.0)`、`[1, 10]`）
  - 该范围是包含还是排除？
  - 对字符串，最小与最大长度是什么，允许哪些字符？
  - 若值超过最大长度，你截断还是发送错误？
- 它是否始终存在？（示例："Container for voting information. Present only when voting information is recorded."）
- 它是否有默认设置？（示例："If `page_size` is omitted, the default is 50."）

### 格式

注释中的任何格式必须使用 [CommonMark](https://commonmark.org/)。不得使用标题与表格：这些会给若干工具带来问题，且不适合客户端库参考文档。

注释应当对字段或方法名以及字面量（例如 `true`）使用 `code font`。

不得使用原始 HTML。

不得使用「ASCII art」试图在 protos 内呈现图表。protos 内的 Markdown 会被大量渲染器消费，任何 ASCII art 都极不可能被所有渲染器很好地呈现。若图表对理解 API 有用，包含指向含该图表作为图像的文档页的链接。

### 交叉引用

注释可以「链接」到另一个组件（service、method、message、field、enum 或 enum value）作为 Markdown 引用链接。引用必须为下列形式之一：

- 元素的完全限定名，例如 `[Book][google.example.v1.Book]`
- 相对作用域限定的引用，例如 `[Sci-Fi genre][Genre.GENRE_SCI_FI]`
- 隐含引用，例如 `[Book][]`，等价于 `[Book][Book]`

这些引用按 [name resolution](https://protobuf.dev/programming-guides/proto3/#name-resolution) 规则解析。

引用中不得使用包含字段的名称。它们不会解析。必须改为引用原始定义。例如，`[author][Book.author.family_name]` 其中 `author` 是 `Book` 的字段，将不会解析，但 `[author][Author.family_name]` 会。

### 外链

注释可以链接到外部页面，提供超出公开注释本身所描述的背景信息。外链必须使用绝对（而非相对）URLs，包括协议（通常是 `https`），并且不应当假定文档位于任何特定主机上。例如：
`[Spanner Documentation](https://cloud.google.com/spanner/docs)`

### 商标名称

在注释中提及公司或产品的专有、商标名称时，不应当使用缩写，除非该缩写在口语中如此主导，以至于避免它会模糊引用（示例：[IBM](https://en.wikipedia.org/wiki/IBM)）。

注释应当按商标所有者当前品牌拼写并大写商标名称。

### 弃用

要弃用一个组件（service、method、message、field、enum 或 enum value），必须把 `deprecated` [option](https://developers.google.com/protocol-buffers/docs/proto#options) 设为 `true`，并且相应注释的第一行必须以 `"Deprecated: "` 开头，并提供给开发者的替代方案。若没有替代方案，必须给出弃用原因。

### 内部注释

注释可以通过把内部内容包在 `(--` 与 `--)` 中来显式标为内部。

非公开链接、内部实现注释（例如 `TODO` 与 `FIXME` 指令）以及其它此类材料必须标为内部。

注释应当只使用前导注释（不是尾随注释或分离注释）。特别地，注释不得同时使用前导与尾随注释来描述任何组件：这是内部内容注解无意遗漏的常见来源。
