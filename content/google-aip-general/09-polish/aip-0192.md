文档是 API 设计最关键的方面之一。你的 API 用户无法深入实现来更好地理解 API；常常，API 表面定义及其对应文档将是用户拥有的仅有东西。因此，文档尽可能清晰、完整、无歧义很重要。

## Guidance

在用 protocol buffers 定义的 APIs 中，**must** 用 protocol buffers 注释格式在每个组件（service、method、message、field、enum 与 enum value）之上包含公开注释。即使注释简短且无趣，这也很重要，因为大量工具会读取这些注释并使用它们。

服务尤其 **should** 有描述性注释，解释该服务是什么以及用户能用它做什么。

**Note:** 许多读者不会是英语母语者。注释 **should** 避免行话、俚语、复杂隐喻、流行文化引用，或任何其它不容易翻译的内容。此外，许多读者会有不同背景与观点；若写涉及人物的示例，注释 **should** 使用无争议且已不在世的人物。

### Style

注释 **should** 使用语法正确的美式英语。然而，每条注释的第一句 **should** 省略主语并以第三人称现在时：

```proto
// Creates a book under the given publisher.
rpc CreateBook(CreateBookRequest) returns (Book) {
  option (google.api.http) = {
    post: "/v1/{parent=publishers/*}/books"
    body: "book"
  };
}
```

### Descriptions

messages 与 fields 的描述 **should** 简短但完整。有时注释必然敷衍，因为没什么可说；然而，在跳到该结论之前，考虑下列问题是否相关：

- 它是什么？
- 你如何使用它？
- 成功时它做什么？失败时它做什么？
- 它是否幂等？
- 单位是什么？（示例：meters、degrees、pixels）
- 副作用是什么？
- 可能破坏它的常见错误是什么？
  - 期望的输入格式是什么？
  - 它接受什么值范围？（示例：`[0.0, 1.0)`、`[1, 10]`）
  - 该范围是包含还是排除？
  - 对字符串，最小与最大长度是什么，允许哪些字符？
  - 若值超过最大长度，你截断还是发送错误？
- 它是否始终存在？（示例："Container for voting information. Present only when voting information is recorded."）
- 它是否有默认设置？（示例："If `page_size` is omitted, the default is 50."）

### Formatting

注释中的任何格式 **must** 使用 [CommonMark](https://commonmark.org/)。**must not** 使用标题与表格，因为这些会给若干工具带来问题，且不适合客户端库参考文档。

注释 **should** 对字段或方法名以及字面量（例如 `true`）使用 `code font`。

**must not** 使用原始 HTML。

**must not** 使用「ASCII art」试图在 protos 内呈现图表。protos 内的 Markdown 会被大量渲染器消费，任何 ASCII art 都极不可能被所有渲染器很好地呈现。若图表对理解 API 有用，包含指向含该图表作为图像的文档页的链接。

### Cross-references

注释可以「链接」到另一个组件（service、method、message、field、enum 或 enum value）作为 Markdown 引用链接。引用 **must** 为下列形式之一：

- 元素的完全限定名，例如 `[Book][google.example.v1.Book]`
- 相对作用域限定的引用，例如 `[Sci-Fi genre][Genre.GENRE_SCI_FI]`
- 隐含引用，例如 `[Book][]`，等价于 `[Book][Book]`

这些引用按 [name resolution](https://protobuf.dev/programming-guides/proto3/#name-resolution) 规则解析。

引用中 **must not** 使用包含字段的名称。它们不会解析。**must** 改为引用原始定义。例如，`[author][Book.author.family_name]` 其中 `author` 是 `Book` 的字段，将不会解析，但 `[author][Author.family_name]` 会。

### External links

注释 **may** 链接到外部页面以提供超出公开注释本身所描述的背景信息。外部链接 **must** 使用绝对（而非相对）URLs，包括协议（通常是 `https`），并且 **should not** 假定文档位于任何特定主机上。例如：
`[Spanner Documentation](https://cloud.google.com/spanner/docs)`

### Trademarked names

在注释中提及公司或产品的专有、商标名称时，**should not** 使用缩写，除非该缩写在口语中如此主导，以至于避免它会模糊引用（示例：[IBM](https://en.wikipedia.org/wiki/IBM)）。

注释 **should** 按商标所有者当前品牌拼写并大写商标名称。

### Deprecations

要弃用一个组件（service、method、message、field、enum 或 enum value），**must** 把 `deprecated` [option](https://developers.google.com/protocol-buffers/docs/proto#options) 设为 `true`，并且相应注释的第一行 **must** 以 `"Deprecated: "` 开头并提供给开发者的替代方案。若没有替代方案，**must** 给出弃用原因。

### Internal comments

注释 **may** 通过把内部内容包在 `(--` 与 `--)` 中来显式标为内部。

非公开链接、内部实现注释（例如 `TODO` 与 `FIXME` 指令）以及其它此类材料 **must** 标为内部。

**Note:** 注释 **should** 只使用前导注释（不是尾随注释或分离注释）。特别地，注释 **must not** 同时使用前导与尾随注释来描述任何组件，因为这是内部内容注解无意遗漏的常见来源。
