有效的错误沟通是设计简单、直观 APIs 的重要部分。返回标准化错误响应的服务使 API 客户端能够构造集中的公共错误处理逻辑。此公共逻辑简化 API 客户端应用，并消除对繁琐自定义错误处理代码的需要。

## Guidance

发生 API 错误时，服务 **must** 返回 [`google.rpc.Status`](https://github.com/googleapis/googleapis/blob/master/google/rpc/status.proto) message，并且 **must** 使用 [`google.rpc.Code`](https://github.com/googleapis/googleapis/blob/master/google/rpc/code.proto) 中定义的规范错误码。关于特定码的更多信息见 [gRPC status code documentation](https://github.com/grpc/grpc/blob/master/doc/statuscodes.md)。

错误消息 **should** 帮助有合理技术背景的用户*理解*并*解决*问题，并且 **should not** 假定用户是你特定 API 的专家。此外，错误消息 **must not** 假定用户会知道其底层实现的任何事情。

错误消息 **should** 简短但可行动。任何额外信息 **should** 在 `details` 字段中提供。若需要更多信息，你 **should** 提供一个链接，读者可以在那里获得更多信息或提问以帮助解决问题。写消息时 [设定正确语气](https://developers.google.com/tech-writing/error-messages/set-tone) 也很重要。

下列各节描述 `google.rpc.Status` 的字段。

### Status.message

`message` 字段是面向开发者的、人类可读的「调试消息」，**should** 为英语。（本地化消息用 `details` 字段内的 `LocalizedMessage` 表达。见 [`LocalizedMessage`](#localizedmessage) 了解更多细节。）消息的任何动态方面 **must** 作为出现在 [`details`](#status-details) 中的 `ErrorInfo` 内的 metadata 包含。

该消息视为问题描述。它意在让开发者理解问题，并且比 [`ErrorInfo.reason`](https://github.com/googleapis/googleapis/blob/master/google/rpc/error_details.proto#L57) 更详细，后者 [稍后](#errorinfo) 讨论。

消息 **should** 使用易于理解的简单描述性语言（无技术行话），清楚陈述导致错误的问题，并提供可行动的解决办法。

对先前在没有机器可读标识符的情况下返回错误的既有（brownfield）APIs，对任何给定错误，`message` 的值 **must** 保持相同。更多信息见 [Changing Error Messages](#changing-error-messages)。

### Status.code

`code` 字段是状态码，**must** 为 [`google.rpc.Code`](https://github.com/googleapis/googleapis/blob/master/google/rpc/code.proto) enum 某个元素的数值。

例如，值 `5` 是 `NOT_FOUND` enum 元素的数值。

### Status.details

`details` 字段允许把带额外错误信息的 messages 包含在错误响应中，每个都打包在 `google.protobuf.Any` message 中。

Google 定义了一组用于错误细节的 [standard detail payloads](https://github.com/googleapis/googleapis/blob/master/google/rpc/error_details.proto)，覆盖 API 错误的大多数常见需求。可行时服务 **should** 使用这些标准 detail payloads。

每种类型的 detail payload **must** 最多包含一次。例如，`details` 中 **must not** 有超过一条 [`BadRequest`](https://github.com/googleapis/googleapis/blob/477a59d764428136ba1d857a9633c0d231de6efa/google/rpc/error_details.proto#L168-L218) message，但 **may** 有一条 `BadRequest` 和一条 [`PreconditionFailure`](https://github.com/googleapis/googleapis/blob/6f3fcc058ff29989f6d3a71557a44b5e81b897bd/google/rpc/error_details.proto#L139-L166)。

所有错误响应 **must** 在 `details` 内包含 `ErrorInfo`。这提供机器可读标识符，以便用户可以对错误的特定方面写代码。

下列各节描述最常见的标准 detail payloads。

#### ErrorInfo

[`ErrorInfo`](https://github.com/googleapis/googleapis/blob/6f3fcc058ff29989f6d3a71557a44b5e81b897bd/google/rpc/error_details.proto#L27-L76) message 是发送机器可读标识符的主要方式。上下文信息 **should** 包含在 `ErrorInfo` 的 `metadata` 中，并且若它出现在错误消息中则 **must** 包含。

`reason` 字段是错误原因的简短 snake_case 描述。错误 reasons 在特定错误域内唯一。reason **must** 最多 63 个字符，并匹配正则表达式 ``[A-Z][A-Z0-9_]+[A-Z0-9]``。（这是 UPPER_SNAKE_CASE，无前导或尾随下划线，且无前导数字。）

reason **should** 简洁，但对人类读者有足够意义以理解该 reason 指什么。

好例子：

- `CPU_AVAILABILITY`
- `NO_STOCK`
- `CHECKED_OUT`
- `AVAILABILITY_ERROR`

坏例子：

- `THE_BOOK_YOU_WANT_IS_NOT_AVAILABLE`（过于冗长）
- `ERROR`（过于笼统）

`domain` 字段是 `reason` 所属的逻辑分组。domain **must** 为全局唯一值，并且通常是生成该错误的服务名，例如 `pubsub.googleapis.com`。

(reason, domain) 对形成识别特定错误的机器可读方式。服务 **must** 对同一错误使用相同的 (reason, domain) 对，并且 **must not** 对逻辑上不同的错误使用相同的 (reason, domain) 对。两个错误是否「相同」的决定并不总是清楚，但 **should** 一般从客户端可能采取以解决它们的期望动作来考虑。

`metadata` 字段是提供额外动态信息作为上下文的键/值对 map。`metadata` 内每个键 **must** 最长 64 个字符，并符合正则表达式 ``[a-z][a-zA-Z0-9-_]+``。

任何贡献于 `Status.message` 或 `LocalizedMessage.message` 消息的请求特定信息 **must** 在 `metadata` 内表示。此实践至关重要，以便机器 actor 无需解析错误消息来提取信息。

例如考虑下列消息：

> An \<e2-medium\> VM instance with \<local-ssd=3,nvidia-t4=2\> is currently unavailable
> in the \<us-east1-a\> zone. Consider trying your request in the \<us-central1-f,us-central1-c\>
> zone(s), which currently has/have capacity to accommodate your request. Alternatively,
> you can try your request again with a different VM hardware configuration
> or at a later time. For more information, see the troubleshooting documentation.

同一错误的 `ErrorInfo.metadata` map 可以是：

- `"zone": "us-east1-a"`
- `"vmType": "e2-medium"`
- `"attachment": "local-ssd=3,nvidia-t4=2"`
- `"zonesWithCapacity": "us-central1-f,us-central1-c"`

未出现在错误消息中的额外上下文信息 **may** 也包含在 `metadata` 中，以允许客户端程序化使用。

任何给定 (reason,domain) 对包含的 metadata 可以随时间演进：

- **may** 包含新键
- 所有已包含的键 **must** 继续被包含（但可以有空值）

换句话说，一旦用户对某个 (reason, domain) 对观察到给定键，服务 **must** 允许他们依赖它将来继续存在。

每个 (reason, domain) 对提供的键集合独立于其它对，但服务 **should** 追求一致的键命名。例如，同一 domain 内的两个错误 reasons 不应使用 `vmType` 与 `virtualMachineType` 的 metadata 键。

#### LocalizedMessage

[`google.rpc.LocalizedMessage`](https://github.com/googleapis/googleapis/blob/e9897ed945336e2dc967b439ac7b4be6d2c62640/google/rpc/error_details.proto#L275-L285) 用于提供 **should** 在可能时本地化到用户指定 locale 的错误消息。

若 [`Status.message`](#status-message) 字段有因 [Changing Error Messages](#changing-error-messages) 一节中的约束而无法更改的次优值，即使没有用户指定的 locale 可用，`LocalizedMessage` **may** 用于提供更好的错误消息。

无论消息的 locale 如何确定，`locale` 与 `message` 字段都 **must** 被填充。

`locale` 字段指定消息的 locale，遵循 [IETF bcp47](https://www.rfc-editor.org/rfc/bcp/bcp47.txt)（Tags for Identifying Languages）。示例值：`"en-US"`、`"fr-CH"`、`"es-MX"`。

`message` 字段包含本地化文本本身。这 **should** 包含错误的简要描述以及解决错误的行动号召。消息 **should** 包含上下文信息以使消息尽可能具体。消息中的任何上下文信息 **must** 包含在 `ErrorInfo.metadata` 中。见 [`ErrorInfo`](#errorinfo) 了解上下文信息如何包含在消息与对应 metadata 中的更多细节。

`LocalizedMessage` payload **should** 包含错误的完整解决办法。若需要的信息超出此 payload 可合理容纳的范围，则额外的解决信息 **must** 在 `Help` payload 中提供。见 [Help](#help) 一节的指导。

#### Help

当其它文本错误消息（在 `Status.message` 或 `LocalizedMessage.message` 中）没有给用户提供足够上下文或可行动的下一步，或若故障排查中需要考虑多个失败点时，**must** 在 `Help` payload 中提供指向补充故障排查文档的链接。

把此信息作为清楚的问题定义与可行动解决办法的补充提供，而不是作为它们的替代。链接的文档 **must** 清楚与该错误相关。若单个页面包含关于多个错误的信息，**must** 使用 [`ErrorInfo.reason`](#errorinfo) 值来缩小相关信息。

`description` 字段是链接信息的文本描述。这 **must** 适合作为超链接文本显示给用户。这 **must** 为纯文本（不是 HTML、Markdown 等）。

示例 `description` 值：`"Troubleshooting documentation for STOCKOUT errors"`

`url` 字段是要链接到的 URL。这 **must** 为绝对 URL，包括 scheme。

示例 `url` 值：
`"https://cloud.google.com/compute/docs/resource-error"`

对公开文档化的服务，即使实际使用有访问控制，链接的内容 **must** 无需认证即可访问。

对私有文档化的服务，链接的内容 **may** 需要认证。

### Error messages

文本错误消息可以同时出现在 `Status.message` 与 `LocalizedMessage.message` 字段中。消息 **should** 简洁但可行动，在适当时用请求特定信息（例如 resource name 或 region）提供精确细节。任何请求特定细节 **must** 出现在 [`ErrorInfo.metadata`](#errorinfo) 中。

#### Changing error messages

随时间更改 `Status.message` 的内容必须谨慎进行，以避免破坏先前不得不依赖该消息获取全部信息的客户端。更多细节见 [the rationale section](#updating-statusmessage)。

对给定 RPC：

- 若该 RPC *始终* 返回带机器可读信息的 `ErrorInfo`，`Status.message` 的内容 **may** 随时间变更。（例如，API producer 可能提供更清楚的解释，或更多请求特定信息。）
- 否则，`Status.message` 的内容 **must** 稳定，提供相同文本与相同请求特定信息。与其更改 `Status.message`，API **should** 在 `Status.details` 内包含 [`LocalizedMessage`](#localizedmessage)。

即使 RPC 始终返回 `ErrorInfo`，API **may** 保持现有 `Status.message` 稳定，并在 `Status.details` 内添加 [`LocalizedMessage`](#localizedmessage)。

`LocalizedMessage.details` 的内容 **may** 随时间变更。

### Partial errors

APIs **should not** 支持部分错误。部分错误给用户增加显著复杂性，因为它们通常绕过错误码的使用，或把那些错误码移入响应 message，用户 **must** 写专门的错误处理逻辑来解决问题。

然而，偶尔部分错误是必要的，特别是在批量操作中，因单个条目的问题而使整个大请求失败会对用户不友好。

需要部分错误的方法 **should** 使用 [long-running operations]({{< ref "aip-0151" >}})，并且该方法 **should** 把部分失败信息放在 metadata message 中。错误本身 **must** 仍用 [`google.rpc.Status`](https://github.com/googleapis/googleapis/blob/master/google/rpc/status.proto) 对象表示。

### Permission Denied

若用户没有权限访问该资源或父资源，无论它是否存在，服务 **must** 以 `PERMISSION_DENIED`（HTTP 403）报错。权限 **must** 在检查资源或父资源是否存在之前检查。

若用户确有适当权限，但请求的资源或父资源不存在，服务 **must** 以 `NOT_FOUND`（HTTP 404）报错。

## HTTP/1.1+JSON representation

当客户端按 [AIP-127]({{< ref "aip-0127" >}}) 使用 HTTP/1.1 时，错误信息在响应 body 中作为 JSON 对象返回。因向后兼容原因，这并不精确映射到 `google.rpc.Status`，但包含相同的核心信息。schema 在下列 proto 中定义：

```proto
message Error {
  message Status {
    // The HTTP status code that corresponds to `google.rpc.Status.code`.
    int32 code = 1;
    // This corresponds to `google.rpc.Status.message`.
    string message = 2;
    // This is the enum version for `google.rpc.Status.code`.
    google.rpc.Code status = 4;
    // This corresponds to `google.rpc.Status.details`.
    repeated google.protobuf.Any details = 5;
  }

  Status error = 1;
}
```

最重要的区别是 JSON 中的 `code` 字段是 HTTP 状态码，*不是* `google.rpc.Status.code` 的直接值。例如，`code` 值为 5 的 `google.rpc.Status` message 会映射到包含下列与码相关字段的对象（以及 message、details 等）：

```json
{
  "error": {
    "code": 404,          // The HTTP status code for "not found"
    "status": "NOT_FOUND" // The name in google.rpc.Code for value 5
  }
}
```

下列 JSON 展示错误响应的完整填充 HTTP/1.1+JSON 表示。

```json
{
  "error": {
    "code": 429,
    "message": "The zone 'us-east1-a' does not have enough resources available to fulfill the request. Try a different zone, or try again later.",
    "status": "RESOURCE_EXHAUSTED",
    "details": [
      {
        "@type": "type.googleapis.com/google.rpc.ErrorInfo",
        "reason": "RESOURCE_AVAILABILITY",
        "domain": "compute.googleapis.com",
        "metadata": {
          "zone": "us-east1-a",
          "vmType": "e2-medium",
          "attachment": "local-ssd=3,nvidia-t4=2",
          "zonesWithCapacity": "us-central1-f,us-central1-c"
        }
      },
      {
        "@type": "type.googleapis.com/google.rpc.LocalizedMessage",
        "locale": "en-US",
        "message": "An <e2-medium> VM instance with <local-ssd=3,nvidia-t4=2> is currently unavailable in the <us-east1-a> zone. Consider trying your request in the <us-central1-f,us-central1-c> zone(s), which currently has/have capacity to accommodate your request. Alternatively, you can try your request again with a different VM hardware configuration or at a later time. For more information, see the troubleshooting documentation."
      },
      {
        "@type": "type.googleapis.com/google.rpc.Help",
        "links": [
          {
            "description": "Additional information on this error",
            "url": "https://cloud.google.com/compute/docs/resource-error"
          }
        ]
      }
    ]
  }
}
```

## Rationale

### Requiring ErrorInfo

要求 `ErrorInfo` 是因为它进一步识别错误。`Status.status` 仅有大约二十个 [available values](https://github.com/googleapis/googleapis/blob/master/google/rpc/code.proto)，很难在整个 [API Service](https://cloud.google.com/apis/design/glossary#api_service) 中把一个错误与另一个区分开。

此外，错误消息常常包含表达可变信息的动态段，因此*每个*错误响应都需要有机器可读组件，使客户端能够程序化使用此类信息。

### Including LocalizedMessage

选择 `LocalizedMessage` 作为呈现替代错误消息的位置。尽管 `LocalizedMessage` **may** 使用请求中指定的 locale，服务 **may** 即使没有用户指定的 locale 也提供 `LocalizedMessage`，通常是为了在 [`Status.message` 无法更改的情形](#updating-statusmessage) 中提供更好的错误消息。未由用户指定 locale 时，它 **should** 为 `en-US`（US English）。

即使 `Status.message` 中提供了相同消息、且不支持本地化到用户指定 locale，服务 **may** 也包含 `LocalizedMessage`。这样做的原因包括：

- 打算在不久的将来支持用户指定的本地化，允许客户端一致使用 `LocalizedMessage`，并在引入该功能时不更改其错误报告代码。
- 服务内所有 RPCs 的一致性：若某些 RPCs 包含 `LocalizedMessage`，而某些仅用 `Status.message` 作为错误消息，客户端必须知道哪些 RPCs 会做什么，或实现回退机制。在所有 RPCs 上提供 `LocalizedMessage` 允许编写简单且一致的客户端代码。

### Updating Status.message

若客户端曾经观察到带已填充 `Status.message`（它始终会被填充）但没有 `ErrorInfo` 的错误，该客户端的开发者很可能不得不求助于解析 `Status.message` 以找出超出 `Status.code` 所传达的信息。该信息可能通过匹配特定文本找到（例如 "Connection closed with unknown cause"），或通过解析消息找出 metadata 值（例如资源不足的 region）。此时，`Status.message` 隐含地成为 API 契约的一部分，因此 **must not** 被更新——那会是破坏性变更。这是把 `LocalizedMessage` 引入 `Status.details` 的原因之一。

**始终** 包含 `ErrorInfo` 的 RPCs 处于更好的位置：此时契约更多是关于任何给定错误的 `ErrorInfo` 稳定性。reason 与 domain 需要随时间一致，并且任何给定 (reason,domain) 提供的 metadata 只能扩展。客户端仍可能解析 `Status.message` 而不是使用 `ErrorInfo`，但他们始终有更稳健的选项可用。
