错误若各写各的，客户端就得为每个 API 堆一套处理逻辑。返回标准化错误，客户端才能把公共处理收拢到一处：应用更简单，也不必再写繁琐的自定义错误代码。

## 怎么返回错误

发生 API 错误时，服务必须返回 [`google.rpc.Status`](https://github.com/googleapis/googleapis/blob/master/google/rpc/status.proto)，错误码必须用 [`google.rpc.Code`](https://github.com/googleapis/googleapis/blob/master/google/rpc/code.proto) 里的规范值。各码含义见 [gRPC status code documentation](https://github.com/grpc/grpc/blob/master/doc/statuscodes.md)。

错误消息应当让有一定技术背景的人看得懂、能动手修。不要假设读者是你这个 API 的专家，更不要假设他们知道你们内部怎么实现。

消息本身应当短、而且可行动。多出来的信息放 `details`。还不够就给一个链接，让人能继续查或提问。写的时候注意 [语气](https://developers.google.com/tech-writing/error-messages/set-tone)。

下面按 `google.rpc.Status` 的字段讲。

### Status.message

`message` 是给开发者看的调试说明，应当用英语。给最终用户的本地化文案放 `details` 里的 LocalizedMessage。消息里任何会变的部分，必须同时写进 ErrorInfo 的 `metadata`。

把它当成问题描述：让人明白出了什么事，比 ErrorInfo.reason 更细。用直白的话把问题和下一步写清楚，少用行话。

老 API 如果以前从没给过机器可读的错误标识，同一个错误的 `message` 不得改写。详见下文「改错误消息」。

### Status.code

`code` 必须是 `google.rpc.Code` 某个枚举值的数字。例如 `5` 就是 `NOT_FOUND`。

### Status.details

`details` 用来附带额外错误信息，每条打成 `google.protobuf.Any`。

Google 定义了一组用于错误细节的 [standard detail payloads](https://github.com/googleapis/googleapis/blob/master/google/rpc/error_details.proto)，覆盖 API 错误的大多数常见需求。可行时服务应当使用这些标准 detail payloads。

每种类型的 detail payload 必须最多包含一次。例如，`details` 中不得有超过一条 [`BadRequest`](https://github.com/googleapis/googleapis/blob/477a59d764428136ba1d857a9633c0d231de6efa/google/rpc/error_details.proto#L168-L218) message，但可以有一条 `BadRequest` 和一条 [`PreconditionFailure`](https://github.com/googleapis/googleapis/blob/6f3fcc058ff29989f6d3a71557a44b5e81b897bd/google/rpc/error_details.proto#L139-L166)。

所有错误响应必须在 `details` 内包含 ErrorInfo。这提供机器可读标识符，以便用户可以对错误的特定方面写代码。

下列各节描述最常见的标准 detail payloads。

#### ErrorInfo

[`ErrorInfo`](https://github.com/googleapis/googleapis/blob/6f3fcc058ff29989f6d3a71557a44b5e81b897bd/google/rpc/error_details.proto#L27-L76) message 是发送机器可读标识符的主要方式。上下文信息应当包含在 ErrorInfo 的 `metadata` 中；若它出现在错误消息中，则必须包含。

`reason` 字段是错误原因的简短 snake_case 描述。错误 reasons 在特定错误域内唯一。reason 必须最多 63 个字符，并匹配正则表达式 ``[A-Z][A-Z0-9_]+[A-Z0-9]``。（这是 UPPER_SNAKE_CASE，无前导或尾随下划线，且无前导数字。）

reason 应当简洁，但对人类读者有足够意义以理解该 reason 指什么。

好例子：

- `CPU_AVAILABILITY`
- `NO_STOCK`
- `CHECKED_OUT`
- `AVAILABILITY_ERROR`

坏例子：

- `THE_BOOK_YOU_WANT_IS_NOT_AVAILABLE`（过于冗长）
- `ERROR`（过于笼统）

`domain` 字段是 `reason` 所属的逻辑分组。domain 必须为全局唯一值，并且通常是生成该错误的服务名，例如 `pubsub.googleapis.com`。

(reason, domain) 对形成识别特定错误的机器可读方式。服务必须对同一错误使用相同的 (reason, domain) 对，并且不得对逻辑上不同的错误使用相同的 (reason, domain) 对。两个错误是否「相同」的决定并不总是清楚，但应当一般从客户端可能采取以解决它们的期望动作来考虑。

`metadata` 字段是提供额外动态信息作为上下文的键/值对 map。`metadata` 内每个键必须最长 64 个字符，并符合正则表达式 ``[a-z][a-zA-Z0-9-_]+``。

任何贡献于 `Status.message` 或 `LocalizedMessage.message` 消息的请求特定信息，必须在 `metadata` 内表示。此实践至关重要，以便机器 actor 无需解析错误消息来提取信息。

例如考虑下列消息：

> An \<e2-medium\> VM instance with \<local-ssd=3,nvidia-t4=2\> is currently unavailable
> in the \<us-east1-a\> zone. Consider trying your request in the \<us-central1-f,us-central1-c\>
> zone(s), which currently has/have capacity to accommodate your request. Alternatively,
> you can try your request again with a different VM hardware configuration
> or at a later time. For more information, see the troubleshooting documentation.

同一错误的 `ErrorInfo.metadata` map 可以是：

- `"zone": "us-east1-a"`
- `"vmType": "e2-medium"`
- `"attachment": "local-ssd=3,nvidia-t4=2"`
- `"zonesWithCapacity": "us-central1-f,us-central1-c"`

未出现在错误消息中的额外上下文信息也可以包含在 `metadata` 中，以允许客户端程序化使用。

任何给定 (reason,domain) 对包含的 metadata 可以随时间演进：

- 可以包含新键
- 所有已包含的键必须继续被包含（但可以有空值）

换句话说，一旦用户对某个 (reason, domain) 对观察到给定键，服务必须允许他们依赖它将来继续存在。

每个 (reason, domain) 对提供的键集合独立于其它对，但服务应当追求一致的键命名。例如，同一 domain 内的两个错误 reasons 不应使用 `vmType` 与 `virtualMachineType` 的 metadata 键。

#### LocalizedMessage

[`google.rpc.LocalizedMessage`](https://github.com/googleapis/googleapis/blob/e9897ed945336e2dc967b439ac7b4be6d2c62640/google/rpc/error_details.proto#L275-L285) 用于提供应当在可能时本地化到用户指定 locale 的错误消息。

若 `Status.message` 字段有因「改错误消息」一节中的约束而无法更改的次优值，即使没有用户指定的 locale 可用，LocalizedMessage 也可以用于提供更好的错误消息。

无论消息的 locale 如何确定，`locale` 与 `message` 字段都必须被填充。

`locale` 字段指定消息的 locale，遵循 [IETF bcp47](https://www.rfc-editor.org/rfc/bcp/bcp47.txt)（Tags for Identifying Languages）。示例值：`"en-US"`、`"fr-CH"`、`"es-MX"`。

`message` 字段包含本地化文本本身。这应当包含错误的简要描述以及解决错误的行动号召。消息应当包含上下文信息以使消息尽可能具体。消息中的任何上下文信息必须包含在 `ErrorInfo.metadata` 中。上下文信息如何写进消息与对应 metadata，见上文 ErrorInfo。

LocalizedMessage payload 应当包含错误的完整解决办法。若需要的信息超出此 payload 可合理容纳的范围，则额外的解决信息必须在 Help payload 中提供。见下文 Help。

#### Help

当其它文本错误消息（在 `Status.message` 或 `LocalizedMessage.message` 中）没有给用户提供足够上下文或可行动的下一步，或若故障排查中需要考虑多个失败点时，必须在 Help payload 中提供指向补充故障排查文档的链接。

把此信息作为清楚的问题定义与可行动解决办法的补充提供，而不是作为它们的替代。链接的文档必须清楚与该错误相关。若单个页面包含关于多个错误的信息，必须使用 `ErrorInfo.reason` 值来缩小相关信息。

`description` 字段是链接信息的文本描述。这必须适合作为超链接文本显示给用户。这必须为纯文本（不是 HTML、Markdown 等）。

示例 `description` 值：`"Troubleshooting documentation for STOCKOUT errors"`

`url` 字段是要链接到的 URL。这必须为绝对 URL，包括 scheme。

示例 `url` 值：
`"https://cloud.google.com/compute/docs/resource-error"`

对公开文档化的服务，即使实际使用有访问控制，链接的内容必须无需认证即可访问。

对私有文档化的服务，链接的内容可以需要认证。

### 改错误消息

文本错误消息可以同时出现在 `Status.message` 与 `LocalizedMessage.message` 字段中。消息应当简洁但可行动，在适当时用请求特定信息（例如 resource name 或 region）提供精确细节。任何请求特定细节必须出现在 `ErrorInfo.metadata` 中。

随时间更改 `Status.message` 的内容必须谨慎进行，以避免破坏先前不得不依赖该消息获取全部信息的客户端。更多细节见下文「更新 Status.message」。

对给定 RPC：

- 若该 RPC *始终* 返回带机器可读信息的 ErrorInfo，`Status.message` 的内容可以随时间变更。（例如，API producer 可能提供更清楚的解释，或更多请求特定信息。）
- 否则，`Status.message` 的内容必须稳定，提供相同文本与相同请求特定信息。与其更改 `Status.message`，API 应当在 `Status.details` 内包含 LocalizedMessage。

即使 RPC 始终返回 ErrorInfo，API 也可以保持现有 `Status.message` 稳定，并在 `Status.details` 内添加 LocalizedMessage。

`LocalizedMessage.details` 的内容可以随时间变更。

### 部分错误

APIs 不应当支持部分错误。部分错误给用户增加显著复杂性，因为它们通常绕过错误码的使用，或把那些错误码移入响应 message，用户必须写专门的错误处理逻辑来解决问题。

然而，偶尔部分错误是必要的，特别是在批量操作中：因单个条目的问题而使整个大请求失败，会对用户不友好。

需要部分错误的方法应当使用 long-running operations（见 [AIP-151]({{< ref "aip-0151" >}})），并且该方法应当把部分失败信息放在 metadata message 中。错误本身必须仍用 [`google.rpc.Status`](https://github.com/googleapis/googleapis/blob/master/google/rpc/status.proto) 对象表示。

### PERMISSION_DENIED

若用户没有权限访问该资源或父资源，无论它是否存在，服务必须以 `PERMISSION_DENIED`（HTTP 403）报错。权限必须在检查资源或父资源是否存在之前检查。

若用户确有适当权限，但请求的资源或父资源不存在，服务必须以 `NOT_FOUND`（HTTP 404）报错。

## HTTP/1.1+JSON 表示

当客户端按 [AIP-127]({{< ref "aip-0127" >}}) 使用 HTTP/1.1 时，错误信息在响应 body 中作为 JSON 对象返回。因向后兼容原因，这并不精确映射到 `google.rpc.Status`，但包含相同的核心信息。schema 在下列 proto 中定义：

```proto
message Error {
  message Status {
    // The HTTP status code that corresponds to `google.rpc.Status.code`.
    int32 code = 1;
    // This corresponds to `google.rpc.Status.message`.
    string message = 2;
    // This is the enum version for `google.rpc.Status.code`.
    google.rpc.Code status = 4;
    // This corresponds to `google.rpc.Status.details`.
    repeated google.protobuf.Any details = 5;
  }

  Status error = 1;
}
```

最重要的区别是 JSON 中的 `code` 字段是 HTTP 状态码，不是 `google.rpc.Status.code` 的直接值。例如，`code` 值为 5 的 `google.rpc.Status` message 会映射到包含下列与码相关字段的对象（以及 message、details 等）：

```json
{
  "error": {
    "code": 404,          // The HTTP status code for "not found"
    "status": "NOT_FOUND" // The name in google.rpc.Code for value 5
  }
}
```

下列 JSON 展示错误响应的完整填充 HTTP/1.1+JSON 表示。

```json
{
  "error": {
    "code": 429,
    "message": "The zone 'us-east1-a' does not have enough resources available to fulfill the request. Try a different zone, or try again later.",
    "status": "RESOURCE_EXHAUSTED",
    "details": [
      {
        "@type": "type.googleapis.com/google.rpc.ErrorInfo",
        "reason": "RESOURCE_AVAILABILITY",
        "domain": "compute.googleapis.com",
        "metadata": {
          "zone": "us-east1-a",
          "vmType": "e2-medium",
          "attachment": "local-ssd=3,nvidia-t4=2",
          "zonesWithCapacity": "us-central1-f,us-central1-c"
        }
      },
      {
        "@type": "type.googleapis.com/google.rpc.LocalizedMessage",
        "locale": "en-US",
        "message": "An <e2-medium> VM instance with <local-ssd=3,nvidia-t4=2> is currently unavailable in the <us-east1-a> zone. Consider trying your request in the <us-central1-f,us-central1-c> zone(s), which currently has/have capacity to accommodate your request. Alternatively, you can try your request again with a different VM hardware configuration or at a later time. For more information, see the troubleshooting documentation."
      },
      {
        "@type": "type.googleapis.com/google.rpc.Help",
        "links": [
          {
            "description": "Additional information on this error",
            "url": "https://cloud.google.com/compute/docs/resource-error"
          }
        ]
      }
    ]
  }
}
```

## 为什么

### 为何要求 ErrorInfo

要求 ErrorInfo，是因为它进一步识别错误。`Status.status` 仅有大约二十个 [available values](https://github.com/googleapis/googleapis/blob/master/google/rpc/code.proto)，很难在整个 [API Service](https://cloud.google.com/apis/design/glossary#api_service) 中把一个错误与另一个区分开。

此外，错误消息常常包含表达可变信息的动态段，因此每个错误响应都需要有机器可读组件，使客户端能够程序化使用此类信息。

### 为何包含 LocalizedMessage

选择 LocalizedMessage 作为呈现替代错误消息的位置。尽管 LocalizedMessage 可以使用请求中指定的 locale，服务也可以即使没有用户指定的 locale 也提供 LocalizedMessage，通常是为了在 `Status.message` 无法更改的情形中提供更好的错误消息。未由用户指定 locale 时，它应当为 `en-US`（US English）。

即使 `Status.message` 中提供了相同消息、且不支持本地化到用户指定 locale，服务也可以包含 LocalizedMessage。这样做的原因包括：

- 打算在不久的将来支持用户指定的本地化，允许客户端一致使用 LocalizedMessage，并在引入该功能时不更改其错误报告代码。
- 服务内所有 RPCs 的一致性：若某些 RPCs 包含 LocalizedMessage，而某些仅用 `Status.message` 作为错误消息，客户端必须知道哪些 RPCs 会做什么，或实现回退机制。在所有 RPCs 上提供 LocalizedMessage 允许编写简单且一致的客户端代码。

### 更新 Status.message

若客户端曾经观察到带已填充 `Status.message`（它始终会被填充）但没有 ErrorInfo 的错误，该客户端的开发者很可能不得不求助于解析 `Status.message`，以找出超出 `Status.code` 所传达的信息。该信息可能通过匹配特定文本找到（例如 "Connection closed with unknown cause"），或通过解析消息找出 metadata 值（例如资源不足的 region）。此时，`Status.message` 隐含地成为 API 契约的一部分，因此不得被更新——那会是破坏性变更。这是把 LocalizedMessage 引入 `Status.details` 的原因之一。

始终包含 ErrorInfo 的 RPCs 处于更好的位置：此时契约更多是关于任何给定错误的 ErrorInfo 稳定性。reason 与 domain 需要随时间一致，并且任何给定 (reason,domain) 提供的 metadata 只能扩展。客户端仍可能解析 `Status.message` 而不是使用 ErrorInfo，但他们始终有更稳健的选项可用。
