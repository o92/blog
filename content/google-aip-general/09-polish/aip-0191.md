.proto 放哪、文件里谁先谁后、各语言的 package 注解怎么写，技术上差不了多少。但结构一致，用户和评审者读 API 表面会轻松很多。

下列指导适用于用 protocol buffers 定义的 APIs，例如 Google 通篇使用的那些。精神也适用于用其它规范语言或格式定义的 APIs，但某些具体建议可能无关。

## Syntax

用 protocol buffers 定义的 APIs 必须使用 `proto3` syntax。

## 单个 package

用 protocol buffers 定义的 APIs 必须把每个单独的 API 定义在单个 package 中，该 package 必须以版本组件结尾。例如：

```proto
syntax = "proto3";

package google.cloud.translation.v3;
```

Google APIs 必须位于匹配 protocol buffer `package` 指令的目录中。例如上面的 package 决定目录为 `google/cloud/translation/v3`。

## 文件名

把 API 定义分成多个文件常常有用。文件名必须使用 `snake_case`。

APIs 应当有一个明显的「入口」文件，一般以 API 本身命名。具有少量离散服务的 API（Google Cloud Pub/Sub 的 `Publisher` 与 `Subscriber` 是好例子）可以每个服务有单独的入口文件。

只有一个文件的 APIs 应当使用与 API 名称对应的文件名。

API `service` 定义以及关联的 RPC 请求与响应 `message` 定义，应当定义在同一文件中。

记住：文件名常常成为客户端库中的模块名，客户在 `import` 或 `use` 语句中使用它们。因此，选择描述性且不含语言关键字的文件名确实重要。例如名为 `import.proto` 的文件在 Python 中可能有问题。

版本不得用作文件名，这会在客户端库中产生怪异的 imports。诸如 `v3.proto` 或 `v1beta1.proto` 的文件名被禁止。

## 文件内布局

单个文件应当把更高层、更重要的定义放在更低层、较不重要的定义之前。

在 proto 文件中，组件应当按下列顺序，且每一项应当用空行分隔：

- Copyright 与许可声明（若适用）。
- proto `syntax` 语句。
- proto `package` 语句。
- 任何 `import` 语句，按字母顺序。
- 任何文件级 `option` 语句。
- 任何 `service` 定义。
  - Methods 应当按它们影响的资源分组，且标准方法应当先于 custom methods。
- 资源 `message` 定义。父资源必须在其子资源之前定义。
- RPC 请求与响应 `message` 定义，与对应方法相同的顺序。每个请求 message 必须先于其对应的响应 message（若有）。
- 任何剩余的 `message` 定义。
- 任何顶层 `enum` 定义。

## Packaging annotations

Protocol buffers 附带注解，用于声明生成文件的 package 或 namespace（取决于目标语言的词汇）。例如，设置 `go_package` 或 `csharp_namespace` 将覆盖推断的 package 名称。

定义 APIs 时，适用下列规则：

- Java
  - 必须设置 `java_package` 注解。正确值通常是带适当 TLD 前缀的 proto package。示例：`com.google.example.v1`。
  - `java_multiple_files` 注解必须设为 `true`。
  - 必须设置 `java_outer_classname` 注解，并且应当设为 proto 文件名的 `PascalCase`，并追加 `Proto`。示例：`LibraryProto`。
- 其它语言
  - 其它语言的 package 或 namespace 指令必须要么在 proto package 的每个文件中设置，要么都不设置。若设置，每个文件中的值必须相同。
  - 若 protobuf package 的任何部分是复合名（例如 accessapproval），必须指定 C#、Ruby 与 PHP 选项，以便用 PascalCase（UpperCamelCase）考虑词边界。示例：

    ```proto
    option csharp_namespace = "Google.Cloud.AccessApproval.V1";
    option php_namespace = "Google\\Cloud\\AccessApproval\\V1";
    option ruby_package = "Google::Cloud::AccessApproval::V1";
    ```

  - `go_package` 值直接取决于 Go 代码如何管理，即模块名基于 VCS provider 还是使用远程 import 路径，但常常有一致结构。
  - 模块可以按产品领域不同，例如 `google.cloud.accessapproval.v1` 会在模块 `cloud.google.com/go/accessapproval` 中。
  - package import 路径应当从 proto package 派生。
  - proto package 中的 API 版本应当以 `api` 为前缀，例如 proto package 段 `v1` 变成 `apiv1`。
  - 终端 import 路径段应当基于 proto package 中找到的产品名，并且必须以 `pb` 为后缀，例如 `accessapproval` 变成 `accessapprovalpb`。
  - 此值应当留给拥有生成代码的团队来决定。

所有 packaging annotations 应当按名称字母顺序指定。关于语言 package 选项见 [Protobuf documentation](https://protobuf.dev/programming-guides/proto3/#packages)。

尽管 Java 以外的语言对不含复合名的 APIs 有合理默认值，请注意：添加此注解（其值不等价于默认值）在该语言中构成破坏性变更。发布 protos 时，确保省略是有意的。

## 为什么

### Java packaging options

把选项 `java_multiple_files` 设为 true，是为了更干净的文件结构。这样做指示 `protoc` 为每个 Protobuf 类型创建一个输出文件，从而允许更细粒度的 imports。选项 `java_outer_classname` 与 `java_multiple_files` 组合是必需的。它指示 `protoc` 把每个编译后的 Protobuf 类型包装在名称为此选项值的 Java 类中。这防止生成类型之间潜在的命名冲突。

### Go packaging option

Go packaging option 需要由拥有生成代码的团队决定，因为它直接与该团队的源代码管理实践绑定。允许每个 proto package 自行决定 Go package，会在代码管理中造成不一致与摩擦。在该拥有团队内，Go package 命名中有一致结构，对一致的最终用户体验至关重要。
