**英文标题**：API-specific protos  
**原文**：[AIP-215](https://google.aip.dev/215) · approved · 创建 2018-10-01  
**许可**：原文 © Google，[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)

APIs 主要用自己的 protos 定义，偶尔才依赖 common components。把 APIs 彼此隔开，是为了避开版本纠缠和客户端库打包问题：你不该直接 import 别人 API 里的 message。

## 怎么做

- 特定于某 API 的所有 protos 必须位于带主版本的 package 内（例如 `google.library.v1`）。
- 对其它 APIs 中资源的引用必须用 resource names（见 [AIP-122]({{< ref "aip-0122" >}})）表达，而不是使用资源 messages。
- 当某 API 的两个版本使用实际上相同的（API 专属）proto 时，该 proto 必须在每个版本中复制。换句话说，APIs 不得创建自己的「API-specific common component」packages。
- Organization-specific common components 可以放在公共 package 中，如 [AIP-213]({{< ref "aip-0213" >}}) 所述，但不得被该组织外的任何 API 使用。
- Global common components（也在 [AIP-213]({{< ref "aip-0213" >}}) 中描述）可以被任何 API 自由使用。

## 为什么

当一个 API 依赖另一个 API 定义的 protos 时，这会在客户期望行为与客户端库依赖管理方面引入不确定性。假设 `google.cloud.library.v1` 依赖 `google.cloud.movies.v2` 中的 protos（而不是抽象资源）。对 `google.cloud.movies.v2` 的任何变更都可能导致问题。

例如：

- 若字段添加到 `google.cloud.movies.v2` 中的 message，使用 `google.cloud.library.v1` 的客户是否应期望看到它？若是，在字段添加后多久？其它 API 变更呢？
- 若整个主版本 `google.cloud.movies.v2` 被弃用（通常在 v3 发布之后），这是否意味着 `google.cloud.library.v1` 必须改为使用 `google.cloud.movies.v3`？若是，这是否也要求 library API 的新主版本？
- 客户端库版本控制应如何反映对依赖 APIs 的变更？

把 APIs 彼此隔离，配合以高度纪律维护的有限 common components 集合，减少大量依赖问题。

跨版本共享的 API-specific common components 为客户端库生成与打包增加复杂性，并且在版本控制方面不灵活。当 protos 因为它们在多个版本中开始相同而被复制时，它们仍可以随时间发散，因为它们彼此隔离。
