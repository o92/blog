**英文标题**：Unreachable resources  
**原文**：[AIP-217](https://google.aip.dev/217) · approved · 创建 2019-08-26  
**许可**：原文 © Google，[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)

用户偶尔会请求一份资源列表，而列表里有一组资源暂时不可用。最典型的是支持跨集合读取时（见 [AIP-159]({{< ref "aip-0159" >}})）。例如：跨多个 parent locations 列出资源，其中一个 location 暂时不可达。这时仍希望把所有可用资源交给用户，同时标明有东西缺失。

## 响应里的 unreachable

若检索数据的方法可能因一个或多个资源暂时不可达而部分失败，响应 message 必须包含一个字段来表明这一点：

```proto
message ListBooksResponse {
  // The books matching the request.
  repeated Book books = 1;

  // The next page token, if there are more books matching the
  // request.
  string next_page_token = 2;

  // Unreachable resources.
  repeated string unreachable = 3 [
    (google.api.field_behavior) = UNORDERED_LIST
  ];
}
```

- 该字段必须为 repeated string，并且应当名为 `unreachable`。
- 该字段必须包含不可达资源的 resource names，或那些阻碍到达所请求集合的资源，例如无法到达的集合的 parent resource。
  - 例如：整个 location 不可达，挡住了所请求的本地化资源集合，就包含该 location 资源。
- 该字段必须包含 *service-relative* resource names，不得包含完整 resource names、资源 URIs 或简单 resource IDs。定义见 [AIP-122]({{< ref "aip-0122" >}})。
  - 例如：`Book` 资源不可达时，`unreachable` 里放 *service-relative* resource name `"shelves/scifi1/books/starwars4"`，而不是 *full* resource name `"//library.googleapis.com/shelves/scifi1/books/starwars4"`、*parent-relative* 资源 `"books/starwars4"`、resource ID `"starwars4"` 或资源 URI。
- 响应不得再提供关于「为何所列资源不可达」的任何其它信息。
  - 例如：响应不能再带一个字段，给每个 `unreachable` 条目写错误原因。
- 服务必须提供一种方式，让用户发出更具体的请求并收到带额外信息的错误。例如针对不可达集合 parent 做 Standard Get 或 Standard List。
  - 服务也必须允许用户用更受限的参数重复原始调用。
- 出现在 `unreachable` 中的 resource names 可以是异质的。
  - `unreachable` 字段定义应当文档化此字段中可能提供哪些潜在资源，并注明以后可能扩展。
  - 例如：整个 location 与不同 location 中的特定资源都不可达时，不可达 location 的名称（例如 `"projects/example123/locations/us-east1"`）与不可达资源的名称（例如 `"projects/example123/locations/europe-west2/instances/example456"`）都会出现在 `unreachable` 里。
- `unreachable` 字段不得在列表内有语义上有意义的排序或结构。换句话说，`unreachable` 必须是无序列表。
  - 因此，`unreachable` 字段必须标注 `UNORDERED_LIST` field behavior（见 [AIP-203]({{< ref "aip-0203" >}})）。

若单个不可达 location 或资源按定义阻止返回任何数据（例如针对单个 publisher 的 list 请求，而该 publisher 不可达），服务必须以错误让整个请求失败。

## 分页

准备一页结果以兑现页面获取 RPC（例如 Standard List，见 [AIP-132]({{< ref "aip-0132" >}})）时，若服务遇到任何不可达资源或集合，必须做下列事项：

- 在 `unreachable` 响应字段中包含不可达资源的 resource name。
  - resource name 必须是对该不可达资源或集合最适当范围的。
  - 例如：区域内特定 zone 不可达，不可达 resource name 会是 zonal Location，例如 `projects/example/locations/us-west1-a`；若整个 region 不可达，resource name 会是 regional Location，例如 `projects/example/locations/us-west1`。
  - 当被识别为不可达时，无论受限分页参数例如 `order_by` 如何，resource name 都必须被包含。
- 若可用性恢复且分页参数允许包含，在后续页上填充先前视为不可达的结果。
  - 基于分页参数确定包含资格，也包括请求中没有用户指定排序时任何文档化的默认排序行为。
  - 例如：region `projects/example/locations/us-west1` 在有序分页调用的第一页不可用，并且包含其资源会违反排序，那些乱序资源不包含在后续页中。
  - 类似地：若发出完全相同的请求，并且先前视为不可达的资源再次可用，它们必须在分页参数约束内被填充。
- 若即使在上扩不可达 resource name 的范围之后，不可达 resource names 的数量仍超过文档化的最大值，限制给定响应中返回的不可达 resource names 数量。
  - 此最大值必须直接在 `unreachable` 字段注释中文档化。
  - 这独立于调用方设置的 `page_size`。

### 保留先前行为

服务可以继续先前实现的 `unreachable` 分页行为，若更改它会按 [AIP-180]({{< ref "aip-0180" >}}) 引起不兼容变更。但必须直接在 `unreachable` 字段上文档化所述行为。

## 棕地采用部分成功

为使默认行为与前述指导*不同*的现有 API（即 API 调用返回错误状态而不是部分结果）采用 `unreachable` 模式，API 必须做下列事项：

- 必须保留默认行为，以避免不兼容的行为变更。
  - 例如：若默认行为是任何 location 不可达时返回错误，该默认行为必须被保留。
- 请求 message 必须有 `bool return_partial_success` 字段。
- 响应 message 必须有标准 `repeated string unreachable` 字段。
- 上述两个字段必须同时添加。

当请求中 `bool return_partial_success` 字段设为 `true` 时，API 必须按前述指导表现，填充 `repeated string unreachable` 响应字段。

```proto
message ListBooksRequest {
  // Standard List request fields...

  // Setting this field to `true` will opt the request into returning the
  // resources that are reachable, and into including the names of those that
  // were unreachable in the [ListBooksResponse.unreachable] field. This can
  // only be `true` when reading across collections e.g. when `parent` is set to
  //  `"projects/example/locations/-"`.
  bool return_partial_success = 4;
}

message ListBooksResponse {
  // Standard List Response fields...

  // Unreachable resources. Populated when the request opts into
  // `return_partial_success` and reading across collections e.g. when
  // attempting to list all resources across all supported locations.
  repeated string unreachable = 3 [
    (google.api.field_behavior) = UNORDERED_LIST
  ];
}
```

### 部分成功的粒度

若请求中 `bool return_partial_success` 字段设为 `true`，而该请求的范围超出 API 合理报告不可达资源能力的受支持粒度，API 应当返回 `INVALID_ARGUMENT` 错误，并附解释该问题的详情。例如：若 API 仅在跨集合读取（见 [AIP-159]({{< ref "aip-0159" >}})）时支持 `return_partial_success`，当给定范围限定到特定 parent 资源集合的请求时，它返回 `INVALID_ARGUMENT`。受支持粒度必须在 `return_partial_success` 字段上文档化。

## 为什么这样规定

### 用 service-relative resource names

一般而言，如 [AIP-122]({{< ref "aip-0122" >}}) 所定义的相对 resource names，是在服务*内部*、以及在其它服务显而易见时按名称引用资源的最佳实践。完整 resource name 格式更难消费（例如客户端还要多解析一步），对 `unreachable` 的用途也过指定。资源 URIs 不是传输无关的：gRPC 用户在标准方法里拿不到它们。简单 resource IDs 在异质资源列表里，又不够说明究竟哪个资源不可达。

### 少在响应里塞额外错误详情

发现不可达资源的语境可能敏感，系统状态在调用之间可能流动。更可取的是：通过发出更具体的 RPC，把详情推迟给服务，去拿某个资源或 parent 的更多信息。这样 parent 在请求时处理所有必要的 RPC 检查与系统状态解析，而不是把潜在特权或陈旧信息塞进它不可达的更广 list 调用里。

### `unreachable` 内容无序

对广泛 API 一致性而言，`unreachable` 的内容没有特定或有序语义结构很重要。若每个 API 把特定排序烘焙进标准字段，没有任何单一实现（客户端或服务端）会正确。

### 按页填 unreachable

按页填充 `unreachable` 资源，让最终用户立刻看出这一页不完整，而不是翻完所有结果*之后*才知道。不保证会翻页到完成，所以尽早传达「这一页有不可达资源缺失」很重要。它也让用户识别：后续调用里要考虑哪些潜在问题。最后，把不可达资源留到分页结果结束，要求服务为本应独立且完全隔离的 API 调用保留状态。

### 用请求字段选择加入

引入新请求字段作为选择加入部分成功行为的方式，是在保持默认行为向后兼容的同时，传达用户意图的最佳方式。替代方案——随 `unreachable` 响应字段的引入更改默认行为——是向后不兼容变更。先前期望「任何资源不可达就失败」的用户，会假定成功响应意味着响应里所有资源都已计入。

### 两个字段同时引入

同时引入请求与响应字段，是为了防止只加其中一个所呈现的无效中间状态。若只加 `unreachable`，可能假定它为空意味着所有资源都已返回，而这可能不真。若只加 `return_partial_success`，用户没有办法知道哪些资源不可达。

### 部分成功的粒度限制

在请求范围粒度的某一层，API 根本无法枚举不可达的资源。例如：仅全局的 API 可能无法在本地化集合层级提供粒度。这时，当 `return_partial_success=true` 时抢先返回错误，保护用户免于替代方案的风险——若有问题则期望看到不可达资源，但一个也没得到，从而错误地假定一切都已检索。这与本文建议对无法兑现的请求抢先失败的指导对齐。

## 沿革

### 分页指导

如何填充 `unreachable` 字段的原始指导，是把内容当作分页结果来消费。这意味着分页资源与不可达资源不能出现在同一响应即同一页里，用户需要完全翻完所有结果才能看到是否有任何不可达。变更理由见上面「为什么这样规定」。
