字符串怎么解释、怎么限制、怎么计费，API 应当对齐。小到字段「限制为 1024 个字符」这种歧义，大到计费困惑：Datastore 里属性的名称与值，是按字符还是按字节计费？

按字节设限制，等于歧视非 ASCII 文本：它占的空间更多。按「字符」设限制，又含糊：到底是 Unicode code points、某种编码（UTF-8 或 UTF-16）的 code units、graphemes，还是 grapheme clusters？

## Unicode 速览

字符编码常被一笔带过，先对齐几个词：

- 字符串只是根据某种编码格式表示数字的字节。
- 说 **characters** 时，有时指 Unicode **code points**：Unicode 规范里的数字（最多 21 位）。
- 其它时候可能指 **graphemes** 或 **grapheme clusters**：可能有多个数值表示，也可能由不止一个 code point 表示。例如 `á` 可以写成 `U+0061 + U+0301`（`a` + 重音组合标记），也可以写成单个 code point `U+00E1`。
- Protocol buffers 用 **UTF-8**（Unicode Transformation Format）：每个 code point 最多使用 4 个 **code units**（8 位字节）的变长编码。

## 什么叫 character

在 API 文档里（参考文档、博客、营销材料、计费说明等），"character" 必须定义为 Unicode code point。

## 长度单位

API 注释里定义的所有字符串字段长度限制，必须按上面的 characters 衡量并强制。这意味着底层有一个最大限制：`4 * characters` 字节。只有专门使用由 4 个 UTF-8 code units（32 位）组成的字符时，才会碰到这个上限。

若底层数据库允许按 characters 定义限制（例如 Spanner），可以假定按字节定义的要求由存储系统处理。

## 计费单位

API 可以用 code points 或字节（UTF-8 编码）作为计费或配额衡量单位。例如 Cloud Translation 选择用 characters。若 API 没定义这一点，假定计费单位是 characters（例如每 *character* $0.01，不是每 *byte* $0.01）。

## Unique identifiers

用作 unique identifiers 的字符串，应当把输入限制为 ASCII 字符，通常是字母、数字、连字符与下划线（``[a-zA-Z][a-zA-Z0-9_-]*``）。这样永远不会因规范化而意外碰撞。

若 API 决定在 unique identifiers 里允许所有有效 Unicode 字符，必须拒绝任何不处于 Normalization Form C 的输入。

一般而言，unique identifiers 不应当以数字开头。该前缀保留给 Google 生成的标识符，也好简单区分：是我们生成的唯一数字 ID，还是用户自己选的。

Unique identifiers 应当使用最大长度 64 个字符，不过此限制可以按需扩展。64 个字符对大多数目的应足够：即使 UUID 也只需要 36 个字符。

resource ID 分段的建议见 [AIP-122]({{< ref "aip-0122" >}})。

## 规范化

值应当始终规范化为 [Normalization Form C](https://unicode.org/reports/tr15/)。Unique identifiers 必须以 Normalization Form C 存储。

设想西班牙语输入「estar é」（重音部分加粗）。可视化成 6 个「characters」（此时它们是 grapheme clusters）。Unicode 表示有两种：

- 6 个 code points：`U+0065` `U+0073` `U+0074` `U+0061` `U+0072` **`U+00E9`**
- 7 个 code points：`U+0065` `U+0073` `U+0074` `U+0061` `U+0072` **`U+0065` `U+0301`**

编码成 UTF-8 时，序列化也不一样：

- 7 个 code-units（7 字节）：`0x65` `0x73` `0x74` `0x61` `0x72` **`0xC3` `0xA9`**
- 8 个 code-units（8 字节）：`0x65` `0x73` `0x74` `0x61` `0x72` **`0x65` `0xCC` `0x81`**

为避免这种大小差异（code units 与 code points 都有），用提供字符串规范表示的 [Normalization Form C](https://unicode.org/reports/tr15/)。

## 唯一性

为唯一标识目的（例如 `name`、`id` 或 `parent`），值在检查唯一性之前必须规范化为 [Normalization Form C](https://unicode.org/reports/tr15/)（碰巧也是最紧凑的）。否则可能用本质上「同一字符串」标识两个完全不同的资源。

上例里，本质上相同的文本有两种表示。问题变成：这两种表示应否视为等价？换句话说，若有人把那两个字节序列都用在作为 unique identifier 的字符串字段里，会不会违反唯一性约束？

W3C 建议对所有在互联网上移动的内容使用 Normalization Form C。它是 Unicode 文本最紧凑的规范化形式，并避开大多数互操作问题。若两种 Unicode 字节序列有相同 NFC 表示时仍把它们视为不同，Get 就可能要用**未**规范化形式的内容来回复。那绝对不可接受。因此必须把二者视为相同：把任何传入字符串数据转换成 Normalized Form C，或拒绝不处于规范化形式的标识符。

关于该把字符串看成「表示为字节的 code points 序列」（唯一性按字节表示来定），还是看成「有许多不同可能字节表示的更高层抽象」，存在争论。这里的立场是：处理前者已经有字段类型 `bytes`。类型为 `string` 的字段已经对输入有效性表了态（必须是有效 UTF-8）。因此，只因为底层字节表示不同，就把有相同规范化形式的两个输入视为不同，有违 `string` 类型的初衷。

此区分对服务不透明的字符串（例如 `description` 或 `display_name`）通常无关紧要。但当我们依赖字符串唯一标识资源时，必须站队。

目标是：持有任何编码（ASCII、UTF-16、UTF-32 等）文本的人，都能跟 API 交互，而不踩一大堆陷阱。
