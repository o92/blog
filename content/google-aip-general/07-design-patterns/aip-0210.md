APIs 应在如何解释、限制与计费字符串值及其编码上保持一致。这从小的歧义（例如字段「限制为 1024 个字符」）一直到计费困惑（Datastore 中属性的名称与值是按字符还是按字节计费？）。

一般而言，若我们谈论以字节衡量的限制，我们在歧视非 ASCII 文本，因为它占用更多空间。另一方面，若我们谈论「字符」，我们对它们是 Unicode「code points」、特定编码（例如 UTF-8 或 UTF-16）的「code units」、「graphemes」还是「grapheme clusters」含糊不清。

## Unicode primer

字符编码往往是我们常常一笔带过的领域，因此快速入门：

- 字符串只是根据某种编码格式表示数字的字节。
- 当我们谈论 **characters** 时，有时指 Unicode **code points**，它们是 Unicode 规范中的数字（最多 21 位）。
- 其它时候我们可能指 **graphemes** 或 **grapheme clusters**，它们可能有多个数值表示，并可能由不止一个 code point 表示。例如，`á` 可以表示为 `U+0061 + U+0301` 的组合（`a` + 重音组合标记），或作为单个 code point `U+00E1`。
- Protocol buffers 使用 **UTF-8**（"Unicode Transformation Format"），这是每个 code point 最多使用 4 个 **code units**（8 位字节）的变长编码方案。

## Guidance

### Character definition

**TL;DR:** 在我们的 APIs 中，"characters" 意为 "Unicode code points"。

在 API 文档中（例如 API 参考文档、博客文章、营销文档、计费说明等），"character" **must** 定义为 Unicode code point。

### Length units

**TL;DR:** 以「characters」（如上定义）设置大小限制。

API 注释中定义的所有字符串字段长度限制 **must** 按如上定义的 characters 衡量并强制。这意味着有一个底层最大限制为（`4 * characters`）字节，不过此限制仅在专门使用由 4 个 UTF-8 code units（32 位）组成的字符时才会触及。

若你使用允许按 characters 定义限制的数据库系统（例如 Spanner），可以假定此按字节定义的要求由底层存储系统处理。

### Billing units

APIs **may** 使用 code points 或字节（使用 UTF-8 编码）作为计费或配额衡量的单位（例如 Cloud Translation 选择使用 characters）。若 API 未定义这一点，假定计费单位是 characters（例如每 *character* $0.01，不是每 *byte* $0.01）。

### Unique identifiers

**TL;DR:** Unique identifiers **should** 限制为 ASCII，一般只有字母、数字、连字符与下划线，并且 **should not** 以数字开头。

用作 unique identifiers 的字符串 **should** 把输入限制为 ASCII 字符，通常是字母、数字、连字符与下划线（``[a-zA-Z][a-zA-Z0-9_-]*``）。这确保永远不会因规范化而意外碰撞。若 API 决定在 unique identifiers 中允许所有有效 Unicode 字符，API **must** 拒绝任何不处于 Normalization Form C 的输入。一般而言，unique identifiers **should not** 以数字开头，因为该前缀保留给 Google 生成的标识符，并给我们一种简单方式来检查是我们生成了唯一数字 ID 还是 ID 由用户选择。

Unique identifiers **should** 使用最大长度 64 个字符，不过此限制可以按需扩展。64 个字符对大多数目的应足够，因为即使 UUIDs 也只需要 36 个字符。

**Note:** resource ID 分段的建议见 [AIP-122]({{< ref "aip-0122" >}})。

### Normalization

**TL;DR:** Unicode 值 **should** 以 [Normalization Form C](https://unicode.org/reports/tr15/) 存储。

值 **should** 始终规范化为 Normalization Form C。Unique identifiers **must** 始终以 Normalization Form C 存储（见下一节）。

想象我们在处理西班牙语输入「estar é 」（重音部分全文加粗）。此文本我们可能可视化为 6 个「characters」（此时它们是 grapheme clusters）。它有两种可能的 Unicode 表示：

- 使用 6 个 code points：`U+0065` `U+0073` `U+0074` `U+0061` `U+0072` **`U+00E9`**
- 使用 7 个 code points：`U+0065` `U+0073` `U+0074` `U+0061` `U+0072` **`U+0065` `U+0301`**

此外，编码为 UTF-8 时，这些 code points 有两种不同的序列化表示：

- 使用 7 个 code-units（7 字节）：`0x65` `0x73` `0x74` `0x61` `0x72` **`0xC3` `0xA9`**
- 使用 8 个 code-units（8 字节）：`0x65` `0x73` `0x74` `0x61` `0x72` **`0x65` `0xCC` `0x81`**

为避免此大小差异（code units 与 code points 都有），使用提供字符串规范表示的 [Normalization Form C](https://unicode.org/reports/tr15/)。

### Uniqueness

**TL;DR:** Unicode 值在检查唯一性之前 **must** 规范化为 [Normalization Form C](https://unicode.org/reports/tr15/)。

为唯一标识目的（例如 `name`、`id` 或 `parent`），值 **must** 规范化为 [Normalization Form C](https://unicode.org/reports/tr15/)（碰巧是最紧凑的）。否则我们可能用本质上「同一字符串」标识两个完全不同的资源。

在上例中，有两种方式表示本质上相同的文本。这提出了两种表示应否视为等价的问题。换句话说，若有人把那两个字节序列都用在作为 unique identifier 的字符串字段中，它会违反唯一性约束吗？

W3C 建议对所有在互联网上移动的内容使用 Normalization Form C。它是 Unicode 文本最紧凑的规范化形式，并避免大多数互操作问题。若我们在两种 Unicode 字节序列有相同 NFC 表示时把它们视为不同，我们就需要用**未**规范化形式的内容回复可能的 "Get" 请求。因为那绝对不可接受，我们 **must** 通过把任何传入字符串数据转换为 Normalized Form C、或拒绝不处于规范化形式的标识符，把二者视为相同。

关于我们应把字符串视为表示为字节的 code points 序列（导致基于所述字符串的字节表示确定唯一性），还是把字符串解释为有许多不同可能字节表示的更高层抽象，存在一些争论。此处采取的立场是我们已经有处理前者的字段类型：`bytes`。类型为 `string` 的字段已经对输入有效性表达了意见（它必须是有效 UTF-8）。因此，由于底层字节表示而把有相同规范化形式的两个输入视为不同，似乎有违 `string` 类型的初衷。此区分对服务不透明的字符串（例如 `description` 或 `display_name`）通常无关紧要，然而当我们依赖字符串唯一标识资源时，我们被迫采取立场。

换句话说，我们的目标是让持有任何编码（ASCII、UTF-16、UTF-32 等）文本的人与我们的 APIs 交互而没有大量「陷阱」。
