APIs 常常需要提供数据集合，最常见的是在 [List]({{< ref "aip-0132" >}}) 标准方法中。然而，集合常常可以任意大小，并且常常随时间增长，增加查找时间以及线上发送的响应大小。因此，集合必须分页。

## Guidance

返回数据集合的 RPCs **must** *一开始*就提供分页，因为向现有方法添加分页是 [向后不兼容变更](#backwards-compatibility)。

```proto
// The request structure for listing books.
message ListBooksRequest {
  // The parent, which owns this collection of books.
  // Format: publishers/{publisher}
  string parent = 1 [
    (google.api.field_behavior) = REQUIRED,
    (google.api.resource_reference) = {
      child_type: "library.googleapis.com/Book"
    }];

  // The maximum number of books to return. The service may return fewer than
  // this value.
  // If unspecified, at most 50 books will be returned.
  // The maximum value is 1000; values above 1000 will be coerced to 1000.
  int32 page_size = 2;

  // A page token, received from a previous `ListBooks` call.
  // Provide this to retrieve the subsequent page.
  //
  // When paginating, all other parameters provided to `ListBooks` must match
  // the call that provided the page token.
  string page_token = 3;
}

// The response structure from listing books.
message ListBooksResponse {
  // The books from the specified publisher.
  repeated Book books = 1;

  // A token that can be sent as `page_token` to retrieve the next page.
  // If this field is omitted, there are no subsequent pages.
  string next_page_token = 2;
}
```

- 集合的请求 messages **should** 定义 `int32 page_size` 字段，允许用户指定要返回的最大结果数。
  - `page_size` 字段 **must not** 为必填。
  - 若用户未指定 `page_size`（或指定 `0`），API 选择适当的默认值，API **should** 文档化它。API **must not** 返回错误。
  - 若用户指定大于 API 允许最大值的 `page_size`，API **should** 强制降到允许的最大 page size。
  - 若用户为 `page_size` 指定负值，API **must** 发送 `INVALID_ARGUMENT` 错误。
  - API **may** 返回比请求数量更少的结果（包括零结果），即使尚未到集合末尾。
- 集合的请求 messages **should** 定义 `string page_token` 字段，允许用户前进到集合中的下一页。
  - `page_token` 字段 **must not** 为必填。
  - 若用户在后续页请求中更改 `page_size`，服务 **must** 兑现新的 page size。
  - 用户被期望保持对该 RPC 的所有其它参数相同；若任何参数不同，API **should** 发送 `INVALID_ARGUMENT` 错误。
- 响应 **must not** 为 streaming response。
- 集合的响应 messages **should** 定义 `string next_page_token` 字段，向用户提供可用于检索下一页的 page token。
  - 包含分页结果的字段 **should** 为 message 中的第一个字段，字段号为 `1`。它 **should** 为包含构成单页结果的资源列表的 repeated 字段。
  - 若已到达集合末尾，`next_page_token` 字段 **must** 为空。这是向用户传达「集合结束」的*唯一*方式。
  - 若尚未到达集合末尾（或若 API 无法及时确定），API **must** 提供 `next_page_token`。
- 集合的响应 messages **may** 提供 `int32 total_size` 字段，向用户提供列表中的总条目数。
  - 此总数 **may** 为估计值（但 API **should** 明确文档化这一点）。

### Skipping results

分页操作的请求定义 **may** 定义 `int32 skip` 字段以允许用户跳过结果。

`skip` 值 **must** 指要跳过的个别资源数，不是页数。

例如：

- 没有 page token 且 `skip` 值为 `30` 的请求返回从第 31 个结果开始的单页结果。
- 对应第 51 个结果的 page token（因为前 50 个结果在第一页返回）且 `skip` 值为 `30` 的请求返回从第 81 个结果开始的单页结果。

若提供了无法兑现的 `skip` 值，例如由于查询海量数据集的延迟，响应 **must** 为带空结果集的 `200 OK`。若*已知*会把游标放到集合总大小之外，响应 **must not** 包含 `next_page_token`。

### Opacity

APIs 提供的 page tokens **must** 为不透明（但 URL-safe）字符串，并且 **must not** 可被用户解析。这是因为若用户能够解构它们，*他们就会这样做*。这实际上使你的 API 分页实现细节成为 API 表面的一部分，不破坏用户就无法更新那些细节。

**Warning:** 对否则透明的 page token 做 Base-64 编码 **不是** 足够的混淆机制。

对不需要存储在数据库中、且不含敏感数据的 page tokens，API **may** 通过定义带任何所需数据的内部 protocol buffer message，并发送序列化后、base-64 编码的 proto 来混淆 page token。

Page tokens **must** 仅限于指示分页过程从何处继续。它们 **must not** 对底层资源提供任何形式的授权，并且无论是否存在 page token，**must** 像任何其它请求一样对请求执行授权。

### Expiring page tokens

许多 APIs 在内部把 page tokens 存储在数据库中。此时，APIs **may** 在发送后经过合理时间让 page tokens 过期，以免无谓存储大量不太可能使用的数据。不必文档化此行为。

**Note:** 合理时间可能因 APIs 而异，经验法则是三天。

## Backwards compatibility

向现有 RPC 添加分页是向后不兼容变更。这可能看起来奇怪；向 proto messages 添加字段一般是向后兼容的。然而，此变更在*行为上*不兼容。

考虑一个集合有 75 个资源、且已经编写并部署了代码的用户。若 API 后来添加分页字段，并把默认设为 50，则该用户的代码会破坏；它原先得到所有资源，现在只得到前 50 个（并且不知道如何推进分页）。即使 API 设置更高的默认限制，例如 100，用户的集合也可能增长，*然后*代码会破坏。

此外，[客户端库实现自动分页](https://google.aip.dev/client-libraries/4233)，通常用与未分页不同的方法签名表示分页 RPCs。这意味着向先前未分页的方法添加分页会在那些库中造成破坏性变更。

因此，重要的是始终*一开始*就向返回集合的 RPCs 添加分页；它们始终重要，并且以后无法添加而不给现有用户造成问题。

**Warning:** 这也意味着，除了呈现分页字段外，它们 **must** 以非无限的默认值*实际实现*。对最初较小的集合，实现内存版本（可能先获取全部再分页）是合理的。

## Rationale

### Degraded `skip` response

大型集合、复杂查询与全球分布的数据都可能导致分页方法无法快速或有把握地兑现给定的 `skip` 请求。后端查询可能超时，数据整理可能耗时，最终用户体验不必因此受苦。此时，可以利用分页接口通过提供 `next_page_token` 让客户端保持参与，同时服务收集适当结果。当服务确定所请求的 `skip` 超出可用结果时，再次应用分页接口并省略 `next_page_token` 以表示结果结束。
