API 经常要交回数据集合，最常见的是 List（见 [AIP-132]({{< ref "aip-0132" >}})）。集合可以任意大，还会随时间增长。查找时间和线上响应都会跟着涨。所以集合必须分页。

返回数据集合的 RPC 必须*一开始*就提供分页。以后再加是[向后不兼容变更](#向后兼容)。

```proto
// The request structure for listing books.
message ListBooksRequest {
  // The parent, which owns this collection of books.
  // Format: publishers/{publisher}
  string parent = 1 [
    (google.api.field_behavior) = REQUIRED,
    (google.api.resource_reference) = {
      child_type: "library.googleapis.com/Book"
    }];

  // The maximum number of books to return. The service may return fewer than
  // this value.
  // If unspecified, at most 50 books will be returned.
  // The maximum value is 1000; values above 1000 will be coerced to 1000.
  int32 page_size = 2;

  // A page token, received from a previous `ListBooks` call.
  // Provide this to retrieve the subsequent page.
  //
  // When paginating, all other parameters provided to `ListBooks` must match
  // the call that provided the page token.
  string page_token = 3;
}

// The response structure from listing books.
message ListBooksResponse {
  // The books from the specified publisher.
  repeated Book books = 1;

  // A token that can be sent as `page_token` to retrieve the next page.
  // If this field is omitted, there are no subsequent pages.
  string next_page_token = 2;
}
```

- 集合的请求 messages 应当定义 `int32 page_size`，让用户指定最多回多少条。
  - `page_size` 不得设为必填。
  - 用户未指定 `page_size`（或指定 `0`）时，API 自己选一个合适的默认值，并且应当文档化它。不得因此返回错误。
  - 用户指定的 `page_size` 大于 API 允许的最大值时，应当强制降到允许的最大 page size。
  - 用户给 `page_size` 指定负值时，必须返回 `INVALID_ARGUMENT`。
  - API 可以返回比请求数量更少的结果（包括零条），即使还没到集合末尾。
- 集合的请求 messages 应当定义 `string page_token`，让用户前进到下一页。
  - `page_token` 不得设为必填。
  - 用户在后续页请求里改了 `page_size`，服务必须兑现新的 page size。
  - 用户需要保持对该 RPC 的所有其它参数相同；有任何不同，API 应当返回 `INVALID_ARGUMENT`。
- 响应不得做成 streaming response。
- 集合的响应 messages 应当定义 `string next_page_token`，给用户下一页的 page token。
  - 包含分页结果的字段应当是 message 里的第一个字段，字段号为 `1`。它应当是 repeated 字段，装着这一页的资源列表。
  - 已到集合末尾时，`next_page_token` 必须为空。这是向用户传达「集合结束」的*唯一*方式。
  - 尚未到集合末尾（或 API 无法及时确定）时，必须提供 `next_page_token`。
- 集合的响应 messages 可以提供 `int32 total_size`，告诉用户列表里总共有多少条。
  - 此总数可以是估计值（但应当明确文档化这一点）。

## 跳过结果

分页操作的请求定义可以加 `int32 skip`，让用户跳过结果。

`skip` 的值必须指要跳过的个别资源数，不是页数。

例如：

- 没有 page token 且 `skip` 为 `30`：从第 31 个结果开始回一页。
- 对应第 51 个结果的 page token（前 50 个已在第一页返回）且 `skip` 为 `30`：从第 81 个结果开始回一页。

若提供了无法兑现的 `skip` 值，例如查询海量数据集太慢，响应必须是带空结果集的 `200 OK`。若*已知*游标会落到集合总大小之外，响应不得包含 `next_page_token`。

## 不透明

API 提供的 page tokens 必须是不透明（但 URL-safe）的字符串，不得可被用户解析。用户能拆开，*他们就会拆*。分页实现细节一旦暴露成 API 表面，不破坏用户就改不了。

**Warning:** 对本来透明的 page token 做 Base-64 编码，**不是**足够的混淆。

对不需要存进数据库、且不含敏感数据的 page tokens，API 可以这样混淆：定义带所需数据的内部 protocol buffer message，再发送序列化后、base-64 编码的 proto。

Page tokens 必须只用来指示分页从何处继续。它们不得对底层资源提供任何形式的授权。无论有没有 page token，都必须像其它请求一样做授权。

## 过期的 page tokens

许多 API 在内部把 page tokens 存在数据库里。这时，可以在发出后经过合理时间让 page tokens 过期，免得无谓存一大堆不太可能再用的数据。不必文档化此行为。

合理时间因 API 而异，经验法则是三天。

## 向后兼容

向现有 RPC 添加分页是向后不兼容变更。看起来奇怪：往 proto messages 加字段一般是向后兼容的。但这次*行为上*不兼容。

设想集合有 75 个资源，用户代码已经写好并部署了。API 后来加上分页字段，默认 50。用户代码就坏了：原先拿到全部，现在只拿到前 50 个，还不知道怎么往下翻。即使默认设成 100，用户的集合也可能再涨，*然后*代码才坏。

另外，[客户端库会实现自动分页](https://google.aip.dev/client-libraries/4233)，分页 RPC 的方法签名通常和未分页的不一样。给先前未分页的方法加分页，会在那些库里造成破坏性变更。

所以：返回集合的 RPC 必须一开始就带分页。它们始终重要，以后再加会坑现有用户。

**Warning:** 不只是表面有分页字段。它们必须以非无限的默认值*真正实现*。集合一开始很小，先全量取再在内存里分页，是合理的。

## 为什么这样规定

### 降级的 `skip` 响应

大型集合、复杂查询、全球分布的数据，都可能让分页方法没法又快又有把握地兑现某个 `skip`。后端查询可能超时，数据整理可能很慢，最终用户体验不必跟着遭罪。这时可以继续用分页接口：给 `next_page_token`，让客户端先别走，服务一边收集合适结果。服务确定所请求的 `skip` 已经超出可用结果时，再次走分页接口，省略 `next_page_token`，表示结果结束。
