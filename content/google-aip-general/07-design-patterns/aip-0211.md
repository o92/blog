**英文标题**：Authorization checks  
**原文**：[AIP-211](https://google.aip.dev/211) · approved · 创建 2021-02-24  
**许可**：原文 © Google，[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)

大多数操作，读或写，都需要授权：有没有权限做用户正在请求的事。给*未授权*用户多少信息，必须小心。泄漏存在性本身就是安全问题。

## 先查授权

服务必须在校验任何请求之前检查授权，以保证安全的 API 表面和一致的用户体验。操作可以要求多个权限或前置条件才能授予授权。

若请求因任何原因无法通过授权检查，服务必须以 `PERMISSION_DENIED` 报错。对应错误消息应当看起来像："Permission '`{p}`' denied on resource '`{r}`' (or it might not exist)." 这样不会泄漏资源是否存在。

若因为资源不存在而无法确定对资源的授权，服务应当检查在 parent 资源上读取 children 的授权；若授权检查通过，再返回 `NOT_FOUND`。

## 多种操作

服务可能遇到这种情形：两个操作、两种不同权限，任一被调用都会揭示资源存在，但用户只对其中之一有权限。

这时，服务应当仍只检查适用于正在被调用之操作的授权。不应当试图通过检查「会揭示存在性」的相关授权来「帮忙」。这类算法做对很难，也容易意外泄漏。

例如：

- 用户无法读取的给定集合里，已经有一个资源。
- 用户*确实*有能力创建其它资源，并且该集合使用用户指定的 IDs。因重复 ID 失败，就会揭示存在性。

这时，get 或 create 在决定返回何种错误时，应当仍只检查*它们自己的*权限，而不是彼此的。

## 为什么这样规定

[RFC 7231 §6.5.3](https://tools.ietf.org/html/rfc7231#section-6.5.3) 指出：服务不想泄露存在性时，可以用 `404 Not Found` 代替 `403 Forbidden`。本文主张改用 `PERMISSION_DENIED`（对应 HTTP 的 `403 Forbidden`）。理由如下：

- 「在你有足够权限得到 `403 Forbidden` 之前一直得到 `404 Not Found`」有违直觉，排查更难。
  - 服务*可以*在仍用 `404 Not Found` 状态码的同时，附上缺失权限的信息。但这是混合消息。
- `403 Forbidden` 本质上几乎总是需要人手处理的错误。`404 Not Found` 常常是应用可以处理的有效响应（例如「get or create」）。为权限错误过载它，等于拿走这个好处。
- RFC 7231 §6.5.4 指出 `404 Not Found` 结果可缓存，但权限错误一般不可缓存。有条件地发显式缓存控制可以改善这一点，但会违背目的。
- 此处指导与大多数其它真实世界授权系统更一致。
