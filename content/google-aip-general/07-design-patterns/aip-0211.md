**英文标题**：Authorization checks  
**原文**：[AIP-211](https://google.aip.dev/211) · approved · 创建 2021-02-24

大多数操作，无论读还是写，都需要授权：做用户正在请求之事的权限。此外，向*未授权*用户提供多少信息必须小心，因为泄漏信息可能是安全问题。

## Guidance

服务 **must** 在校验任何请求之前检查授权，以确保安全的 API 表面与一致的用户体验。操作 **may** 需要多个权限或前置条件才能授予授权。

若请求因任何原因无法通过授权检查，服务 **must** 以 `PERMISSION_DENIED` 报错，并且对应错误消息 **should** 看起来像："Permission '`{p}`' denied on resource '`{r}`' (or it might not exist)." 这避免泄漏资源存在性。

若因为资源不存在而无法确定对资源的授权，服务 **should** 检查在 parent 资源上读取 children 的授权，若授权检查通过则返回 `NOT_FOUND`。

### Multiple operations

服务可能遇到一种情形：它有两个带两种不同权限的不同操作，其中任一被调用都会揭示资源的存在，但用户只对调用其中之一有权限。

此时，服务 **should** 仍只检查适用于正在被调用之操作的授权，并且 **should not** 试图通过检查会提供揭示存在性之权限的相关授权来「帮忙」，因为此类算法实现正确很复杂，且容易意外泄漏。

例如，设想一种场景：

- 用户无法读取的给定集合内存在一个资源。
- 用户*确实*有能力创建其它资源，并且该集合使用用户指定的 IDs（意味着因重复 ID 失败会揭示存在性）。

此时，get 或 create 方法在确定返回何种错误时 **should** 仍只检查*它们自己的*权限，而不是彼此的。

## Rationale

[RFC 7231 §6.5.3](https://tools.ietf.org/html/rfc7231#section-6.5.3) 指出，服务被允许在不想泄露存在性的情形下使用 `404 Not Found` 代替 `403 Forbidden`，而本文主张改用 `PERMISSION_DENIED`（对应 HTTP 中的 `403 Forbidden`）。我们采取此立场出于下列原因：

- 「在你有足够权限得到 `403 Forbidden` 之前一直得到 `404 Not Found`」的做法有违直觉，并增加排查难度。
  - 服务*可以*通过在仍使用 `404 Not Found` 状态码的同时发送关于缺失权限的信息来改善这一点，但这构成混合消息。
- 尽管 `403 Forbidden` 本质上几乎总是需要手动行动的错误，`404 Not Found` 常常是应用可以处理的有效响应（例如「get or create」）；为权限错误过载它剥夺了应用的这一好处。
- RFC 7231 §6.5.4 指出 `404 Not Found` 结果可缓存，但权限错误一般不可缓存。有条件地发送显式缓存控制可以改善这一点，但会违背目的。
- 此处指导与大多数其它真实世界授权系统更一致。
