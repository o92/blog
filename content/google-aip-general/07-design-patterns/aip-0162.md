有些 API 需要带修订历史的资源，让用户能推理资源随时间的状态。常见原因：

- 用户想回滚到先前修订，或跟先前修订做 diff。
- API 会从某个时间点的资源派生数据。这时可能希望把该资源快照下来，以后还能引用。

这里用 *revision* 指某个资源的历史引用，有意避开 *version*：后者指 API 整体的版本。

## 什么时候存修订

API 可以为资源存修订历史。有用的情形包括：

- 通过 API 暴露资源较旧的版本有价值。客户就不必自己再写一套存储和检索修订的 API。
- 其它资源依赖某资源的不同修订。
- 需要表示资源随时间的变化。

实现带修订历史之资源的 API，应当把资源修订抽象成该资源的嵌套集合。有时修订集合可以是顶层集合，例外包括：

- 资源修订意在比 parent 资源活得更久。换句话说：资源删了，修订还在。

```proto
message BookRevision {
  // The name of the book revision.
  string name = 1;

  // The snapshot of the book
  Book snapshot = 2
    [(google.api.field_behavior) = OUTPUT_ONLY];

  // The timestamp that the revision was created.
  google.protobuf.Timestamp create_time = 3
    [(google.api.field_behavior) = OUTPUT_ONLY];

  // Other revision IDs that share the same snapshot.
  repeated string alternate_ids = 4
    [(google.api.field_behavior) = OUTPUT_ONLY];
}
```

- `message` 必须标注为资源（见 [AIP-123]({{< ref "aip-0123" >}})）。
- `message` 名称必须名为 `{ResourceType}Revision`。
- 资源修订必须包含一个类型为 parent 资源 message、字段名为 `snapshot` 的字段。
  - `snapshot` 的值必须是创建修订时 parent 的配置。
- 资源修订必须包含 `create_time` 字段（见 [AIP-142]({{< ref "aip-0142" >}})）。
- 资源修订可以包含 repeated 字段 `alternate_ids`，列出该修订也被知晓的 resource IDs（例如 `latest`）。

## 何时创建修订

取决于资源，不同 API 可以有不同策略：

- 每当 parent 资源有变更时创建新修订
- 当重要系统状态改变时创建新修订
- 当被特别请求时创建新修订

API 可以用其中任何一种。必须文档化自己的修订创建策略。

## 修订的资源名称

引用资源的特定修订时，子集合名称必须名为 `revisions`。资源修订的名称格式为 `{resource_name}/revisions/{revision_id}`。例如：

```
publishers/123/books/les-miserables/revisions/c7cfa2a8
```

## 服务指定的 aliases

服务可以保留特定 IDs 作为 aliases（见 [AIP-122]({{< ref "aip-0122" >}})），例如 `latest`。这些是只读的，由服务管理。

```
GET /v1/publishers/{publisher}/books/{book}/revisions/{revision_id}
```

- 若存在 `latest` ID，它必须表示最近创建的修订。`publishers/{publisher}/books/{book}/revisions/latest` 与 `publishers/{publisher}/books/{book}` 的内容可以不同：最新修订未必等于资源的当前状态。

## 用户指定的 aliases

API 可以提供机制，让用户用 custom method `alias` 为现有修订分配 alias ID（见 [AIP-122]({{< ref "aip-0122" >}})）：

```proto
rpc AliasBookRevision(AliasBookRevisionRequest) returns (Book) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*/revisions/*}:alias"
    body: "*"
  };
}
```

```proto
message AliasBookRevisionRequest {
  string name = 1 [
    (google.api.field_behavior) = REQUIRED,
    (google.api.resource_reference) = {
      type: "library.googleapis.com/BookRevision"
    }];

  // The ID of the revision to alias to, e.g. `CURRENT` or a semantic
  // version.
  string alias_id = 2 [(google.api.field_behavior) = REQUIRED];
}
```

- 请求 message 必须有 `name` 字段：
  - 该字段必须标注为 required（见 [AIP-203]({{< ref "aip-0203" >}})）。
  - 该字段必须标识它所引用的 resource type（见 [AIP-123]({{< ref "aip-0123" >}})）。
- 请求 message 必须有 `alias_id` 字段：
  - 该字段必须标注为 required（见 [AIP-203]({{< ref "aip-0203" >}})）。
- 用户用现有 `alias_id` 调用该方法时，请求必须成功，并且 alias 会更新为指向所提供的修订。这样用户可以针对特定 alias（例如 `published`）写代码，修订可以改，代码不用改。

## 回滚

带修订历史之资源的常见用例是回滚到给定修订。API 应当用 `Rollback` custom method 处理：

```proto
rpc RollbackBook(RollbackBookRequest) returns (BookRevision) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*/revisions/*}:rollback"
    body: "*"
  };
}
```

- 该方法必须使用 `POST` HTTP 动词。
- 该方法应当返回资源修订。

```proto
message RollbackBookRequest {
  // The revision that the book should be rolled back to.
  string name = 1 [
    (google.api.field_behavior) = REQUIRED,
    (google.api.resource_reference) = {
      type: "library.googleapis.com/BookRevision"
    }];
}
```

- 请求 message 必须有 `name` 字段，指向资源应回滚到其配置的那条资源修订。
  - 该字段必须标注为 required（见 [AIP-203]({{< ref "aip-0203" >}})）。
  - 该字段必须标识它所引用的 resource type（见 [AIP-123]({{< ref "aip-0123" >}})）。

## 子资源

带修订历史的资源可以有 child resources。若有，有两种潜在变体：

- 每个 child resource 是 parent 资源整体的 child。
- 每个 child resource 是 parent 资源*单个修订*的 child。

API 不应当包含多层带修订的资源，那样很快就推不动了。

## 标准方法

任何标准方法必须实现对应的 AIP（见 [AIP-131]({{< ref "aip-0131" >}}) 到 [AIP-135]({{< ref "aip-0135" >}})），并带下列额外行为：

- List：默认情况下，list 响应中的修订必须按逆时间顺序排列。用户可以提供 `order_by` 覆盖默认行为。
- 若修订支持 aliasing，带 alias 的 resource name（例如 `revisions/1.0.2`）的 delete 方法必须移除该 alias，而不是删除该资源。

修订嵌套在资源下，也见 cascading delete（见 [AIP-135]({{< ref "aip-0135" >}})）。

## 为什么这样规定

### 把修订抽象成嵌套集合

修订作为嵌套集合下的资源，修订才是一等公民。

- 修订可以提供标准 get、list 与 delete。
- 以后要在资源 message 之外给修订加新字段，仍然灵活。

### 从 tag 并进 alias

先前有 `tag` 概念。它和 alias（见 [AIP-122]({{< ref "aip-0122" >}})）重复，术语合并掉，降低 AIP 里的复杂度。

### Output only 的资源配置

把资源配置作为 create 的一部分交给修订，也是一种选项。但那样用户可以提交该资源从未处于的修订配置。

做成 `OUTPUT_ONLY`，并要求所创建的修订表示当前时间点的资源，这个问题就没了。

## 沿革

### 从集合扩展改成子集合

2023-09，修订被抽象成嵌套资源集合。在此之前，修订更像用 `@` 符号对现有资源的扩展。列出与删除修订是资源集合上的 custom methods。单个 Get 既用来取资源修订，也用来取资源。

主要优势：资源引用可以无缝指向资源或其修订。

也有若干劣势：

- List revisions 是资源集合上的 custom method（`:listRevisions`）
- Delete revision 是资源集合上的 custom method
- 在 API discovery doc 中不可见
- Resource ID 不能使用 `@`

指导最终被改掉，让修订表现得像资源：降低用户认知负荷，也让面向资源的客户端能轻松 list、get、create 与 update 修订。

### 用 resource ID 而不是 tag

先前设计里，修订有单独的修订标识符叫 `tag`，住在修订里。

Tags 实际上是影子 resource ID，还得再搞一套基于 tag 值来创建、获取并过滤修订的方法。

把 tag 的概念并进 revision ID 之后，用户不必再熟悉第二套检索与标识方法。
