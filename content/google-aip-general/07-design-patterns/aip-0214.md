**英文标题**：Resource expiration  
**原文**：[AIP-214](https://google.aip.dev/214) · approved · 创建 2018-06-19  
**许可**：原文 © Google，[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)

客户常常希望提供给定资源或资源属性不再有用或有效的时间（例如轮换的安全密钥）。当前我们建议客户通过把精确的「expiration time」指定进 `google.protobuf.Timestamp expire_time` 字段来做；然而，当他们想指定相对时间偏移而不是特定过期时间时，这给用户增加了额外负担。

此外，世界理解「time-to-live」概念，常缩写为 TTL，但此字段的典型格式（以秒衡量的整数）在使用自动生成的客户端库时导致次优体验。

## Guidance

1. 希望传达过期的 APIs **must** 依赖名为 `expire_time` 的 [`google.protobuf.Timestamp`](https://github.com/protocolbuffers/protobuf/blob/master/src/google/protobuf/timestamp.proto) 字段。
2. 希望允许相对过期时间的 APIs **must** 定义名为 `expiration`（或 `{something}_expiration`）的 `oneof`，同时包含 `expire_time` 字段与单独的、标为 input only 的 [`google.protobuf.Duration`](https://github.com/protocolbuffers/protobuf/blob/master/src/google/protobuf/duration.proto) 字段 `ttl`。
3. 检索资源时 APIs **must** 始终在 `expire_time` 字段中返回过期时间，并让 `ttl` 字段留空。
4. 依赖「time to live」特定语义的 APIs（例如必须把 TTL 表示为整数的 DNS）**may** 使用 `int64 ttl` 字段（并且此时 **should** 提供 aip.dev/not-precedent（[AIP-200]({{< ref "aip-0200" >}})）注释）。

### Example

```proto
message ExpiringResource {
  // google.api.resource and other annotations and fields

  oneof expiration {
    // Timestamp in UTC of when this resource is considered expired.
    // This is *always* provided on output, and is calculated using
    // the value of [ttl][] if set when created.
    google.protobuf.Timestamp expire_time = 2;

    // Input only. The TTL for this resource.
    google.protobuf.Duration ttl = 3 [(google.api.field_behavior) = INPUT_ONLY];
  }
}
```

## Rationale

### Alternatives considered

#### A new standard field called `ttl`

我们考虑允许名为 `ttl` 的标准字段作为定义过期的替代方式，然而这样做会要求 API 服务持续更新该字段，像倒计时钟。这可能对读-改-写生命周期造成问题：资源处理一段时间，实际上因其处理时间而延长了寿命。

#### Always use `expire_time`

这是当前世界状态，有少数例外。在此场景中，我们可能把 `now + ttl = expire_time` 的计算推进客户端库；然而，这在命令行与使用 REST/JSON 时导致某种令人沮丧的体验。保持原样通常是默认，但似乎许多客户想要定义相对过期时间的能力，因为它相当更容易，并去掉时区、陈旧时钟与其它愚蠢错误的问题。
