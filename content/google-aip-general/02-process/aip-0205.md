API 常常先发 Alpha，尽早从客户那里收反馈。Alpha 是临时的，在重要反馈收进来、表面为 Beta 稳定下来之前，可以变很多次。

Alpha 的目的就是收集反馈，这时不必完美。作者也并非必须处理每一个可用性关切，或标准里的每一点。作者和 reviewers 常常无法就最佳设计达成一致；找出答案的最好办法，就是让用户先试用。

反馈收完、要升 Beta 时，可用性关切和文体问题就必须处理。为免忘掉，应当在 API 里显式记下来。

## 怎么标

若某 API 存在可用性关切或违反 API 标准，且当前设计在带到 Beta 之前应再看一眼，则必须有一条内部注释，用描述性链接 [aip.dev/beta-blocker](https://google.aip.dev/beta-blocker) 指到本文。这样在发到 Beta 之前，这条设计会被纠正。

注释必须同时写明：Beta 应当改成什么样。例如：

```proto
message InputConfig {
  // Parameters for input.
  // (-- aip.dev/beta-blocker: Convert well-known parameters into explicit
  //     fields before the Beta launch. --)
  map<string, string> parameters = 1;
}
```

若对 API 标准的例外确实需要带到 Beta 与 GA，见 [AIP-200]({{< ref "aip-0200" >}})。
