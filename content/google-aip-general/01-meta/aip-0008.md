**英文标题**：AIP Style and Guidance  
**原文**：[AIP-8](https://google.aip.dev/8) · approved · 创建 2019-05-28

AIP 是 API Improvement Proposal：给 API 设计和开发用的高层、短文档。目标是当 Google 内部 API 文档的事实来源，也当团队讨论、拍板指导的场地。

一篇 AIP 把单个主题讲透、写得清楚短，才有用。它要求 API 用一致的模式；它自己也应当用一致的模式来写。

## 写什么、不写什么

- 一篇 AIP 必须覆盖单个、离散的主题，并给出清楚、可执行的指导。
- 不得与另一篇 AIP 里的指导重复或打架。
- 也可以写**不要**做什么，但不应当整篇只写反模式。
- 指导若有条件（例如 Jobs 这类设计模式），必须写清：什么条件下才遵循。

AIP 里的指导必须对一类或多类 client（或其作者）有好处，包括但不限于：

- 可用于审计与分析资源的资产清单。
- 用于探索与简单自动化的命令行界面。
- 轮询实时状态并相应调整资源配置的自定义控制器（例如 auto-scaler）。
- 用于编排与自动化多个资源的 Infrastructure as Code client（见 [AIP-9]({{< ref "aip-0009" >}})）。
- 就哪些 API 适用于特定用例以及如何使用它们提供建议的推荐工具。
- 从编程语言与 API 交互的 Software Development Kit，常大量用于 data-plane 操作。
- 安全编排、自动化与修复工具。
- 用于自动化或编排任务的简单脚本。
- 测试框架。
- 对静态资源数据操作的工具。
- 用于可视化与一次性手动操作的可视化用户界面。
- Users。

改进的例子：要求新的 proto annotation，让 client 上的接口更好描述。例如要求在 `google.api.resource` annotation 上提供 `singular` 与 `plural`。

AIP 指导不得明显损害 client 的可用性，也不得明显加大实现或维护难度。

损害的例子：

- 在标准方法里塞不一致的模式，所有 client 都得加额外代码，却没什么收益。例如 List 平常这样，**除非**资源名以 Foo 开头。
- 为可读性上的一点点改进，去改已经广泛用开的字段名。例如把 `expire_time` 改成 `lapse_time`，只因为 `lapse` 在自己服务里是常用词。

篇幅必然随问题复杂度变。但多数 AIP 应当能用大约两页印刷篇幅讲完。

### 文件结构

AIP 必须用 Markdown 写，必须用四位数字命名（例如 `0008.md`）。服务于特定 scope 的 AIP 必须放在该 scope 的子目录里。

AIP 必须有恰当的 front matter。

```yaml
---
id: 8
state: reviewing
created: 2019-05-28
permalink: /8
redirect_from:
  - /08
  - /008
  - /0008
---

```

front matter 必须包含：

- `aip` 键：
  - `id`：必填。该 AIP 的 ID，整数。
  - `state`：必填。当前状态，全小写。有效状态见 [AIP-1]({{< ref "aip-0001" >}})。常见是 `draft`、`reviewing`、`approved`。
  - `created`：必填。最初起草的 ISO-8601 日期（`yyyy-mm-dd`），不加引号。
  - `updated`：最近修订的 ISO-8601 日期（`yyyy-mm-dd`）。
  - `scope`：该 AIP 的 scope。必须与该 scope 的目录名一致。ID >= 1000 的 AIP 必填，否则禁止。
- `permalink` 键（必填）：必须设为 `/{aip.scope}/{aip.id}`。没有 scope 时用 `/{aip.id}`。
- `redirect_from` 键：应当列出读者可能输入的 `/{aip.id}` 变体，包括：
  - `/{aip.id}`（当 permalink 含 scope 时）
  - 带前导零的 AIP ID，从一位零填到四位（例如 `/08`、`/008`、`/0008`）。

### 文档结构

AIP 必须以带标题的顶级标题开头（`# Title`）。标题应当是名词，不要用祈使句。例如用 "Bad API precedents"，不要用 "Avoid breaking API precedent"。

接下来应当是引言（不再加标题），然后是 `## Guidance`。有必要的话，指导之后可以按这个顺序再加节：

- "Further reading"：指向其他 AIP 的项目符号列表，那些篇有助于把本篇读完整。
- "Appendices"：同一篇里的进一步解释。相对少见。需要对决策做大量论证时很重要，常常是把考虑过的替代方案写清楚，好解释为什么是现在这条。
- "Changelog"：自首次撰写以来的变更列表。

guidance 可以再分子节。子节会进目录，也会生成可供引用的锚点。

下面是用到各主要章节的骨架：

```md
# AIP 标题

开篇讲这篇 AIP 为什么存在：把问题说清楚，但先不告诉读者要怎么做。

## Guidance

这一节告诉读者怎么做。常见写法：先一句总要求，再给例子，再用列表把例子拆开讲。

### 子节

子节可以单独引用，用来展开细节。

## Rationale

可选。讲「为什么要这样规定」。设计权衡必须写在这里，不要散落到其它节，好让正文能当速查。

## History

可选。记录一次重大改写前后的背景。changelog 是一行一条的变更摘要；History 用叙述把大事讲清楚。不要在这里穷举所有改动，那是 changelog 的事。

## Further reading

通常是其它 AIP 的列表，例如：

- [AIP-1](./0001.md): AIP purpose and guidelines

## Changelog
```

A bulleted list of changes in reverse chronological order, using the following
format:

- **2020-02-18**: Specified ordering.
- **2019-07-01**: Added a subsection clarifying XYZ.
```

应当尽量跟这个总格式。有必要可以偏离。尤其是：死守格式反而更难读，哪怕读者已经习惯常见写法。

除标题外，必须只用二级标题（`##`）及以上。应当只用二级和三级（`##`、`###`）。

### 要求级别用词

原文 AIP 应当使用下列要求级别关键词：MUST、MUST NOT、SHOULD、SHOULD NOT、MAY，含义见 [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt)。

在 AIP 里用这些词时，必须小写并加粗。不应当拿它们当普通英文用。

用 SHOULD 或 SHOULD NOT 时，必须附上：什么别的关切可以压过这条。有效例子要写出来。

rationale 用来补背景、帮人把指导理解完整。不得在 rationale 里写指导，也不得在那里用 RFC 2119 那些词。

### 代码示例

API 设计示例应当用 [protocol buffers](https://developers.google.com/protocol-buffers/)。示例应当只覆盖足以讲清概念的语法。示例里出现 RPC 时，应当带上 `google.api.http` annotation。

### 引用其他 AIP

引用时必须写成 `AIP-XXXX`，不补零（例如 `AIP-8`，不是 `AIP-0008`），并且必须链到那一篇。合适的时候，链接可以指到那一篇的某一节。

AIP 链接必须用仓库里文件的相对路径（核心 AIP 如 `./0008.md`，子目录里的如 `../0008.md`）。这样在 AIP 站点上、在 GitHub 上看 Markdown、用本地开发服务器、或在分支上，链接都能工作。

## 为什么面向广泛的 client 做设计

API 指导跟任何软件一样：目的清楚、受益者清楚，才有用。

改进 API 设计的受益者是 users。这些 users 按自己的用例，通过上文那些 client 跟 API 打交道。

所以写指导时必须把对这些 client 的影响想宽。
