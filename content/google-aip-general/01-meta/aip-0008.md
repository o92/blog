**英文标题**：AIP Style and Guidance  
**原文**：[AIP-8](https://google.aip.dev/8) · approved · 创建 2019-05-28

AIP 是 **API Improvement Proposal**，一份为 API 设计与开发提供高层、简明文档的设计文档。目标是让这些文档成为 Google 内部 API 相关文档的事实来源，以及 API 团队讨论并就 API 指导达成共识的方式。

AIP 在清晰、简洁、且把单个主题或问题讲透时最有用。正如 AIP 描述 API 中应使用的一致模式与文体，它们自身也**遵循**一致的模式与文体。

## Guidance

- AIP **must** 覆盖单个、离散的主题，并给出清晰、可执行的指导。
- AIP **must not** 与另一篇 AIP 中的指导重复或矛盾。
- AIP **may** 也覆盖**不要**做什么，但 **should not** **只**覆盖反模式。
- 若 AIP 指导是有条件的（例如 Jobs 这类设计模式），该指导 **must** 清楚说明在何种条件下应遵循。

AIP 中的指导 **must** 有益于一类或多类 client 或其作者，包括但不限于：

- 可用于审计与分析资源的资产清单。
- 用于探索与简单自动化的命令行界面。
- 轮询实时状态并相应调整资源配置的自定义控制器（例如 auto-scaler）。
- 用于编排与自动化多个资源的 Infrastructure as Code（[AIP-9]({{< ref "aip-0009" >}})） client。
- 就哪些 API 适用于特定用例以及如何使用它们提供建议的推荐工具。
- 从编程语言与 API 交互的 Software Development Kit，常大量用于 data-plane 操作。
- 安全编排、自动化与修复工具。
- 用于自动化或编排任务的简单脚本。
- 测试框架。
- 对静态资源数据操作的工具。
- 用于可视化与一次性手动操作的可视化用户界面。
- Users。

改进的例子包括：

- 要求新的 proto annotation，使 client 上的接口更具描述性（例如要求在 `google.api.resource` annotation 上提供 `singular` 与 `plural`）。

AIP 指导 **must not** 对 client 的可用性、实现难度或维护难度造成显著损害。

损害的例子包括：

- 在标准方法中引入非一致模式，以至于所有 client 都必须增加额外代码却没有足够收益（例如 List 的行为是这样，**除非**资源名以 Foo 开头）。
- 为可读性上的微小改进而重命名已广泛确立的字段（例如把 `expire_time` 改成 `lapse_time`，只因为 `lapse` 在我的服务里是常用词）。

AIP 篇幅必然随问题复杂度而变，但多数 AIP **should** 能用大约两页印刷篇幅覆盖其内容。

### File structure

AIP **must** 用 Markdown 撰写，且 **must** 用四位数字命名（示例：`0008.md`）。服务于特定 scope 的 AIP **must** 放在该 scope 的子目录中。

AIP **must** 具有恰当的 front matter。

```yaml
---
id: 8
state: reviewing
created: 2019-05-28
permalink: /8
redirect_from:
  - /08
  - /008
  - /0008
---

```

AIP 的 front matter **must** 包含：

- `aip` 键：
  - `id`：必填。该 AIP 的 ID，整数。
  - `state`：必填。AIP 的当前状态，全小写。有效状态见 [AIP-1]({{< ref "aip-0001" >}})，常见状态为 `draft`、`reviewing` 与 `approved`。
  - `created`：必填。该 AIP 最初起草的 ISO-8601 日期（`yyyy-mm-dd`），不加引号。
  - `updated`：该 AIP 最近修订的 ISO-8601 日期（`yyyy-mm-dd`）。
  - `scope`：该 AIP 的 scope。**must** 与该 scope 的目录名一致。ID >= 1000 的 AIP 必填，否则禁止。
- `permalink` 键（必填）：**must** 设为 `/{aip.scope}/{aip.id}`。若无 scope，则用 `/{aip.id}`。
- `redirect_from` 键：应包含读者可能输入的任何 `/{aip.id}` 变体列表，包括：
  - `/{aip.id}`（当 permalink 含 scope 时）
  - 带前导零的 AIP ID，从一级零填充到四位（例如：`/08`、`/008`、`/0008`）。

### Document structure

AIP **must** 以带 AIP 标题的顶级标题开头（`# Title`）。标题 **should** 是名词（不是祈使句）。例如用 "Bad API precedents"，而不是 "Avoid breaking API precedent"。

AIP **should** 接着以引言开始（不再加标题），然后是 `## Guidance` 标题。如有必要，AIP **may** 在指导之后按下列顺序包含以下任一节：

- "Further reading" 是指向其他 AIP 的项目符号列表，这些 AIP 有助于完整理解当前 AIP。
- "Appendices" 覆盖同一 AIP 中的进一步解释。相对少见，但在 AIP 需要对决策做大量论证时很重要。这常常主要是对所考虑替代方案的说明，以帮助解释该指导。
- "Changelog" 是自首次撰写以来对该 AIP 所做变更的项目符号列表。

guidance 一节 **may** 包含进一步阐述细节的子节。子节会自动在目录中生成条目，并生成可供引用的锚点。

以下是使用各主要章节的 AIP 骨架示例：

```md
# AIP title

The introductory text explains the background and reason why the AIP exists. It
lays out the basic question, but does not tell the reader what to do.

## Guidance

The "guidance" section helps the reader know what to do. A common format for
the guidance section is a high-level imperative, followed by an example,
followed by a bulleted list explaining the example.

### Subsection

Individual subsections can be cited individually, and further elaborate
details.

## Rationale

The "rationale" section is optional, and helps the reader understand the
motivation behind specific guidance within the AIP.

Deeper explanations of design justification and tradeoffs **must** be in the
rationale instead of other sections, to ensure the rest of the document acts as
an easily actionable reference.

## History

The "history" section is optional, and documents events and context around a
significant edit to an AIP. For example, explanation of rewrite would be
included in this section

While the changelog is a dotted list of one-line summaries of changes to an AIP,
the history section should elaborate on significant events in a descriptive
format.

The section **must not** be used to exhaustively enumerate all changes. This
is what the changelog provides.

## Further reading

A bulleted list of (usually) other AIPs, in the following format:

- [AIP-1](./0001.md): AIP purpose and guidelines

## Changelog

A bulleted list of changes in reverse chronological order, using the following
format:

- **2020-02-18**: Specified ordering.
- **2019-07-01**: Added a subsection clarifying XYZ.
```

AIP **should** 尽量遵循这一总体格式，但若有必要 **may** 偏离（尤其是若遵循该格式反而更难理解，哪怕读者已经习惯阅读通常格式的 AIP）。

**Note:** 除标题外，AIP **must** 只使用二级标题（`##`）及以上。AIP **should** 只使用二级与三级标题（`##`、`###`）。

### Requirement keywords

AIP **should** 使用下列要求级别关键词："MUST"、"MUST NOT"、"SHOULD"、"SHOULD NOT" 与 "MAY"，其解释见 [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt)。

在 AIP 中使用这些术语时，它们 **must** 为小写且 **加粗**。这些术语 **should not** 以其它方式使用。

若使用 "SHOULD" 或 "SHOULD NOT"，它们 **must** 包含其它关切可能压过该指导的有效例子。

**Important:** 若使用 rationale，它用于提供背景与更完整的理解，但 **must not** 包含指导（且 **must not** 使用 RFC-2119 术语）。

### Code examples

AIP 中的 API 设计示例 **should** 使用 [protocol buffers](https://developers.google.com/protocol-buffers/)。示例 **should** 只覆盖足以解释该概念的语法。在示例中使用 RPC 时，**should** 包含 `google.api.http` annotation。

### Referencing AIPs

当 AIP 引用其他 AIP 时，行文 **must** 使用 `AIP-XXXX` 格式且不补零（例如 `AIP-8`，而不是 `AIP-0008`），并且 **must** 链接到相关 AIP。AIP 链接 **may** 在合适时指向该 AIP 的某一节。

**Important:** AIP 链接 **must** 使用仓库中文件的相对路径（核心 AIP 如 `./0008.md`，子目录中的 AIP 如 `../0008.md`）；这确保链接在 AIP 站点上、在 GitHub 上查看 Markdown 文件时、使用本地开发服务器时、或在分支上都能工作。

## Rationale

### 面向广泛的 client 做设计

API 指导与任何软件类似，在有明确目的与目标受益者时最有益。

改进 API 设计的受益者是 users。这些 users 按其用例通过上文列举的各类 client 与 API 交互。

因此 API 指导必须广泛考虑对这些 client 的影响。
