标准常常是 API **已经发布之后**才补上的。有时故意不跟标准走也说得通：要跟既有系统对齐、性能卡得很死，或别的现实约束。评审再仔细，错误也会漏。

既有错误往往改不了，标准也不可能覆盖每一种用例。例外会在 API 上待很久。新 API 又爱抄旧 API 的名字、类型、结构。于是一篇里的破例会溢到别的 API，哪怕当初那条理由在新 API 上根本不成立。

所以要「止住出血」：别让这些例外渗进新 API。每条例外把原因记下来，历史才不会丢。

## 怎么标

API 不论为何违反 AIP 标准，都必须有一条内部注释，用描述性链接 [aip.dev/not-precedent](https://google.aip.dev/not-precedent) 指到本文。这样别人不会照抄，也不会把错误当成「先前已批准 API」的先例来引。

注释还应当写清：违反了哪条、为什么非这样不可。例如：

```proto
message DailyMaintenanceWindow {
  // Time within the maintenance window to start the maintenance operations.
  // It must use the format "HH MM", where HH : [00-23] and MM : [00-59] GMT.
  // (-- aip.dev/not-precedent: This was designed for consistency with crontab,
  //     and preceded the AIP standards.
  //     Ordinarily, this type should be `google.type.TimeOfDay`. --)
  string start_time = 2;

  // Output only. Duration of the time window, automatically chosen to be
  // smallest possible in the given scenario.
  // (-- aip.dev/not-precedent: This preceded the AIP standards.
  //     Ordinarily, this type should be `google.protobuf.Duration`. --)
  string duration = 3;
}
```

只有处于 beta 或 GA 的 API 才应被视为可立先例。

### 本地一致性

若某 API 通篇都在违反某条标准，仅为了跟全局标准对齐而拆掉既有模式，对 users 会很突兀。

例如：该 API 所有资源都用 `creation_time`，而不是 [AIP-142]({{< ref "aip-0142" >}}) 的标准字段 `create_time`。那这个 API 里的新资源应当继续跟本地模式。

但别人要仿这个 API 时，应当被告知：这跟标准相反，发新 API 时不应当当先例引。

```proto
// ...
message Book {
  // (-- aip.dev/not-precedent: This field was present before there was a
  //     standard field.
  //     Ordinarily, it should be spelled `create_time`. --)
  google.protobuf.Timestamp creation_time = 1;
}

// ...
message Author {
  // (-- aip.dev/not-precedent: `Book` had `creation_time` before there was
  //     a standard field, so we match that here for consistency. Ordinarily,
  //     this would be spelled `create_time`. --)
  google.protobuf.Timestamp creation_time = 1;
}
```

### 上线前就漏了、或标准来得更晚

违反有时在上线前被忽略，API 已经稳定，再改就很难。稳定 API 也可能早于某条标准。

这些情形下，很难让 API 符合标准。但仍应标明：这个功能跟标准相反。免得别的 API 复制，还拿既有 API 当「设计该获批」的理由。

### 迁就外部规范

偶尔必须违反标准：这个请求是在实现外部规范（例如 OAuth），而那份规范跟 AIP 冲突。这时跟外部规范走，往往是合适的。

### 迁就既有系统

跟上面类似：API 为迁就既有系统而违反 AIP，也可能恰当。本质一样——客户在哪儿，就往哪儿靠。例如跟合作伙伴 API 集成，或做成长得像。

### 赶工

有时用户必须在非常硬的截止日期前拿到 API 表面，否则生意会丢。多数 API 是商业的，就会有这种时候：本可以更好，但那个形态赶不上截止日期。这时 API review councils 可以因时间和业务约束，批准发布违反指南的 API。

### 技术约束

内部系统有时有非常具体的实现需求。例如依赖用 UTF-16 而不是 UTF-8 的 operation transform。这时跟 AIP 走要额外干活，对 API consumer 却没什么明显价值。将来很可能要暴露 API 的系统，应当把这点记在心里，别把底层建成以后很难跟 AIP 对齐。
