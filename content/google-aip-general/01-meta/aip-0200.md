**原文**：[AIP-200](https://google.aip.dev/200) · approved · 创建 2018-06-28 · 亦见 [aip.dev/not-precedent](https://google.aip.dev/not-precedent)

很多时候，API 的写法与这些标准在 API **已经发布之后**才加入的新指导并不匹配。此外，有时出于特定理由有意违反标准是合理的，例如与既有系统保持一致、满足严苛的性能要求，或其它实际关切。最后，无论发布前评审多么仔细，有时仍会有错误漏过。

由于往往无法修正既有错误，也无法让标准覆盖每一种用例，API 可能在相当长时间内卡在这些例外上。进一步，由于新 API 常常把设计（名称、类型、结构等）建立在既有 API 之上，一篇 API 中的标准违反可能溢到其它 API，即便当初破例的理由对那些 API 并不适用。

因此，必须「止住出血」，避免这些标准例外渗入新 API，并额外记录每条例外的原因，以免历史经验丢失。

## Guidance

若某 API 因任何原因违反 AIP 标准，**must** 有一条内部注释，用其描述性链接（[aip.dev/not-precedent](https://google.aip.dev/not-precedent)）指向本文，以确保他人不会复制这些违反，或把错误当作「先前已批准 API」的先例来引用。

该注释还应解释违反了什么标准以及为何必要。例如：

```proto
message DailyMaintenanceWindow {
  // Time within the maintenance window to start the maintenance operations.
  // It must use the format "HH MM", where HH : [00-23] and MM : [00-59] GMT.
  // (-- aip.dev/not-precedent: This was designed for consistency with crontab,
  //     and preceded the AIP standards.
  //     Ordinarily, this type should be `google.type.TimeOfDay`. --)
  string start_time = 2;

  // Output only. Duration of the time window, automatically chosen to be
  // smallest possible in the given scenario.
  // (-- aip.dev/not-precedent: This preceded the AIP standards.
  //     Ordinarily, this type should be `google.protobuf.Duration`. --)
  string duration = 3;
}
```

**Important:** 只有处于 beta 或 GA 的 API 才应被视为可立先例。

### Local consistency

若某 API 通篇违反某条标准，仅为遵守全局标准而打破既有模式，对 users 会突兀且令人沮丧。

例如，若某 API 的所有资源都使用 `creation_time`（而不是 [AIP-142]({{< ref "aip-0142" >}}) 所述的标准字段 `create_time`），则该 API 中的新资源应继续遵循本地模式。

但其它可能仿效该 API 的人应被告知：这与标准相反，在发布新 API 时不应当作先例引用。

```proto
// ...
message Book {
  // (-- aip.dev/not-precedent: This field was present before there was a
  //     standard field.
  //     Ordinarily, it should be spelled `create_time`. --)
  google.protobuf.Timestamp creation_time = 1;
}

// ...
message Author {
  // (-- aip.dev/not-precedent: `Book` had `creation_time` before there was
  //     a standard field, so we match that here for consistency. Ordinarily,
  //     this would be spelled `create_time`. --)
  google.protobuf.Timestamp creation_time = 1;
}
```

### Pre-existing functionality

标准违反有时在上线前被忽略，导致 API 变得稳定、因而难以修改。此外，稳定 API 可能早于某条标准要求。

在这些情形下，很难让 API 符合标准。但仍应标明该功能与标准相反，以免其它 API 复制该错误，并引用既有 API 作为其设计应获批准的理由。

### Adherence to external spec

偶尔，API 必须违反标准，因为特定请求是外部规范（例如 OAuth）的实现，而其规范可能与 AIP 指南冲突。此时，遵循外部规范往往是合适的。

### Adherence to existing systems

与上述外部规范类似，API 以某种方式迁就既有系统而违反 AIP 指南，也可能是恰当的。这在根本上类似：明智的做法是迁就客户所在之处。一个可能的例子是与合作伙伴 API 集成或保持相似。

### Expediency

有时用户必须在非常硬的截止日期前拿到 API 表面，否则生意会流失。由于多数 API 服务于商业目的，会有这样的时候：API 本可以更好，却无法在截止日期前做到并以那种形态交到用户手中。在那些情况下，API review councils **may** 因时间与业务约束而批准发布违反指南的 API。

### Technical concerns

内部系统有时有非常具体的实现需求（例如依赖使用 UTF-16 而非 UTF-8 的 operation transform），而遵循 AIP 指南需要额外工作，对 API consumer 却没有显著价值。将来很可能暴露 API 的系统应把这一点记在心里，避免建成难以遵循 AIP 指南的底层基础设施。
