对应原书 **4.4–4.6**：开场/收场如何把焦点放在人；九种协作风格；以及会后回顾。

## Check-in / Check-out（4.4）

许多人无法「进门就写领域事件」。没有过渡就直接建模，人还停在上一场会/情绪里。**Check-in** 先安人、再定向目标；**Check-out** 结束时再聚焦人，把冲突与张力留在门口，并可收反馈（如 Wow / How about?）。

**特征摘要（4.4.2）**

- 不是对话，是分享与「倾倒」
- 独白：说话时不被打断
- 每人至少说点什么（说 pass 也行）
- Popcorn：想说时再说，不要点名逼人
- 引导者先示范开场；结束时摘要 → 问漏了什么 → 问是否有人想回应刚才所听

问题可浅可深，视目标与动力学而定。价值：看见情绪、能量、可能挡路的社会动力学；帮引导者决定往哪深挖、是否改议程；简单却能防止阴影变成 Demons。勿把人逼到聚光灯下硬反馈——**质量优于被迫数量**；没反馈也可能是压力、不敢说，或其实觉得很好。

## 协作风格（4.5）

人越多：知识越多，意见与偏见也越多，决策与包容更难。风格是建模阶段的 **enabling constraints**，让信息与洞见流动。

| 风格 | 一句话 |
|--|--|
| **Together Alone** | 同场各自先建模/写想法，再汇合分享（设计冲刺常见）；降主导、增产选项。例：Bytesize Architecture Session 每人先画架构再分享 |
| **Split and Merge** | 大组（启发：深挖时 >7 人就难决策）切成 3–7 人小组，按 Pivotal Event等切开深挖，再合并领域模型 |
| **Small Group Diverge and Converge** | 小组各自发散出不同领域模型/故事线，再收敛比权衡（软件设计 EventStorm 出现两条竞争线时常用） |
| **1-2-4-All** | Liberating Structures：独自 → 两人 → 四人 → 全体，逐级放大仍保多样 |
| **Ensemble** | 借鉴 ensemble programming：少数角色轮换，带知识缺口的群体合奏同一领域模型 |
| **Fishbowl** | 内圈 3–6 人建模，外圈观察记问题；可限时切入或换位。适演示期望做法、大组经验不均 |
| **Anarchy!** | 经验相当、长期共事的团队：少干预风格与工具，让自组织；引导者更盯阴影与反思 |
| **Guerilla** | **不在**正式会话用，而为争取 Buy-in：公开角落自己开画、故意露假设/错误，引路人加入 |
| **The Secret Modeler** | 无权组织正式会话时，私下（本子/白板/在线板）把对话可视化，借图问有力问题 |

**怎么用（4.5.10）**：短会话不必过度预选（基础 EventStorm 常从 Together Alone 写便签，再一起 enforce timeline）。长而复杂的一天可按段落预想切换点；不熟的风格更要准备。启发：同一风格用久了可换（Different trumps same）——换风格常带来新洞见。

## Retrospective（4.6）

Check-out 与「接下来会怎样」说清后正式散会。可选：散会前 flipchart 上自愿写「何好 / 还想问什么」，或 ROTI / 内容 / 结构三量表；说明可选，次日邮件再开反馈通道。

参与者离开后，与筹备相关的人收拾、拍照（线下）、快速过反馈 → **回顾协作本身**：何好、何差、学到什么、下一场改什么。

引导者第一时间写下观察与感受（易逝）；可隔至少一天再正式评，减轻当下偏见。常忘做回顾 = 早期大错之一；觉得「挺好就行」或时间紧时更要有意识取舍。
