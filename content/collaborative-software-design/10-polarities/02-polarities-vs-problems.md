对应原书 **10.1**：有些问题解不了——要管理，不要硬选边。

## 有些问题解不了（10.1）

「项目还要几个月：今晚该锻炼还是该休息？」——感觉像二选一，其实是 **Polarity**：活动与休息互依，要长期两边都拿到好处，否则烧干。

软件协作里同理：**开写还是继续建模？集中决策还是分散？稳定还是变化？** 用「选边」的解题技能硬套「选一边」去对付极性，往往更糟——两极**互补互依**，永久只选一边会吃到对侧 downside。

## 什么是极性（10.1.1）

极性是 **ongoing**、没有「选一边就结束」的清晰解法的挑战。感觉上好像必须二选一；事实上要知道**何时**偏某一极、何时放回另一极——最大化两侧好处。

## 怎么认：问题 vs 极性（10.1.2）

> GUIDING：碰到难两难时先问——这是要**解决**的问题，还是要**管理**的极性？

| | 问题（Problem） | 极性（Polarity） |
|--|--|--|
| 终点 | 有清晰终点与较好答案 | 持续；要来回平衡 |
| 关系 | 方案可独立成立 | 两极互补互依 |
| 例 | 今晚去 A 餐厅还是 B；要不要投这笔钱；要不要加架构师 | 短期交付 AND 长期质量；个人 AND 团队；创新 AND 效率 |

自检两问：

1. **困难是否 ongoing？**  
2. **是否存在互依的两极？**（个人 vs 团队、远程 vs 现场、创新 vs 效率……）

未管理的极性 → 反复冲突，易从功能性滑到功能失调。要管理得好，必须**同时看见两侧**——协作建模要的「完整共享现实」也依赖这一点。

## 协作建模里常见极性（10.1.3）

| 一极 | 另一极 |
|--|--|
| Planning（协作建模） | Action（编码） |
| Individual responsibility | Organizational responsibility |
| Stability | Change |
| Thinking fast | Thinking slow |
| Autocratic | Democratic |
| Centralized | Decentralized |
| Discussion | Dialogue |
| Toughness | Empathy |
| Part（个人） | Whole（团队） |
| Task oriented | Relationship oriented |
| Innovation | Efficiency |
| Solo | Pair / Ensemble |
| Short term | Long term |
| Bottom-up | Top-down |

极性可在群体、个人、引导者之间。**不是每次都要当场处理**：

> GUIDING：发现极性后，与群体验证，再问「现在可视化它有没有价值？」

## Crusaders 与 Tradition Bearers（10.1.4）

Johnson：两股力把人从一极推向另一极。

- **Crusaders**：该变了——当前极负面太多。  
- **Tradition Bearers**：现在有用——换极会带来对侧负面。

双方都盯着己侧正面与对侧负面，看不见对侧正面。管理目标却是**尽量待在两侧正面**。火气大时双方拒绝看完整画面——引导者要帮群体看见「both/and」。
