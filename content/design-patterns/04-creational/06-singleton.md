## 意图

保证一个类仅有一个实例，并提供全局访问点。

## 问题与解法

- **问题**：某些资源（配置、设备、连接池门面）必须全局唯一，又要控制访问。
- **解法**：私有构造 + 静态获取实例；注意多线程、懒加载、序列化等语言细节。现代实践更常依赖 DI 容器的单例生命周期。

## 使用场景

- 确需进程内唯一实例，且需要统一访问点（设备驱动、日志门面、某些硬件抽象）。
- 实例创建昂贵，又希望懒加载且全局共享同一份。
- 必须控制并发下「只初始化一次」（如 `sync.Once`）。
- 现代实践中更常见的是：由 DI 容器配置单例生命周期，而不是到处手写全局变量。
- 例子：进程级配置中心客户端；唯一的指标上报器；旧代码里的「应用上下文」。能注入依赖时，优先显式注入而非全局单例。

## 优点

- 保证唯一实例，避免重复占用昂贵资源。
- 提供受控的访问点，比「谁都可以 `new`」更清晰（在确有此需求时）。
- 懒加载可推迟初始化成本到首次使用。
- 在遗留系统中，常是收敛全局状态的权宜之计。
- 与 Facade 等搭配时，可简化「全进程共用一个入口」的用法。

## 缺点

- 实质是全局状态：隐藏依赖，调用栈上看不出谁依赖了它。
- 难测：测试间互相污染，要重置/替换很麻烦。
- 常违反单一职责：既管「唯一性」又塞业务逻辑。
- 并发、多进程、多类加载器、序列化反序列化都会破坏「唯一」假设。
- 过度使用会阻碍扩展与替换（假单例、可测试性差）；多数业务对象并不需要单例。

## 易混 / 关系

外观上像全局变量；Facade 有时被做成单例。能用显式注入就少用。

## Go 示例

进程内全局配置（如 Env）只需加载一次，多处 `GetConfig()` 应拿到同一实例。用 `sync.Once` 保证初始化只跑一遍；能注入依赖时尽量少用全局单例。

```go
package main

import (
	"fmt"
	"sync"
)

type Config struct{ Env string }

var (
	cfg  *Config
	once sync.Once
)

func GetConfig() *Config {
	once.Do(func() {
		cfg = &Config{Env: "prod"}
	})
	return cfg
}

func main() {
	a, b := GetConfig(), GetConfig()
	fmt.Println(a == b, a.Env) // true prod
}
```
